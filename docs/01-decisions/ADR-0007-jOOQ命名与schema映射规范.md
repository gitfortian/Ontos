## 背景

编译器采用 jOOQ **无代码生成模式**（技术选型 §4.3 冻结）：不引入生成类，物理名通过 `DSL.name(...)`
动态构造。规范未定时，出现两个风险：物理名大小写/引号行为不一致导致 PoC #2 可复现被破坏；
清单里的物理名携带需要转义的字符（空格、中文、保留字）时静默产生错误 SQL。本 ADR 把规则定死。

## 决策

1. **物理名唯一来源是已发布清单**：`table` / `column` 一律从 `SemanticManifest` 解析
   （`metric.getTable()` / `dimension.getColumn()`），DSL 代码里**禁止手写任何物理标识符字面量**。
   现状符合（`SqlCompiler` 已如此），列入代码评审检查项。
2. **命名形态**：全部使用**限定名**（`schema.table` / `schema.table.column` 两段或三段），
   由 `columnName()` / `tableName()` 按 `.` 拆段传入 `DSL.name(...)`；禁止单段裸名。
3. **大小写约定**：清单中的物理名必须为 **PostgreSQL 惯例的小写 snake_case**；
   `OntologyPublishValidator` 新增校验项：物理名匹配 `^[a-z][a-z0-9_]*(\.[a-z][a-z0-9_]*)*$`，
   违规拒绝发布（把「需要转义的名字」挡在发布前，而不是运行时靠引号兜底）。
4. **保留字与特殊字符**：不做白名单枚举，直接按第 3 条的正则挡掉——任何需要 jOOQ 引号转义
   才能工作的名字都不得发布。
5. **参数绑定**：全部值走绑定参数（`ParamType.INDEXED`），零字符串拼接（PoC #4 判据延续）；
   `DSL.field(name, type)` 的类型显式声明（时间列 `Timestamp.class` 等），不做运行时类型推断。
6. **方言锁定**：`DSL.using(SQLDialect.POSTGRES)` 单例复用；`FETCH NEXT ? ROWS ONLY` 语法
   随方言产出，不手写 limit 字符串。
7. **可复现性优先**：任何命名相关改动必须跑 PoC #2 回归（同一清单重复编译逐字一致）。

## 备选方案

| 备选 | 为何未选 |
|---|---|
| 引入 jOOQ 代码生成 | 违反技术选型 §4.3「无代码生成模式」冻结；生成类与动态清单模型冲突 |
| 允许大写/混合大小写物理名靠引号转义 | 转义名进审计后难读、易错；发布期挡掉更符合 fail-closed |
| 物理名散落各处由调用方传入 | 破坏「物理名只来自清单」的单一事实源，PoC #2 复现边界失控 |

## 影响

- `OntologyPublishValidator` 增加物理名正则校验（M1/T2.4 交付）；
- 现有 demo 清单物理名（`public.fact_order` 等）已符合规范，无需迁移；
- M2 编译器（跨表 Join）直接沿用本规范，无需再决策。

## 回退方案

规范只收紧不放宽；若发布校验发现存量资产违规，修正资产重发布（清单不可变，出新版本）。
