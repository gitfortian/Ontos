## 背景

### 产品定位表态

负责人 2026-11-12 明确：不要求当前交付页面化建模，但「作为一个完整的产品，功能需要不断增强」，完整产品同时包含资产运营侧（建模）与业务用户侧（问数），先行收敛角色模型。

### 现状核查（2026-11-12，代码级）

1. **载体**：本体 / 指标语义 / 规则 / 场景 / Skill / VQR 全部定义于 `ontos-assets/first-release*.json`（v1–v19，纯 JSON）；全仓无 YAML 业务配置，YAML 为 M1 规格历史措辞，偏差已在 `scripts/publish.mjs` 头注与 M1 规格 §8 登记（YAML 表述待 M8 CI 平台接入时评估）。
2. **加载**：运行时权威是 System DB `published_snapshot.payload`（JSONB，DB 触发器禁止 UPDATE/DELETE）；`scripts/publish.mjs` 走 `POST /api/v1/ontology/publish`（dryRun 预检 → 确认发布）+ `POST /api/v1/ontology/manifests/{id}/activate`；启动时 `ManifestServiceImpl`（ApplicationRunner）从 DB 取最新并校验 contentHash / 结构 / 本体图，载入进程内 `active`。**系统运行时不直接读取资产文件**。
3. **页面**：`app/ontology` 四页（manifests / assets / diff / records）全部 GET 只读；ontology 模块仅 `publish` / `activate` 两个清单级写接口，**无单资产 CRUD、无草稿-审批 API、页面无编辑入口**。
4. **骨架**：`V3` / `V15` 已建 `rule` / `copy_template` / `scenario_definition` / `skill_definition` / `vqr_definition` 草稿表（draft → reviewing → published → retired），`*LifecycleService` 状态机完整，但 `ontos-module-catalog` 无 Controller、未被生产代码引用、运行时明确不读草稿。
5. **身份**：无用户表 / 角色表；身份仅靠网关注入 `X-Ontos-Tenant` / `X-Ontos-User`；发布审计 `published_by` 为发布脚本写死的 `publisher`。

### 口径张力

技术选型 v1.1 §4.2「管理界面只提交变更单，不直写运行时表」、M1 规格 R9「不造编辑器」、M8 规格 v1.1 §1 把「可视化配置器、管理面功能增强」列为非目标——三处均为**阶段范围声明**；负责人本次表态确认其不构成对后续版本的能力否决。本 ADR 即为后续演进提供决策载体，无需修改任何冻结文档。

## 决策

### D1 · 四角色定义（平台四权分立）

| 角色 | 主职责 | 关键边界 |
|---|---|---|
| 超级管理员（平台级） | 用户 / 角色 / 租户管理、审计合规 | 只管系统，不碰业务资产：不建模、不审批、不发布 |
| 本体工程师 | 本体建模、语义资产、场景 / Skill / VQR 草稿与提交；验证视图（DSL / 执行回放） | 不能审批、不能激活 |
| 业务专家 | 审批资产变更、发布与激活、口径裁决 | 只批不编；提交人 ≠ 审批人 |
| 用户 | 问数、澄清、问数流程内审批确认、提交口径发布申请 | 不可见物理表 / 列名与治理页 |

M8 规格中的「开发者视图」（事件日志 / DSL / 执行计划回放 / 候选域状态）并入本体工程师的「验证视图」，不设第五角色。

### D2 · 资产变更审批发布流程（两步激活）

提交（本体工程师）→ 预检（系统自动执行现有 dryRun 校验链）→ 审批（业务专家；**通过时系统自动以专家身份执行发布**，写入不可变清单；发布失败自动打回）→ **激活（业务专家显式动作，可一键回滚上一版）**。

即「审批通过 ≠ 自动上线」：批了未上线、上线要回滚是两个可分别处置的状态，延续现行发布 / 激活分离语义。草稿状态机沿用 catalog 既有 `draft → reviewing → published → retired`，`active` 语义由清单侧承载。

### D3 · 超级管理员为平台级

用户 / 角色 / 租户数据为**平台库**（跨租户）：所有租户账号由平台运营方统一分配，租户内不自助管理（平台代运营模式）。存储分离原则：**用户归属租户、角色归属平台**，自第一天分离存储；未来如需租户自助管理，增加「租户管理员」角色（由平台超管授权），不需迁移数据。

### D4 · 起步载体口径与不变基线

资产编辑页面化按「**页面即编辑器**」起步：草稿在系统内编辑与流转，定稿后导出为 `ontos-assets/*.json` 经既有发布链入库，Git 仍是唯一可发布真源。以下基线任何阶段不得突破：

1. Git / 资产文件为唯一可发布真源；
2. 管理界面不直写运行时表，草稿与 `published_snapshot` 严格隔离，运行时只读已发布快照；
3. 发布必经 dryRun 预检 → 不可变清单 → 显式激活，不开第二个写入口；
4. fail-closed、contentHash 校验、身份仅来自认证上下文、审计写入失败即整单失败，均不降级。

「草稿表升格为真源（Git 降为发布产物归档）」登记为远期选项，变更须另发 ADR。

### D5 · 角色落地首个跨角色功能候选

v1.4 §11.5「用户口径发布申请」链路（用户在对话中发现口径问题 → 提申请 → 本体工程师修改 → 业务专家审批 → 发布激活）作为四角色落地后的**第一个跨角色闭环候选**（R3 已标「无实现无载体」），优先级高于独立可视化建模器。

### D6 · 辅助归属

失败看板分诊（问数质量，大头为口径 / 语义问题）归本体工程师；审计日志（合规性质）归超级管理员；如后续需独立合规审查，增设只读审计位，不急于扩展第五角色。

## 备选方案

| 备选 | 为何未选 |
|---|---|
| 三角色（管理员兼任建模与审批） | 职责不分离，「自审」使 M1 设计的审核工作台空转 |
| 租户级超级管理员 | 负责人拍板平台代运营；已预留租户管理员扩展点（D3） |
| 审批通过即自动激活 | 与现行发布 / 激活分离语义冲突，丢失回滚窗口（负责人拍板两步） |
| 草稿表即唯一真源（Git 降级为归档） | 需重写 SSOT 与发布校验、动 M1 冻结口径；登记为远期选项（D4） |
| 立即将可视化配置器并入 M8 | 负责人明确不要求当前交付；M8 已冻结且编码未放行，扩围违反冻结纪律 |
