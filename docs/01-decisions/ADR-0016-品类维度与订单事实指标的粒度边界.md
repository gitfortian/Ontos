## 背景

首发本体按 v1.4 §3.1 定义 `Order 1 --- N OrderItem`（`ontology.Order.containsItem`，归一化基数 1:N）。任何「按商品品类分组的订单事实指标」（GMV / 订单数 / 客单价 / 客户数）都必须经 `orders → order_item → product` 的连接，一行订单会被拆成多行，从而放大金额与计数。

关系规划器对此**正确地** fail-closed：命中粒度扩散即返回 `1002000014`（`PATH_GRAIN_EXPANSION`），不做静默去重、不做近似。但首发清单同时发布了 `dim.product_category`，形成「维度存在、却无法与任何订单指标同用」的落差。D-3 复审实测：v1 test 集有 15 道此类题目全部不可编译，另有 19 道多轮/复合题隐含同一假设。

## 决策

1. **首发不提供「品类维度 × 订单事实指标」查询**。`dim.product_category` 保留在清单中（LOOKUP 投影、未来订单项级分析仍需要），但不得作为 QUERY / YOY_MOM / ATTRIBUTION / FUNNEL / RETENTION 的分组或过滤维度与订单事实指标组合使用。
2. **运行时保持 fail-closed**：`1002000014` 原样返回，不引入隐式去重、不按 `order_item` 摊分金额、不近似降级。拒绝优于「看起来成功、数字全错」。
3. **能力宣示同步收窄**：文档、Scenario 入口、Skill 描述不得宣称支持品类销售分析；M6 的 Scenario/Skill 资产不得把「品类 × 订单指标」绑为可使用能力。
4. **评测口径**：test 集保留 **2 题 `skip` + 2 题拒绝判据**作为缺口哨兵（E-5），有效分母 239；skip 不进主指标分母，拒绝判据验证 fail-closed 行为本身。
5. **M7 再定实现口径**：二选一——① 新增订单项级指标（如按 `order_item` 计销量/金额，明确「订单项口径」）；② 定义订单级去重语义（按订单去重后再分组，需证明口径可解释）。决策前不得改清单结构、不得放宽规划器。

## 后果

- **正面**：避免静默重复计数；主指标分母不含不可实现的能力；缺口有哨兵题与 ADR 双留痕。
- **负面**：首发无法回答「各品类卖了多少」这类常见问题；需在对外能力说明与拒答文案中明确边界（拒答文案归 M6/W5 文案模板）。
- **不受影响**：LOOKUP 按 `product_id` 查品类属性、跨域拒绝路径、订单级（不分组品类）的所有指标。
- **复核**：M7 若决定实现，需新发 ADR 并同步清单版本、test 集（哨兵转正例）、Scenario/Skill 能力声明；不得只改代码不改口径。
