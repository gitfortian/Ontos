## 背景

[ADR-0014](ADR-0014-并行义务纪律与M7同步建设偏离.md) 决策 2 把 `OBL-M7` 的触发阶段定为 **M4**，其语义是「M4 启动前补最小评测框架三件，M4 收口时逐项验收」。当时的约束背景是 M7 全量未启动，需要一个最早的强制检查点把评测框架逼出来。

现状（2026-11-09）：

1. **最小框架三件已交付并真实复跑**：[正式评测集 v1](../06-verification/evaluation/正式评测集-v1.md)（收编 11 个存量子集、四集合归属、版本哈希）、[评测统计口径 v1](../06-verification/evaluation/评测统计口径-v1.md)（§13.4 主指标 + Wilson 95%）、`smoke-runner.mjs` + 冒烟集/gold v2；[零号冒烟-评测证据-v1.json](../06-verification/evaluation/零号冒烟-评测证据-v1.json) 记录了本地 PG18 真实复跑的 **14 pass / 0 fail / 6 skip / 0 error**，gold / 题目文档 / `contentHash` 四方哈希复算全部通过。
2. [M7 最小框架验收记录 v1](../06-verification/checklists/M7-最小框架验收记录-v1.md) 已按 [M4 规格 v1.1 §6 E6](../03-plans/stages/M4/M4-身份权限与安全治理-实施规格-v1.md) 的三条判据（文件在位 / 证据可复算 / 评测集哈希与本阶段资产一致）逐项核对，结论「有条件通过」。
3. **但 M7 全量交付物仍未启动**：`test` 集 0 题（§13.2 建议 ≥200 题）、消融、失败看板、追踪、性能与安全压测全部空白；6 条 skip 依赖 M5/M6 能力。
4. **触发阶段与剩余工作已不匹配**：`check-parallel-obligations.mjs` 的规则是「触发阶段一旦标已通过而义务仍 `deferred` 即 `FAIL`」。M4 一经收口，这条规则会迫使把 OBL-M7 置 `done`——但那样等于把「最小框架」当成「M7 全阶段完成」，直接抹平 §13.5 / §19 的验收要求；而静默改台账又违反 ADR-0014 的回退方案。

## 决策

1. **最小框架三件按 [验收记录 v1](../06-verification/checklists/M7-最小框架验收记录-v1.md) 有条件通过**：四条欠账（test 集 0 题、分层字段缺口、全量交付物未启动、14 例小样本）如实带入 M7 收敛；**不得**把 14/0/6 或「成功率 100%」当作 M7 正式评测结论。
2. **`OBL-M7` 触发阶段由 M4 重定为 M6**：M4 触发点对应的是「最小框架」，该目标已验收；剩余全量交付物按 roadmap「M6 后收敛」，触发阶段应与剩余工作对齐。`status` **维持 `deferred`**，不改成 `done`。
3. **台账证据改为版本化引用**：用 [零号冒烟-评测证据-v1.json](../06-verification/evaluation/零号冒烟-评测证据-v1.json) 替换会被 runner 覆盖的 `-latest` 软名，并补入 [验收记录 v1](../06-verification/checklists/M7-最小框架验收记录-v1.md) 与本 ADR；`minimalFrameworkDone` 升级为带证据的验收结论。
4. **M4 收口直接引用验收记录**：E6 的 OBL-M7 核对项不再重复执行评测；但若生效清单、题目/gold 集或 runner 版本发生变更，必须重跑并给证据升版本，原记录失效。
5. **roadmap 状态同步**：M4 由「待启动」改为「进行中」（规格 v1.1 已冻结、编码待实施计划审核），M7 由「待启动」改为「进行中（最小框架已验收、全量交付物 M6 后收敛）」；**依赖列的硬约束文本一字不改**。
6. **这不构成放宽**：`check-parallel-obligations.mjs` 六项防线（硬约束文本、义务集合、证据存在、触发未过期、进度点名、阶段状态一致）全部不变；M6 一经通过而 OBL-M7 仍 `deferred`，基线自检仍判 `FAIL`。

## 依据

- ADR-0014 决策 2 明确「M6 后按原口径收敛全部交付物」，回退方案要求「必须新发 ADR 重新定触发阶段并说明原因，禁止直接把台账 `status` 改成 `done`、删除义务条目、删改 roadmap 硬约束文本或临时放宽检查脚本」。本次即按该条款执行。
- [M4 实施规格 v1.1 §6 E6](../03-plans/stages/M4/M4-身份权限与安全治理-实施规格-v1.md)：「OBL-M7 核对：最小框架三件已于 M4 启动前交付，M4 验收核对文件在位、证据可复算、评测集哈希与本阶段资产一致；其余 M7 交付物在 M7 验收核对」——E6 只要求核对最小框架，其余明确留给 M7 验收，与本次重定一致。
- [v1.4 §13.5](../02-solutions/architecture/智能问数系统-完整可落地方案-v1.4.md) 评测通过条件、§19「评测可信」「工程可用性」：均要求正式测试集冻结、分层统计与置信区间、P95/成本/并发 SLO、失败样本进入回归集，最小框架不满足也不宣称满足。
- `docs/README.md` §5「计划重排不改旧计划结论」、§7.8「并行义务同步」；`AGENTS.md` §6.4 阶段收口必查。

## 备选方案

| 备选 | 为何未选 |
|---|---|
| 保持触发阶段 M4，M4 收口时把 OBL-M7 直接置 `done` | 把最小框架当全量交付，test 集 0 题、无消融/看板/追踪/压测却宣告 M7 完成，与 §13.5 / §19 冲突 |
| 保持触发阶段 M4，M4 收口前静默改台账 `triggerStage` 或删条目 | 违反 ADR-0014 回退方案「必须新发 ADR 并说明」，正是本纪律要防的静默操作 |
| 把 M7 全量交付物提前到 M4 完成 | 依赖 M5 会话/编排与 M6 Scenario 能力集、以及部署环境（多副本、压测、失败样本），当前无输入，重演「最后补」但更早失败 |
| 把 roadmap M7 改成「M6 后启动」以消除触发冲突 | 事后追认漏做、降级硬约束，ADR-0014 已明确否决 |

## 影响

- 基线自检仍为 5 项，检查脚本不改、判据不放宽；`OBL-M4` 触发 M5 不变；M0–M3 已冻结验收判定不变。
- M4 收口的 E6 已有可复算证据，不再需要临时跑评测；M4 状态栏与真实进度对齐后，`stageStates.M4 = active`（仍非 `passed`）。
- M7 全量交付物的收敛时点保持 roadmap 原口径（M6 后），`OBL-M7` 在 M6 通过前必须闭环或按回退方案再发 ADR。
- [验收记录 v1](../06-verification/checklists/M7-最小框架验收记录-v1.md) 与 [版本化证据](../06-verification/evaluation/零号冒烟-评测证据-v1.json) 成为 M4 E6 与 M7 收敛的共同上游证据，二者升版需同步全仓引用。

## 回退方案

若 M6 收口时 M7 全量交付物仍未收敛，**必须新发 ADR 再次重定触发阶段并说明原因**，同步台账与进度快照；禁止直接改 `status=done`、删除义务、删改 roadmap 硬约束文本、临时放宽检查脚本，或把 dev/validation 结果当作 test 集结论。

## 后续动作

1. M4 期间（依赖域策略 / 脱敏 / 部署环境）：对抗防线专项 5 类用例（注入 / 跨轮差分 / 跨域组合 / 能力边界 / discovery，违规 0）、追踪复用 AgentScope OTel / Studio + Actuator 并回填 PoC #9。

3. 每个阶段收口按 `AGENTS.md` §6.4 在进度快照逐项点名 OBL-M4 / OBL-M7，并同步台账状态与证据。
