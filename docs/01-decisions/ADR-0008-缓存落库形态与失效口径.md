# ADR-0008 · 缓存落库形态与失效口径

> **状态**：已冻结
> **版本**：v1
> **类型**：决策
> **负责人**：项目负责人（2026-11-08 确认冻结）
> **最后更新**：2026-11-08
> **适用范围**：查询结果缓存的键设计、存储与失效；M2 起的编译器执行链路
> **上游依据**：[技术选型 v1.1 §11 第 6 项（本 ADR 即其冻结）](../02-solutions/architecture/智能问数系统技术选型方案-v1.1.md)、[技术选型 v1.1 §4.9（缓存键清单，SSOT）](../02-solutions/architecture/智能问数系统技术选型方案-v1.1.md)
> **修订记录**：2026-11-07 v1 初稿（M1/T1.3）；2026-11-08 v1 负责人确认冻结，M2 缓存读写据此实施

## 背景

技术选型 §4.9 已冻结缓存键必须包含的字段清单（规范化问题、全部版本号、`manifest_id/content_hash`、
租户与用户作用域、实体哈希、时间基准等），并禁止「仅含问题文本」的全局缓存。未定的两项由本 ADR 冻结：
**落库形态**与**失效任务的实现方式**。实现排期在 M2（编译器产出可缓存结果之后）。

## 决策

1. **存储**：System DB 表 `query_cache`（随首发清单建表，M2 使用）：
   - `cache_key CHAR(64)` 主键 = SHA-256(规范化 JSON)；
   - 键的规范化输入 = 技术选型 §4.9 字段清单的**全量序列化**（缺一项即不构成键，禁止自由扩展）；
   - `result JSONB NOT NULL`、`manifest_id`、`content_hash`、`created_at`、`last_hit_at`、`hit_count`。
2. **键含 `content_hash`**：清单发布产生新 hash → 旧键天然失配，**正确性不依赖失效任务**；
   失效任务只是空间回收。
3. **读写与失败语义**：查询命中时读缓存（未命中才编译执行）；回写**同步执行但失败降级**——
   记 WARN 不影响主响应。理由：缓存是可用性优化，不是合规边界（与审计「失败即整单失败」严格区分）。
4. **失效任务**：发布流水线在确认发布后**异步删除旧 `manifest_id` 的键**（按 `manifest_id` 列删）；
   另设每日清理 `last_hit_at` 超过 7 天的键。两类任务都是普通 SQL，不引入调度框架。
5. **禁止事项**（重申 §4.9）：禁止仅含问题文本的键；禁止跨租户共享键（租户在键内）；
   禁止把缓存用于 `out_of_capability` / 澄清 / 拒答类终态（那些必须每次走完整校验链）。
6. **可复现性优先**：缓存命中必须与重新编译执行结果一致；PoC #2 回归在关缓存与开缓存两种模式下都跑。

## 备选方案

| 备选 | 为何未选 |
|---|---|
| 进程内缓存（Caffeine 等） | 违反「权威状态全部外置」的多副本一致性策略（§1.2.1）；键含哈希的多副本正确性难验 |
| 不做缓存 | 键口径与失效规则不冻结，M2 会临场发明口径；§11 第 6 项要求阶段零/一内定版 |
| Redis | 技术选型 §6 明确不引入；PG 表 + 哈希键已满足规模 |

## 影响

- M1/T2.5 建表迁移加 `query_cache`（M2 才读写）；
- M2 编译器任务清单加「缓存读写 + 失效任务」；
- PoC #2 回归脚本增加关/开缓存两模式（M2）。

## 回退方案

缓存导致任何正确性疑问时，第一动作是**关闭缓存**（配置开关），第二动作才是修键口径；
键口径修订需发本 ADR 新版本，不得原地改。
