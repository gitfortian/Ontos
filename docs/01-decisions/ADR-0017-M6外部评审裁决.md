## 背景

外部评审对 M6 规格 v1.0 提出 2 P0 + 3 P1 + 2 P2。逐条对照规格原文与已落地代码复核：

1. **G-2「与路由结果一致」**（§3.2）：评审认为「manual 模式下路由结果 = 用户提交值，一致性校验是同义反复」。**复核：部分成立**——规格 manual 分支已要求「用户显式选择，无权限/已失效 → 拒答，不静默回退」，即授权/已发布校验是选择的**前置**；但「与路由结果一致」的裁决顺序确实没有写成显式步骤，存在被实现成「先路由后校验」的空间。
2. **depends_on 结果引用无 schema**（§3.5 / 决策 6）：**成立**。规格只有自然语言示例「取 sub-1 结果第 1 行某列」；DSL `SubIntent` 目前只有 `dependsOn: List<String>`；冻结题集 v2 的 `derive` 也是自由文本。T4.2 若无 schema 无法验收。但评审给出的「父结果必须 ≤1 行」与决策 6 的「第 1 行」措辞冲突（存在「订单数最多的品类」这类需要排序取首行的题），schema 细节需要单独冻结，不能照抄。
3. **近似降级「征得用户同意」无通道**（§3.3）：**成立**。M5 已有澄清回传校验（`pending_clarification` + candidateId ∈ 候选集，伪造拒绝），应复用而非另起。
4. **VQR「目标库实际执行成功」与 catalog 管理面矛盾**（§3.4 / §3.0）：**成立**。catalog 不得依赖 query；执行类校验必须由 catalog 之外的流水线步骤产出证据。
5. **E5 预期行为定义来源**：**部分成立**。定义来源其实存在——[M2 回填](../06-verification/evaluation/复合意图题集-v2-M2回填.json) 的 counters（pass 12 / deferred_m6 9 / unsupported_partial 4 / unsupported_dsl 3 / expected_reject_grain 2）+ 题集 category/failurePlan 字段，E5 的「9 结果依赖 + 4 单子失败 + 14 回归 + 3 预期拒绝」与之一一对应；缺的是 runner 侧的**显式映射**，不是题集改版。
6. **留存「标注」形态**（§3.1）：**表述问题，且评审指错了对象**——留存的权威契约是 analysis-mode 规格 v1.1，其定档为「未完整周期**排除**，不产出结果行」，没有要求响应标注；M6 §3.1 的「排除并标注」是摘要措辞。需要一个明确解释避免实施分歧。
7. **R-31 多域 ADR 编号**（§3.7）：**成立**，属验收核对项细化。

## 决策

1. **D1 · scenarioId 裁决顺序（T2.4 实现依据）**：`① 客户端提交 scenarioId → ② 授权 + 已发布校验（失败即 SCENARIO_MANUAL_UNAUTHORIZED）→ ③ 校验通过的值才进入路由（manual 分支的唯一来源）→ ④ 路由结果（manual/auto/inherit 任意来源）与 DSL scenarioId 比对，不一致即拒绝`。**校验前置是路由的准入条件，不是路由结果的校验项**；T5.2 探针须覆盖「未授权直传」「已发布但与路由矛盾」「伪造已发布」三类。
2. **D2 · dependsOn 结果引用 schema（T4.1 前冻结单独规格）**：W4 编码前新增《composite dependsOn 结果引用 规格 v1》，最小字段 `source_sub_intent / row_selector / column_id（资产 ID，非 SQL 别名）/ expected_type`；`row_selector` 支持两种形态——`single_row`（父结果必须 ≤1 行，否则结构化失败）与 `ordered_top`（`order_by=资产 ID + direction`，取第 N 行）；替换值再过 `DslValidator` 类型检查。复合题集如需机读引用，升 v3（只增字段）。**本 ADR 只定方向，schema 细节以 W4 前置规格为准**（与 T1.1 留存规格前置同型）。
3. **D3 · 近似降级同意通道（T3.3 依据）**：复用 M5 澄清回传校验通道；候选集合 = `{接受近似（含被近似模式标识）, 拒绝}`，回传 candidateId 不在集合即拒绝（复用 1004000002 同型校验）；审计记 `MODE_APPROXIMATED` + 原请求 mode + 被同意的候选 ID。
4. **D4 · VQR 执行类证据在 catalog 之外产生（T3.4 依据）**：入库七条件中「目标库实际执行成功 / 权限测试通过 / Golden 结果校验通过」由发布流水线的 catalog 之外步骤产生（CI/运维脚本或 server 编排），以**证据字段**（如 `execution_proof`：时间、目标库指纹、结果摘要哈希）进入 VQR 资产；catalog 只校验证据存在、时间在新鲜度窗口内、指纹与当前 Query DS 一致，**不直接连目标库**。证据缺失/过期 → 拒绝发布（fail-closed）。
5. **D5 · 留存「标注」的解释（T5.1 前落地）**：结果行按 v1.1 契约**只输出完整期**（不冒充完整数据）；「标注」落在**编译元数据与审计**——`CompiledQuery` 增加 retention 专用元数据（观察锚点、被排除的未完整期列表），进 dry-plan 展示与审计；execute 响应在 W5 前增加可选 `periodCompleteness` 字段（其他模式缺省 absent），作为 E1 的可测证据。不改 v1.1 契约。
6. **D6 · E5 预期行为映射（T4.5 依据）**：PoC #8 runner 以 M2 回填 counters 为预期来源做显式映射——`pass → M6 回归通过`；`deferred_m6 → dependsOn 全链路按 D2 执行`；`unsupported_partial → 单子失败隔离（其余子正常）`；`unsupported_dsl / expected_reject_grain → 预期拒绝（原因码匹配）`；逐题 `actual == expected`，30/30 一致；不一致的题必须附「预期行为更新」评审记录。**不改冻结题集 v2**。
7. **D7 · R-31 多域 ADR（T5.4 核对项）**：T5.4 验收时确认「多域组合判定」ADR 已进入决策台账（状态 `proposed` 即可，编号在创建时分配）；未创建即 E7 不通过。

## 后果

- **规格正文不动**：本 ADR 是 v1.0 的生效解释，与 ADR-0002 同型；M6 规格下次升版时并入正文。
- **评审定级修正**：P0-1 降为 P1（manual 分支已有授权前置，属顺序显式化）；P0-2 的「≤1 行」不照抄（与「第 1 行」措辞冲突），schema 细节留 W4 前置规格；P1-3 从「缺定义来源」修正为「缺 runner 显式映射」。
- **不新增当期代码**：D1/D3/D4/D6 分别在 T2.4/T3.3/T3.4/T4.5 落地；D5 的元数据部分可在 W5 前实施；D2 的规格在 T4.1 前冻结。各任务验收须引用本 ADR 编号。
