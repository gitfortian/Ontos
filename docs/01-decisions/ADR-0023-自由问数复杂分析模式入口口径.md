## 背景

2026-11-12 mimo 复杂度子集诊断中，FUNNEL 0/4、RETENTION 0/3、ATTRIBUTION 0/4、LOOKUP_BATCH 0/2。
失败样本多表现为模型按提示词输出 `out_of_capability`，而评测期望自由问数直接进入对应分析模式。

执行器能力已有阶段证据：M6 验收报告 v2 的 W1 覆盖 RETENTION / ATTRIBUTION 构造器、FUNNEL 顶层 filters 全局过滤与 DISCOVERY 边界声明；E1 判据为「八种分析模式构造器齐备且 SQL 真库可执行」，以 M6 Golden 23/0、Golden 集 v2 27/0、M3 6/0、M2 27/0 零回退满足。

当前失败的主要直接原因不是执行器不能编译这些模式，而是系统提示词 v3 第 47–48 行仍写着：

> `funnel` / `retention` / `attribution` / `lookup_batch` 由场景与 DSL 入口提供，自由问数不支持；遇到这类诉求输出 `out_of_capability=true`。

同时，现行候选 / 提示词通道还不能稳定承载四类模式：

- `IntentProposalContract` 已允许 `sub_intents[].analysis_mode` 使用封闭枚举 `query / lookup / lookup_batch / funnel / yoy_mom / attribution / retention / discovery`；
- 但提示词 v3 明确禁止四类模式；
- `SessionCandidateContextProvider` 的候选上下文只列资产 ID、名称与别名，不携带模式能力声明；`ManifestCandidateContextProvider` 虽会在指标行展示 `allowedModes`，但不是稳定的「模式入口声明」，也不包含 FUNNEL / RETENTION 的参数 schema 与前置资产说明；
- 因此模型既被旧提示词禁止，又缺乏四类模式的目标 JSON 形态与参数边界说明。

这与 M6 后的引擎能力、test 集 v5 / 复杂度子集的期望不一致，导致模型按旧口径 fail-closed。

## 决策

### 1. 开放自由问数入口，并补齐表达通道

**FUNNEL、RETENTION、ATTRIBUTION、LOOKUP_BATCH 允许自由问数入口。**

- 用户可以在 `/api/v1/ask/runs` 用自然语言表达这些分析诉求。
- 只要候选资产、维度、事件定义、Rule、时间窗与授权满足，编排器应进入对应 `analysis_mode`。
- 不满足时仍按现有 fail-closed / 澄清规则处理，不允许编造参数或绕过安全闸门。

开放入口必须同步解决表达通道：

1. **提示词 v4 是最小必需通道**：必须声明四类模式在自由问数可用，并给出目标 JSON 形态、必填 / 可选参数、澄清与 fail-closed 示例。
2. **不新增 `analysis_mode_candidates` 字段**：现行输出契约没有该字段；模型表达模式的位置是 `sub_intents[].analysis_mode`，不需要为模式引入新的候选 ID。
3. **不强制把 Skill 描述符塞入候选集**：Skill 是服务端路由 / 近似 / 审计事实，不因此自动成为模型候选资产。若后续需要动态声明某个模式何时可用，应增加独立的「模式能力声明」上下文，只包含模式名、语义说明、所需资产类型与参数约束摘要，不包含物理表列、SQL 或 Skill 内部路由细节。
4. **候选上下文可观测**：提示词 v4 实施与小批量复测时，必须能复核当轮模型可见的候选上下文；否则不能把失败简单归因为候选缺口。

### 2. 提示词 v3 禁令作废，失败归因必须可操作

提示词 v3 中「自由问数不支持」的表述作废。

- 后续实现不得把本决策解释为“提示词可以不改”。
- 需要提示词升版 v4 补齐四类模式的目标形态、参数边界与示例，并保持只引用候选集 ID。

失败归因不得只凭最终终态推断，按以下规则执行：

| 判定 | 条件 | 处置 |
|---|---|---|
| **提示词缺口** | 提示词仍禁止该模式，或未给出该模式表达方式；模型输出 `out_of_capability` | 修提示词；不计为模型能力失败 |
| **候选表达缺口** | 提示词已允许，但当轮候选上下文缺少所需事件定义、Rule、维度、指标或模式能力说明；模型无法引用必要 ID 或缺参数 | 修候选上下文 / 资产表达；不计为模型能力失败 |
| **模型表达缺口** | 提示词与候选上下文均支持，但模型输出非法 DSL、错模式、漏参数、错误拆解或错误澄清 | 修提示词示例，必要时评估模型能力；计入模型路径失败 |

对 2026-11-12 的 mimo 诊断：四类模式的 `out_of_capability` 属于「提示词缺口」，因为提示词 v3 明确禁止；但 LOOKUP / 多轮等失败仍需按上表重新归因，不得整体归为模型能力问题。

### 3. 执行侧安全边界不变

- 本决策只开放语义入口，不放宽任何查询执行、RLS、跨轮累计、审批、敏感查询、审计或成本闸门。
- 若候选资产不支持某个模式、事件定义缺失、Rule 未发布或时间窗缺失，仍按现有结构化错误 fail-closed。
- 提示词 v4 只描述语义能力，不得引入物理表名、列名、Join、SQL、绝对日期或候选外 ID。

### 4. 评测同时检查终端态与分析模式

test 集 v5 与 E7 复杂度子集 v1 中上述模式的期望继续有效，但必须明确两层：

- `expected.terminal=query` 只约束终端状态；
- `expected.mode=FUNNEL / RETENTION / ATTRIBUTION / LOOKUP_BATCH` 约束实际分析模式；
- runner 判据必须同时检查 `terminal` 和 `mode`，不得只因终态是 `query` 就判 PASS。

后续小批量复测用同一口径；不得把提示词旧口径造成的 `out_of_capability` 改判为通过。

## 影响

- **正面**：自由问数能力与 M6 引擎能力对齐，减少“系统可查但模型拒绝”的假阴性；复杂度子集后续能更准确区分模型问题与资产 / 提示词问题。
- **负面**：提示词升版前，这类题会继续失败；v4 会增加提示词长度与 token。实施时必须记录 v3 / v4 的 prompt 长度与小批量实测 token / 延迟；如果 prompt 长度或 token 增幅超过 20%，或单题均值超过 [SLO v1](../06-verification/evaluation/SLO与成本预算-v1.md) 的 8k 预算，应评估拆分提示词、按模式动态加载或压缩候选上下文。
- **对 C-1**：本决策不解除 [ADR-0019](ADR-0019-M7有条件通过E7评测挂账.md) 的 C-1，也不改变原 test 集 v5 全量 ×3 的正式验收口径。

## 备选方案与否决理由

| 备选 | 否决理由 |
|---|---|
| 维持“场景 / DSL 入口 only”，测试期望改为拒绝 | 与 M6 已交付的执行能力和 test 集 v5 矛盾；会把可服务诉求变成产品可用性缺口 |
| 按模式分档，仅开放 FUNNEL / ATTRIBUTION | E7 复杂度诊断中 RETENTION / LOOKUP_BATCH 的失败形态与 FUNNEL / ATTRIBUTION 同质：模型按旧提示词输出 `out_of_capability`，而评测期望进入对应模式；无当前证据支持单独禁止。若后续真实使用或安全评估发现某模式自然语言入口需求弱或风险高，可另立 ADR 收紧 |
| 立即改提示词并直接全量复测 | 违反 ADR-0022 的 API 安全模式与负责人“先小批量”要求；应先零 token 定表达再小批验证 |
