# ADR-0014 · 并行义务纪律与 M7 同步建设偏离处置

## 背景

2026-11-09 对 M7 执行了全库只读核查，随后把范围扩到 roadmap 全部并行约束，结论如下：

1. **M7 自 M1 起未同步建设**：roadmap §1 明确「自 M1 起同步建设，M6 后收敛」、并行支线写「不允许最后补」、§4.3 写「安全与评测不许后置」、R7 要求「门槛先冻结」。而 M1 / M2 / **M3 均已通过验收**，M7 状态仍是「待启动」。以 M7 名义的交付物为 0：无实施规格、无 ADR、无进度条目、无 `ontos-module-eval`、无失败看板、无消融、无追踪产品化、无压测报告。
2. **M4 同样漏项**：roadmap §1 与 §4.3 要求「M4 与 M1–M3 并行」，M1–M3 已全部通过，M4 仍「待启动」。此前核查只盯 M7，说明**并行支线整体缺少跟踪机制**，不是某一项的偶然疏忽。
3. **计划内部口径从未对齐**：[M0 实施规格 v1.0 §1](../03-plans/stages/M0/M0-工程基线与阶段零硬判据-实施规格-v1.md) 把「失败看板、追踪压测」明确划归 M7 / M8 并禁止提前实现，与 roadmap 的「自 M1 同步建设」自相矛盾，且从未发 ADR 或升版计划解释。
4. **R7 风险正在发生**：[零号冒烟集 v1](../99-archive/evaluation/零号冒烟集-v2.md) 自认「不是正式评测集，正式评估集另立文档」，该文档至今未立；题集与 gold 随 M0 / M1 / M2 / M3 能力边做边回填（v1 → Golden v2 → 27/30 可构造 → M3 Golden 增量），正是 R7 要防的「效果无法归因」。
5. **属于静默未执行，而非已批准顺延**：`docs/05-progress/2026/` 中 M7 仅出现 1 次（11-06 风险台账），11-07 / 11-08 / 11-09 三份快照、M1 / M2 / M3 验收报告与 M2 收口深度审核中「M7」零命中；13 份 ADR 无一涉及 M7 顺延；`roadmap/` 无重排升版。

客观上已积累可复用素材，但全部挂在 M0 阶段零 PoC 判据与 M1 / M2 / M3 验收编号下：Golden / 冒烟 / 复合 / 提及题集与回填脚本、E5 对抗探针 9/9、RLS 100 轮 0 越权、`traceId` + `audit_log` + 审计页 + Actuator health。这些**不计入 M7 交付物**。

## 决策

1. **roadmap 硬约束不改、不降级**：不把「自 M1 起同步建设」「不允许最后补」改成「M6 后启动」，不事后追认已完成，也不改 roadmap 正文（沿用 ADR-0002 的惯例：冻结口径的生效解释由 ADR 承载）。本次偏离以本 ADR 显式登记，并按 `docs/README.md` §5「计划重排」要求补齐进度留痕。
2. **两条并行义务全部登记为 `deferred`**，写入 [并行义务台账](../00-governance/parallel-obligations.json)：
   - `OBL-M4`：触发阶段 **M5**——roadmap 依赖 `M5 = M3 + M4`，M4 必须在 M5 启动前完成，否则 M5 不得放行。
   - `OBL-M7`：触发阶段 **M4**——M4 启动前先补最小评测框架三件（正式评测集另立文档并收编存量题集、零号冒烟 runner、分层统计与置信区间口径）；M4 收口时逐项验收；M6 后按原口径收敛全部交付物。
   - 台账状态只允许 `done` / `deferred`；`deferred` 必须写清原因、触发阶段、负责人、证据链接。
3. **建立机器强制的纪律检查**：新增 `docs/00-governance/check-parallel-obligations.mjs`，接入 `scripts/verify-baseline.mjs`。它从 roadmap 自动抽取并行义务，强制校验：硬约束文本未被删改、每条义务在台账有登记、证据文件存在且点名该阶段、触发阶段未过期、最近一次进度快照点名所有未闭环义务、阶段状态与验收报告一致。任一不满足即 `FAIL`，禁止为跑通而放宽。
4. **阶段收口强制核对**：`AGENTS.md` §6.4 规定每个阶段收口（验收报告 / 深度审核 / 进度快照）必须逐项核对全部并行义务并点名；已交付写证据链接，未交付写欠账登记并同步台账。**未登记不得宣告阶段关闭**；§6.2 深度审核把这一项列为必查。
5. **M0–M3 的判定不变**：本 ADR 不推翻任何已冻结验收报告，不重开 M1 / M2 / M3；M3 验收报告 v1「M5 放行」仍以 M4 完成为前提，与本 ADR 第 2 条一致。

## 依据

- `docs/README.md` §5「计划重排：不改旧计划结论，发新版本计划并在进度里说明重排原因」；§7.5「完成即记进度」。
- `AGENTS.md` §6.2 深度审核铁律：遗留项必须登记、未闭环不得宣告完成。
- v1.4 §13.2 正式评估集需 dev / validation / test / challenge 四集合并带版本哈希；§12.3 失败看板 5 维下钻；§19「评测可信」「工程可用性」为最终验收条款。
- [ADR-0005](../01-decisions/ADR-0005-评测门槛与PoC执行责任.md) 已冻结评测门槛（§7 建议初值一字不改），说明「门槛先冻结」的治理意图早有先例，缺的是**执行跟踪**而非规则本身。

## 备选方案

| 备选 | 为何未选 |
|---|---|
| 升版 roadmap，把 M7 改成「M6 后启动」、M4 并入主线 | 等于事后追认漏做，把纪律缺口写成计划调整；R7「效果无法归因」的风险不会因此消失 |
| 立刻全量补做 M7（评测集 + 消融 + 看板 + 追踪 + 压测） | M4 未启动、真实环境与稳定能力集尚不具备，压测与失败样本缺少输入；且会挤占主线。改为「最小框架前移到 M4 启动前」，其余按 M6 后收敛 |
| 只在进度快照里补一句「M7 待补」 | 纸面纪律，正是这次失效的原因；无机器强制，下一个阶段仍会静默漏掉 |
| 把已有 Golden / 对抗探针 / 审计 traceId 认定为 M7 已完成 | 抹平「素材」与「交付物」的边界，会让 M7 退出条件（§13.5 / §19）失去可验证性 |

## 影响

- **新增单一事实源**：[并行义务台账](../00-governance/parallel-obligations.json) 只登记跟踪状态，不重定义阶段编号、阈值或验收条款；阶段定义仍在 roadmap。
- **基线自检从 4 项变 5 项**，`verify-baseline.mjs` 与 `AGENTS.md` §7 同步；后续任何并行项漏登、证据失效、触发过期、进度未点名都会让基线变红。
- **M4 启动时新增前置**：最小评测框架三件必须在 M4 开工前落地，M4 验收报告需包含对 `OBL-M7` 的逐项核对结论。
- M0 T1.4「冒烟集脚本」欠账（`M0-验收报告-v2.md` §4 登记项）并入 `OBL-M7` 的第 2 项交付物一并关闭，不再单独悬挂。

## 回退方案

若 M4 收口时 `OBL-M7` 最小框架仍未完成，或 M5 启动前 `OBL-M4` 仍未闭环：**必须新发 ADR 重新定触发阶段并说明原因**，同步台账与进度快照；禁止直接把台账 `status` 改成 `done`、删除义务条目、删改 roadmap 硬约束文本，或临时放宽检查脚本。检查脚本对这类改动会直接判 `FAIL`。

## 后续动作

1. M4 启动前：正式评测集另立文档（收编存量题集、带版本哈希）、零号冒烟 runner、分层统计与置信区间口径；关闭 M0 T1.4 脚本欠账。
2. M4 收口：验收报告逐项核对 `OBL-M7` 最小框架；追踪与压测随部署环境回填，失败看板与消融按 M7 交付物清单推进。
3. 每个阶段收口：进度快照必须点名所有未闭环并行义务，并同步台账状态与证据。
4. M6 后：按 roadmap 原口径收敛 M7 全部交付物，走 §13.5 / §19 验收。
