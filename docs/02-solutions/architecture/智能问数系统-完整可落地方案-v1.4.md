## 1. 执行摘要

本系统采用“业务本体 + 语义资产 + 类型化查询 DSL + 确定性 SQL 编译器”的架构。本体是首发能力的核心，不是后续可选图谱，也不是仅供展示的实体目录：

1. 本体为业务概念、属性、实体类型、关系类型、关系基数、约束和数据域提供版本化定义；
2. 本体把自然语言中的业务实体和关系绑定到 Model、指标、维度、事件及物理字段映射；
3. LLM 只负责识别意图（含复合意图拆分建议）、提出概念/关系/属性候选、推荐业务 Scenario 入口、选择 Analysis Mode 和提取参数；歧义必须澄清；
4. LLM 不输出物理表名、Join 条件、SQL 表达式、自由 SQL 或绝对日期（用户显式给出除外）；DSL 只引用经过授权的本体 ID 和语义资产 ID；
5. 确定性规划器解析本体关系路径、验证约束与粒度，再由编译器生成 SQL；复合意图拆分为子查询序列，各自独立编译、独立授权、结果隔离组装；
6. 数据库原生 RLS、安全视图或受控数据集作为最终权限边界，具体实现按首发数据库确定；
7. 无法完成本体绑定、权限验证或参数补全时，系统必须澄清或拒答；能力边界外的请求必须显式说明；
8. 所有结果保存完整版本链路，包括本体路径、映射版本、会话锚点、查询上下文与子查询关系，能够复现“谁在什么版本下、基于什么上下文生成了什么 DSL、SQL 和结果”。

本体推理限定为显式、有限跳数的关系遍历、类型/基数校验和已声明约束，不引入通用 OWL 推理平台，也不允许隐式推导业务规则。判定类（是/否）查询必须引用已审核规则注册表，不由 LLM 现场定义口径。系统按用户提问谱系（简单/复杂、懂业务/不懂业务、单轮/多轮、正常/对抗）设计兜底路径。本方案不承诺外部宣传数字；系统效果以自有、冻结、可复现的评测集为准。

## 2. 建设目标与非目标

### 2.1 核心概念边界

全文严格区分以下一级概念：

| 概念 | 性质 | 是否可自定义 | 职责 |
|---|---|---|---|
| **Analysis Mode（分析模式）** | 编译器内置、封闭枚举 | 否；扩展需代码变更、测试和版本发布 | 选择确定性查询构造器，例如 `query`、`lookup`、`funnel`、`yoy_mom`、`attribution`、`retention`、`discovery` |
| **Scenario（业务场景）** | 管理员/运营可配置、审核发布、版本化资产 | 是；仅可使用声明式字段 | 业务语义上下文、Ontology/Semantic scope 收窄、入口推荐、默认口径和 Skill/VQR 路由 |
| **Skill（能力单元）** | 注册制、审核发布、版本化能力 | 可新增注册，但不能内联自由逻辑 | 对特定 Analysis Mode 的参数 Schema、确定性构造器或受控工具动作的封装 |
| **Attribute（本体属性）** | 本体资产，版本化 | 由本体 Owner 维护 | 单实体属性直查的投影对象；含敏感级别、存在性敏感、展示提示 |
| **Rule（判定规则）** | 注册制、审核发布、版本化 | 由规则 Owner 维护，不可内联 | 布尔判定型指标（`boolean_rule`）引用的已审核规则；不可由 LLM 现场定义 |
| **Session Context（会话上下文）** | 服务端维护、用户+租户+会话绑定 | 不可由客户端自由写入 | 指代锚点、查询上下文（指标/维度/过滤/时间窗/Scenario）、敏感累计计数 |

关系：一个 Scenario 可允许多个 Analysis Mode，并引用绑定这些模式的已发布 Skill；一个 Skill 只能绑定受支持的 Analysis Mode 和已发布参数 Schema。Analysis Mode 决定引擎走哪类确定性构造器；Scenario 不能增加/改写模式语义；Skill 不能携带自由 SQL、脚本或绕开编译器的逻辑；Attribute 由本体定义并被 DSL 以 ID 引用；Rule 只能被 `boolean_rule` 型 Metric 引用；Session Context 由服务端维护，跨会话清空。

若用户没有进入 Scenario，系统按已授权的全域语义资产执行自由问数，但仍必须经过本体规划、权限校验和同一 DSL/编译器。Scenario 入口只收窄候选空间，不构成权限授权，也不替代用户授权。

### 2.2 建设目标

- 统一指标、维度、事件、业务对象、属性和口径变体的定义；
- 对同一份已校验 DSL、固定版本资产和编译器生成可复现的查询结构；自然语言解析若存在歧义必须澄清，不承诺 LLM 对相同文本逐次输出完全相同；
- 支持自由问数与可版本化 Scenario 两种入口；通过封闭 Analysis Mode 和注册制 Skill 支持普通取数、单实体属性直查/批量直查、布尔判定、漏斗、同环比、简单归因、留存和引导式发现；
- 支持复合意图拆分：一次提问含多个子问题时，拆为子查询序列，各自独立编译、独立授权、结果隔离组装；
- 在查询生成前完成语义、结构、权限、存在性、标签敏感和资源约束校验；
- 支持 VQR 复用高频稳定问题；
- 支持跨用户、跨租户、跨数据域的权限隔离，保护字段存在性、派生标签，并检测跨轮差分与跨域组合风险；
- 支持多轮会话中的指代消解、查询上下文延续与增量修改，且锚点与上下文可审计、跨会话不串号；
- 支持完全不懂业务的用户：意图不明时走引导式发现，能力边界外显式说明；
- 对每次问数形成可审计、可回放、可定位的执行记录；
- 通过正式评测集持续改进，而不是依赖主观体验。

### 2.3 非目标

第一阶段不做：

- 让 LLM 直接生成任意 SQL；
- 自动修改语义资产或自动发布指标口径；
- 让 LLM 现场定义判定口径（如"高价值 = 5000 元"）；判定必须引用已审核 Rule；
- 依赖通用本体推理替代业务定义；
- 自动把用户点赞结果直接发布为 VQR；
- 在没有明确权限策略的情况下允许跨域查询；
- 用 20 道题宣称生产级准确率；
- 用 Ossie draft 查询层定义本系统的内部 DSL；
- 在 Scenario 内联自由 SQL、脚本或未注册逻辑；Scenario 只能引用已发布 Skill；
- 允许用户创建/修改 Analysis Mode 或直接扩展编译器行为；
- 首发支持多语言/方言/拼音输入以外的自然语言；**首发语言范围显式限定为：中文（含常见英文术语混说）**；多语言、方言、拼音全量支持列为后续阶段；同义词资产可登记 `pinyin_aliases` 作为补充召回，但不承诺全量拼音识别；
- 支持预测、自由 SQL 生成、用户画像生成、外部数据抓取等能力边界外请求；此类请求必须走 7.7 `OUT_OF_CAPABILITY` 拒答并说明边界。

## 3. 设计原则

### 原则一：LLM 只做语义匹配和两级路由建议

LLM 输出受约束的 `Intent Proposal`（可含复合意图拆分建议），可推荐 Scenario 入口并识别 Analysis Mode 候选；Scenario 是否生效由确定性入口策略确认。物理表、Join、构造器选择、聚合表达式、函数、规则求值、时间解析和权限条件均由确定性服务解析。

### 原则二：Scenario 收窄上下文，Skill 承载注册能力，Rule 承载判定口径

语义层定义本体、指标、维度、事件、属性和合法词汇。Scenario 负责业务上下文、入口提示、scope 收窄、默认口径和 Skill/VQR 路由；复杂分析逻辑由注册审核的 Skill 承担；判定口径由注册审核的 Rule 承担。新增 Scenario 不要求改编译器；新增 Analysis Mode 或底层构造器需要代码评审、测试和版本发布。

### 原则三：DSL 是受约束的中间表示

DSL 只允许引用 Scenario/Skill/Analysis Mode/Attribute/Rule ID、语义资产 ID、合法枚举值、受控展示转换和已注册的 `analysis_params`。未知字段、额外字段、自由 SQL、自由关系表达式、自由阈值和 LLM 直接输出的绝对日期（用户显式给出除外）均拒绝。

### 原则四：拒答、澄清、引导、复用都是正常终态

- 命中已验证查询：直接复用；
- 信息缺失、候选冲突、口径未定义/并列：澄清（澄清必须含四要素，见 7.7）；
- 意图不明：引导式发现（展示授权 scope 内可问的合法入口）；
- 能力边界外：显式拒答并说明边界；
- 无合法资产、无权限或无法满足资源约束：拒答；
- 不允许通过猜测完成查询；不允许通过猜测定义口径；不允许静默降级或静默拆分。

### 原则五：安全边界不能只在 LLM 层

应用层校验、查询编译器、缓存隔离、数据库 RLS 和审计系统必须共同构成安全边界。字段存在性、派生标签、分群结果、跨轮差分、跨域组合和提示注入同样属于安全边界。任何一层遗漏都不能导致越权成功。

### 原则六：效果以自有评测为准

外部资料不用于承诺准确率、延迟或吞吐。所有量化结论来自冻结的自有评测集和可复现的运行环境。

### 原则七：按用户提问谱系设计兜底

系统必须同时覆盖：简单/复杂、懂业务/不懂业务、单轮/多轮、正常/对抗、单子问题/复合意图。每个谱系档必须有明确的路径、终态、原因码和评测分层；不允许某档用户"无路可走"。

## 4. 总体架构

```text
用户问题 / 用户选定入口 / 会话上下文 / 冷启动
   |
   v
身份认证与请求上下文
(含 session_id、turn_index、resolved_entities、session_query_context、session_scenario_state)
   |
   v
用户授权过滤 + 数据域路由 + 跨域组合检查
   |
   v
Scenario Entry Router
(手动指定 / entry_hints 推荐 / 会话沿用 / 冷启动地图 / 自由问数回退)
   |
   v
确认 Scenario 并裁剪 Scope
(选中：应用 Ontology/Semantic Scope；未选中：使用授权全域)
   |
   v
LLM Intent Proposal（可含 sub_intents 拆分建议）
   |
   v
Proposal Schema 校验 + 来源完整性校验（候选集 context_hash）
   |
   v
意图不明？ --是--> 引导式发现（needs_discovery）--> 受限候选入口清单
   | 否
   v
Scope 内实体消歧、指代消解、查询上下文增量合并、时间解析
   |
   v
Analysis Mode 识别 + 已发布 Skill 路由（含近似降级声明）
   |
   v
复合意图拆分？ --是--> 子查询序列（各自独立 DSL/编译/授权）
   | 否
   v
服务端组装最终 Query DSL（单查询或子查询序列）
   |
   v
DSL Schema + Scenario Scope + 跨域组合 + 累计敏感校验
   |
   v
语义绑定、规则求值与权限编译（字段级/行级/存在性/标签）
   |
   v
确定性查询编译器
  |-- 指标展开（含 boolean_rule 规则求值）
  |-- 属性投影与受控展示转换
  |-- Join 路径解析
  |-- Analysis Mode/Skill 构造器
  |-- RLS / 安全视图注入
  |-- 成本与资源检查
   |
   v
SQL 方言生成（每个子查询独立生成）
   |
   +--> dry-plan：展开 SQL、执行计划、审计附件
   +--> dry-run：真实数据库校验，不返回业务行
   |
   v
正式执行（子查询结果隔离组装，不共享中间结果集）
   |
   v
结果合理性与数据质量检查（含存在性保护、标签敏感、批量差异保护）
   |
   v
脱敏、结果裁剪、审计记录（含 context_delta、batch_size、sub_intent_id）
   |
   v
用户结果 / 澄清 / 引导 / 拒答
```

架构节点与组件对应：`Scenario Entry Router`、`确认 Scenario 并裁剪 Scope`、冷启动地图由 Scenario 服务承担；`Analysis Mode 识别 + 已发布 Skill 路由` 由 Skill 注册中心 + LLM 编排器 + DSL 校验器共同承担；`Scope 内实体消歧、指代消解、查询上下文增量合并、时间解析` 由本体服务 + 会话状态服务 + 时间解析器承担；`规则求值` 由 Rule 注册中心 + 编译器承担；`跨域组合检查`、`累计敏感校验` 由身份与策略服务 + 会话状态服务承担。

### 4.1 首发数据库边界

DataAgent 文档列出 MySQL、PostgreSQL、Oracle 查询数据源，但本方案不假定这些数据库具有相同的原生 RLS 能力。阶段零必须选定一个首发数据库和部署形态，验证其可实施的最终隔离方式（原生 RLS、安全视图、独立只读账号/Schema 或受控代理）。在该决策完成前，不得宣称已具备生产行级安全，也不得对真实敏感数据开放问数。其他数据库在各自完成相同的安全一致性测试前，只能处于受控开发/沙箱环境。

### 4.2 组件边界

| 组件 | 负责 | 不负责 |
|---|---|---|
| 身份与策略服务 | 用户、租户、角色、数据域、RLS 策略、域组合策略 | 生成 SQL |
| 会话状态服务 | `session_id`、`resolved_entities`、`session_query_context`、`session_scenario_state`、`turn_index`、敏感累计计数；锚点绑定 user+tenant+session | 生成 SQL；跨会话沿用 |
| 本体服务 | 管理概念、属性、关系、约束、别名、映射和本体版本；解析类型合法的有限关系路径 | 隐式推断业务规则、绕过数据域授权 |
| 语义资产服务 | 指标、口径变体、维度、事件、枚举、Model 及版本 | 动态猜测业务口径 |
| 规则注册中心 | Rule 注册、审核、版本、失效；`boolean_rule` 求值接口 | 接收内联表达式/自由阈值 |
| 时间解析器 | 版本化相对时间表达式解析（自然语言→绝对区间），记录原始表达 | 生成 SQL；猜测用户未给出的日期 |
| 文案模板服务 | 原因码→用户文案模板、澄清模板、能力边界模板；版本化、多语言键 | 生成业务逻辑 |
| Scenario 服务 | Scenario 入口推荐/确认/会话沿用/冷启动地图、版本、scope 裁剪、默认口径和能力绑定 | 授予用户权限、执行自由逻辑 |
| Skill 注册中心 | Skill 注册、审核、参数 Schema 绑定、`required_capabilities`/`allowed_scenario_ids` 维护、版本、失效和路由、`approximation_of` 近似关系 | 接收内联脚本/自由 SQL、绕过编译器 |
| 检索服务 | 在用户授权且 Scenario scope 裁剪后的本体子图内召回候选概念、资产、属性、Skill 和 VQR；受限模糊候选仅作澄清候选 | 最终决定可执行查询 |
| LLM 编排器 | 推荐 Scenario 候选、提出概念/关系/属性候选、Analysis Mode 候选、复合意图拆分建议和参数 | 输出物理 SQL、自行指定关系路径/Skill 实现/判定口径/绝对日期 |
| DSL 校验器 | Scenario scope、Skill 绑定、`required_capabilities`、`allowed_scenario_ids`、`metric.allowed_modes`、本体 ID、资产 ID、属性 ID、类型、关系路径、基数、模式、参数、跨域组合和累计敏感约束 | 执行查询 |
| 确定性编译器 | 依据已校验本体映射展开 Model、指标、规则、Join、Analysis Mode 构造器、展示转换、权限和成本 | 修改语义/本体/Scenario/Skill/Rule 定义 |
| 数据库执行器 | dry-run、正式执行、超时和资源控制 | 接收任意用户 SQL |
| VQR 服务 | 模板审核、版本、失效和复用 | 绕过权限编译 |
| 审计服务 | 记录完整链路、多轮上下文、子查询关系、脱敏、回放索引 | 修改原始结果 |

## 5. 本体与语义资产层

本体与语义资产统一纳入 Git 版本管理，并可由现有管理界面维护、审核后发布；生产发布生成不可变的兼容版本组合：`ontology_version`、`semantic_version`、`policy_version`、`rule_version`、`time_parser_version`、`copy_template_version` 和物理 Model 映射版本。草稿不得被查询运行时读取；运行时请求固定到一个已发布清单，禁止混用未兼容版本。

### 5.1 资产类型

1. **Ontology Class**：业务概念类型，如 Customer、Order、Product；
2. **Ontology Property**：概念的标识属性、业务属性、度量属性和敏感级别；可被 `lookup` 投影；含存在性敏感与展示提示；
3. **Ontology Relation**：有方向、有类型、基数、语义和约束的业务关系；
4. **Ontology Constraint**：关系路径、属性值、有效时间、状态等可执行约束；
5. **Ontology Mapping**：概念/属性/关系到 Model、逻辑表列、Metric、Dimension、Event 的版本化映射；
6. **Model**：逻辑数据集、事实粒度和物理关系实现；
7. **Metric**：原子指标、衍生指标、布尔判定指标，可含口径变体；
8. **Dimension**：可筛选、分组、排序的维度；
9. **Event**：触发条件、参与者概念、时间属性和可用维度；
10. **Enum**：字段合法值、显示名、业务解释和状态；
11. **Policy**：数据域、域组合、概念/属性/关系可见性、字段敏感等级、RLS、脱敏、存在性保护和跨轮累计阈值；
12. **Rule**：注册审核、版本化的布尔判定规则，供 `boolean_rule` 型 Metric 引用；
13. **Scenario**：经过审核、版本化的业务上下文、scope、默认口径和 Skill/VQR 路由声明；
14. **Skill**：注册审核、版本化的能力单元，绑定 Analysis Mode 和受限参数 Schema，可声明近似关系；
15. **VQR**：经过审核的参数化查询模板；
16. **Synonym**：概念、关系、指标、维度、属性和事件的同义词、缩写、别名、口语别名、拼音别名（补充召回）。
17. **Time Expression Pattern**：版本化相对时间表达模式（"上个月""上个季度最后两周"），供时间解析器使用；
18. **Copy Template**：原因码→用户文案模板、澄清模板、能力边界模板，版本化、多语言键。

本体是语义资产之上的业务概念和关系模型，不替代指标口径、事件定义或物理 Model；通过显式映射将它们连接起来。

### 5.2 Model 规范

Model 必须声明：

- 事实表或主逻辑表；
- 事实粒度，例如“一行一个订单”；
- 主键、外键和关系基数；
- 允许的 Join Path；
- 每条 Join 的去重、空值和多对多策略；
- 支持的 SQL 方言；
- 数据域和权限策略；
- 刷新时间和数据新鲜度。

LLM 不接触物理 Join 条件，只能引用 `model_id` 和 `join_path_id`。

### 5.3 本体模型规范

每个本体类必须声明：

- 全局唯一 `class_id`、业务名称、定义、Owner 和版本；
- 主标识属性及其唯一性范围；
- 属性列表、值类型、单位、时区、枚举、敏感等级（含 `PII`、`label` 等）；
- 同义词、缩写、歧义词及适用数据域；
- 到逻辑实体、表/列、指标、维度和事件的映射；
- 可用动作、可参与的 Analysis Mode，以及允许被哪些 Skill 引用；
- 生效时间、废弃版本及兼容性。

每种本体属性必须声明（供 `lookup` 使用）：

- 唯一 `property_id`、值类型、单位、时区、枚举；
- 是否可被 `lookup` 投影、是否可作为过滤条件、是否可作为标识属性；
- 敏感等级（`public` / `internal` / `PII` / `label`），以及脱敏策略引用；
- 是否存在性敏感（存在与否本身即敏感）；
- 展示提示 `display_hints`：允许的受控展示转换（如 `date_fmt`、`duration_from_now`、`enum_label`）、单位、时区；
- 到逻辑表列的映射版本。

每种本体关系必须声明：

- 唯一 `relation_id`、起点类、终点类、方向和逆向名称；
- 关系语义和基数（1:1、1:N、N:1、N:M）；
- 是否可用于查询规划、聚合、过滤或仅用于描述；
- 对应的逻辑 Join Path 或事件关联映射；
- 连接键唯一性、时间有效性、去重和空值规则；
- 数据域、敏感等级和授权策略；
- 合法路径约束、最大遍历跳数和循环关系处理；
- Golden Path 样例及负例。

首期推理仅支持：

- 经人工发布的关系边上的有限跳数路径搜索；
- 类、属性、关系类型和基数约束校验；
- 已登记的等价概念、逆关系和实体标识关联；
- 明确声明的状态/时间有效性约束。

不支持：开放世界假设、自动规则归纳、无界传递闭包、自由 SPARQL/SQL 或未声明的逻辑推导。存在多条代价相近的合法路径时必须澄清，不能由 LLM 私自选择物理关系。

#### 本体资产示例

```yaml
class_id: ontology.Customer
name: 客户
owner: crm-data
identity:
  property_id: ontology.Customer.customer_id
  uniqueness: tenant
properties:
  - property_id: ontology.Customer.region
    value_type: enum
    maps_to: dimension.customer_region
    sensitivity: internal
  - property_id: ontology.Customer.email
    value_type: string
    maps_to: column.customer_email
    sensitivity: PII
    existence_sensitive: true
    lookup_projectable: true
    filterable: true
    masked_policy: mask.email_v1
  - property_id: ontology.Customer.register_time
    value_type: timestamp
    maps_to: column.customer_register_time
    sensitivity: internal
    lookup_projectable: true
    display_hints:
      allowed_transforms: [date_fmt, duration_from_now]
      timezone: Asia/Shanghai
synonyms: [客户, 买家, 会员]
colloquial_aliases: [老铁, 客官]
pinyin_aliases: [kehu, keh]
domain_id: domain.commerce
version: 1.0.0
```

```yaml
relation_id: ontology.Customer.placesOrder
name: 下单
source_class: ontology.Customer
target_class: ontology.Order
inverse_name: 由客户下单
cardinality: one_to_many
queryable: true
mapping:
  join_path_id: join.order_customer
  valid_time: dimension.order_created_at
constraints:
  - relation: tenant_id_equal
  - deduplicate_by: ontology.Order.order_id
max_path_hops: 3
owner: commerce-data
version: 1.0.0
```

发布前 Schema 校验必须检查映射目标存在、关系基数与物理关系一致、唯一键成立、无未授权跨域边，并通过正向/反向路径样例。

### 5.4 Metric 规范（含口径变体）

每个指标必须包含：

- 唯一 ID、名称、Owner；
- 指标粒度；
- 分子、分母或聚合方式，或布尔判定规则引用；
- 时间字段和时区；
- 过滤条件；
- 空值和零分母策略；
- 去重规则；
- 支持的维度；
- 敏感等级（含 `label` 型派生标签）；
- 可用 Analysis Mode 及其允许绑定的 Skill；
- 测试样例和 Golden Query；
- 生效版本和废弃版本；
- **口径变体 `caliber_variants`**。

**口径变体规范**：

```yaml
id: metric.paid_gmv
name: 已支付GMV
caliber_variants:
  - variant_id: metric.paid_gmv.ex_refund
    alias: [去掉退款的成交额, GMV去退款版]
    condition: {field: order.refund_status, op: eq, value: NONE}
    version: 1.0.0
  - variant_id: metric.paid_gmv.promotion
    alias: [大促口径GMV]
    condition: {field: order.promotion_tag, op: eq, value: PROMO}
    version: 1.0.0
```

规则：

- 变体只能通过声明式 `condition` 表达，禁止自由表达式；变体继承主指标其余字段；
- 用户提及口径别名但未明确变体时，走 `CALIBER_AMBIGUOUS` 澄清，不得由 LLM 二选一；
- 变体 ID 进入 DSL 与审计；变体版本变更按 11.3 触发依赖失效；
- 变体的敏感等级不得低于主指标。

**布尔判定指标（`boolean_rule`）额外要求**：

```yaml
id: metric.high_value_customer
kind: metric
name: 高价值用户
grain: customer
expression:
  type: boolean_rule
  rule_id: rule.high_value_v1     # 必须引用已发布 Rule，禁止内联表达式/阈值
time_window: 12m
allowed_dimensions: []
allowed_modes: [lookup]
sensitive_level: label
version: 2026.11.01
```

规则：

- `expression.type: boolean_rule` 时，`rule_id` 必须指向已发布 Rule；禁止 `expression.rule_inline`、自由阈值、自由公式；
- `rule_id` 进入 DSL 与审计，规则版本变更按 11.3 触发依赖失效；
- 判定结果的敏感级别默认 `label`，返回前按 10.5 脱敏或审批。

衍生指标可按以下五类管理：筛选型、累积计算型、同环比计算型、混合计算型、转化计算型；布尔判定型单列一类。该分类只作为资产组织方式，不作为准确率承诺。

### 5.5 Event 规范

事件必须包含：

- 事件 ID 和业务名称；
- 触发条件；
- 参与者本体类及角色（触发者、对象、受益者等）；
- 用户标识字段；
- 事件时间字段；
- 事件去重规则；
- 可用维度；
- 时间精度和时区；
- 是否允许匿名用户；
- 可参与的 Analysis Mode；
- 到本体关系的映射及其有效时间语义。

Skill 构造器使用 Event 与本体主体、目标对象和触点关系构成分析路径，不直接拼接脱离本体定义的物理字段。

### 5.6 首发本体范围与闭环

首发必须覆盖至少一条真实业务链，而不只是空泛列出类名。建议交易域最小本体（包含 relation_id，供 6.3 示例引用）：

```text
Customer 1 --- N Order          (ontology.Customer.placesOrder)
Order    1 --- N OrderItem      (ontology.Order.containsItem)
OrderItem N --- 1 Product       (ontology.OrderItem.refersProduct)
Customer 1 --- N Event          (ontology.Customer.performsEvent)
Order    1 --- N Event          (ontology.Order.recordsEvent)
Event    N --- 1 Channel        (ontology.Event.attributedToChannel)
Order    N --- 1 Channel        (ontology.Order.attributedToChannel)
```

各关系映射到现有语义 Model 的逻辑 Join Path；Event 必须声明参与者、发生时间、事件类型和去重键。首发资产包至少包含 3 个类、5 个可查询关系、2 个事件、5 个指标（含至少 1 个口径变体）、5 个维度、1 个 PII 属性（`ontology.Customer.email`）和 1 个布尔判定指标（`metric.high_value_customer`）。其中 `performsEvent`、`attributedToChannel` 在阶段一发布元数据，阶段三启用构造器时才开放给 Analysis Mode。

本体驱动查询的完整闭环如下：

1. 从问题中提取实体提及、关系表达、属性意图、指标意图、口径变体意图、时间和过滤条件；
2. 在当前用户已授权的本体子图（且已通过 Scenario scope 裁剪，若进入场景）内解析概念候选和同义词；多轮指代优先用 `resolved_entities` 解析；
3. 若同一词指向多个概念、可能关系路径存在歧义、口径未定义/并列，向用户澄清；
4. 在已发布的 Ontology Relation 中搜索有限路径，校验类类型、方向、基数、租户边界、有效时间和最大跳数；
5. 将概念、关系、属性、指标、维度、事件、口径变体和规则绑定为 DSL ID；
6. 将本体路径映射成 Model/Join Path，编译器检查粒度和聚合安全；
7. 应用字段级、行级授权、存在性保护和标签敏感策略并编译 SQL；
8. 审计记录问题提及、概念候选、最终概念 ID、关系路径、属性投影、口径变体、规则版本、映射版本、授权裁剪、DSL、SQL 和澄清/拒答原因。

本体在此承担实体指代、业务关系路径、属性投影和查询约束四个真实职责；指标公式仍由 Metric 定义，判定口径仍由 Rule 定义，事件发生逻辑仍由 Event 定义，物理关系仍由 Model 实现。四者不能相互替代。

### 5.7 Scenario 资产规范

Scenario 仅声明业务上下文和允许调用的已发布能力，不执行逻辑。字段 Schema：

```yaml
scenario_id: scenario.channel_campaign_review
name: 渠道投放复盘
# entry_mode 取值：
#   manual_only           仅允许用户显式选择，不参与推荐
#   recommend_or_confirm  可推荐，需用户确认后生效
#   auto_if_confident     唯一且高置信时可自动生效（默认）
entry_mode: recommend_or_confirm
default_vqr_ids: []
owner: marketing-analytics
version: 1.0.0
status: published
domain_id: domain.marketing
policy_refs: [policy.marketing_reader]
ontology_scope:
  root_concepts: [ontology.Campaign, ontology.Channel, ontology.Order, ontology.Customer]
  allowed_relations:
    - ontology.Campaign.usesChannel
    - ontology.Customer.touchedByCampaign
    - ontology.Customer.placesOrder
  max_path_hops: 3
  excluded_concepts: [ontology.Employee]
semantic_scope:
  metrics: [metric.ad_spend, metric.paid_gmv, metric.roas]
  dimensions: [dimension.channel, dimension.campaign, dimension.order_date]
  frozen_calibers:
    timezone: {type: string, value: "Asia/Shanghai"}
    revenue_metric: {type: metric_id, value: metric.paid_gmv}
    default_time_field: {type: field_id, value: dimension.order_date}
allowed_analysis_modes: [query, yoy_mom, attribution]
skills:
  - skill_id: skill.semantic_query
    analysis_mode: query
    params_schema_ref: schema.query.v1
  - skill_id: skill.last_touch_attribution
    analysis_mode: attribution
    params_schema_ref: schema.attribution.v1
entry_hints:
  - 渠道投放复盘
  - 广告效果分析
  - 投放 ROI
cold_start_samples:                          # 冷启动展示用
  - "上个月各渠道 ROAS 排名"
  - "哪个活动带来的 GMV 最高"
version_compatibility:
  ontology: "^1.0.0"
  semantic: "2026.11.*"
invalidation:
  on_scope_asset_deprecation: block
  on_skill_deprecation: block
```

规则：

- `entry_mode` 只控制入口推荐与自动生效策略，不改变 7.4 的确定性规则；`auto_if_confident` 仅在"唯一候选 + 置信 ≥ 阈值"时自动生效；
- `entry_hints` 仅用于推荐 Scenario 候选，不参与本体路径规划、权限授权或 DSL 组装；
- `cold_start_samples` 仅用于冷启动展示，必须是已发布 VQR 或 Golden Query 的引用，不得是自由文本；
- `ontology_scope` 和 `semantic_scope` 是查询候选的上限，不能扩大用户自身授权；
- `frozen_calibers` 是带类型的口径值约束（`{type, value}`），`caliber_key` 必须对应已发布资产字段；在该 Scenario 内为只读约束；
- `allowed_analysis_modes` 必须是引擎内置枚举的子集；
- Scenario 只能引用已发布 Skill/VQR，不可内联 SQL、脚本、Prompt 中的可执行代码或自由查询逻辑；
- 依赖资产、策略、Rule 或 Skill 不兼容/废弃时，Scenario 阻断发布或转为失效，不能静默降级；
- 版本兼容判定：语义版本按 SemVer；日期版本按 `YYYY.MM` 前缀匹配，前缀不同视为不兼容，同前缀内仅允许新增字段，删除/改义视为不兼容。

### 5.8 Skill 注册与治理

Skill 是能力单元，不是用户脚本容器。定义：

```yaml
skill_id: skill.entity_lookup
name: 实体属性直查/判定/批量
owner: platform-data
version: 1.1.0
status: published
analysis_mode: lookup
params_schema_ref: schema.lookup.v1
implementation_ref: builtin.lookup.entity@1.1.0
required_capabilities: [semantic.query, rule.evaluate]
allowed_scenario_ids: []
max_batch_size: 100
```

```yaml
skill_id: skill.last_touch_attribution
name: 末次触点归因
owner: marketing-analytics
version: 1.0.0
status: published
analysis_mode: attribution
params_schema_ref: schema.attribution.v1
implementation_ref: builtin.attribution.last_touch@1.0.0
required_capabilities: [semantic.query]
allowed_scenario_ids: [scenario.channel_campaign_review]
approximation_of: []            # 若声明，表示本 Skill 是某不可用模式的预声明近似
```

Skill 生命周期为：`draft → schema/安全校验 → 人工审核 → publish → monitor → deprecate/rollback`。`implementation_ref` 只能指向应用内审核过的构造器或受控工具注册表；`implementation_ref` 命名空间由 Skill 注册中心统一分配，禁止 Scenario 作者自定义命名空间。新增 Skill 可组合已发布工具，但不能添加自由 SQL、绕过权限/成本校验或直接连接数据库。

`params_schema_ref` 必须指向已发布且版本固定的 Schema；`analysis_mode` 必须是内置枚举。若未来引入可扩展构造器，也必须作为经代码签名、测试和发布的服务端插件，不属于 Scenario 自定义能力。

编译期校验（与 8.1 联动）：

- `required_capabilities` 必须被当前部署的受控工具注册表全部满足，否则拒绝路由；
- 若 `allowed_scenario_ids` 非空，当前 Scenario 必须在其列表中；为空表示允许全局（自由问数）调用；
- 引用 `rule.evaluate` 能力的 Skill 必须同时满足 Rule 注册中心可用且规则已发布；
- `max_batch_size` 必须被 DSL 的批量参数遵守。

**`schema.lookup.v1` 参数规范**：

```yaml
subject_class_id: ontology.Customer
identity_filters:
  - field_id: ontology.Customer.customer_id
    op: eq                     # 单实体；批量用 in
    value: user-002
attributes: [ontology.Customer.email]
metrics: []
display_transforms:            # 可选，受控枚举
  ontology.Customer.register_time: duration_from_now
limit: 1                       # lookup_batch 时 ≤ max_batch_size
```

### 5.9 Rule 注册与治理（判定规则）

Rule 是布尔判定口径的唯一合法载体。定义：

```yaml
rule_id: rule.high_value_v1
name: 高价值用户判定
owner: crm-analytics
version: 1.0.0
status: published
subject_class_id: ontology.Customer
time_window: 12m
condition:
  all_of:
    - metric: metric.paid_gmv
      op: gte
      value: 5000
      currency: CNY
input_dependencies: [metric.paid_gmv]
sensitive_level: label
test_cases:
  - subject: user-002
    expected: true
```

规则：

- `condition` 只允许声明式引用已发布资产，禁止自由表达式、子查询、物理字段；
- `input_dependencies` 必须全部为已发布 Metric/Attribute/Enum；任一依赖废弃或不兼容变更时，Rule 失效或阻断发布（与 11.3 联动）；
- Rule 生命周期与 Skill 同构；
- `boolean_rule` 型 Metric 引用 Rule 时锁定 `rule_id + rule_version`；运行时按当前 `rule_version` 求值并记录；
- 用户在对话中给出的临时阈值不得即时转为 Rule；只能引导走 Rule 发布流程（7.7、11.5）。

### 5.10 VQR、Scenario、Skill、Rule 的关系

- VQR 是特定问题的参数化查询模板；
- Skill 是被审核注册的能力单元；
- Rule 是被审核注册的判定口径，仅被 `boolean_rule` 型 Metric 引用；
- Scenario 是语义上下文和路由配置，可引用 Skill 和 `default_vqr_ids`；
- 四者均不得保存绕过当前用户权限的最终可执行 SQL；
- VQR 命中或 Skill 执行时都重新绑定当前 Scenario/本体/语义/规则/策略版本、检查权限和成本，再由确定性编译器生成 SQL（权威表述见 11.4）；
- Scenario 的 `default_vqr_ids` 仅影响候选优先级，不跳过验证、授权或编译。

**时间表达式模式**（供时间解析器使用）：

## 6. 类型化 DSL

### 6.1 两级路由与结构化输出（含复合意图）

Scenario 入口候选和查询意图是两个阶段。用户显式选择时跳过推荐模型；否则入口推荐只看轻量输入和 `entry_hints`，不得先生成查询 DSL。

第一级 `Scenario Entry Proposal` 只推荐入口，不含查询模式、指标或关系路径：

```json
{
  "proposal_version": "1.0",
  "scenario_candidates": [
    {"scenario_id": "scenario.channel_campaign_review", "confidence": 0.91}
  ]
}
```

最终入口来源以服务端 `scenario_entry_source` 为准（见 12.1）。低置信或并列候选回退自由问数，并展示可选入口。

第二级 `Intent Proposal` 仅在已确认 Scenario scope 或自由问数授权全域内生成，支持复合意图拆分建议：

```json
{
  "proposal_version": "1.0",
  "is_composite": true,
  "sub_intents": [
    {
      "sub_intent_id": "s1",
      "analysis_mode_candidates": [{"mode": "query", "confidence": 0.9}],
      "concept_mentions": [{"text": "GMV", "candidate_class_ids": ["ontology.Order"]}],
      "metric_candidates": [{"id": "metric.paid_gmv", "variant_hint": null}],
      "dimension_candidates": ["dimension.region"],
      "filters": [
        {"field_candidates": ["dimension.order_date"], "op": "between", "time_expression_raw": "上个月"},
        {"field_candidates": ["dimension.region"], "op": "eq", "value": "华南"}
      ],
      "missing_information": []
    },
    {
      "sub_intent_id": "s2",
      "analysis_mode_candidates": [{"mode": "yoy_mom", "confidence": 0.85}],
      "depends_on": ["s1"],
      "missing_information": []
    },
    {
      "sub_intent_id": "s3",
      "analysis_mode_candidates": [{"mode": "attribution", "confidence": 0.8}],
      "depends_on": ["s1"],
      "missing_information": []
    }
  ],
  "attribute_mentions": [],
  "rule_mentions": [],
  "needs_discovery": false,
  "missing_information": []
}
```

字段说明：

- `is_composite` / `sub_intents`：复合意图拆分建议；服务端校验后决定是否拆分，LLM 不得绕过拆分规则；
- `depends_on`：子意图间的上下文依赖（如"环比"依赖"10 月华南 GMV"的时间窗），仅用于上下文继承，**不合并 SQL**；
- `variant_hint`：口径变体提示；为空且存在变体时走 `CALIBER_AMBIGUOUS`；
- `time_expression_raw`：相对时间原始表达；绝对日期由时间解析器解析，LLM 不得直接输出绝对日期（用户显式给出除外）；
- `needs_discovery`：意图不明；为 true 时走 7.6 引导式发现，不进入 DSL 组装；
- 多轮指代由服务端 `resolved_entities` 与 `session_query_context` 解析。

单意图 `Intent Proposal` 结构同上，`is_composite: false`，`sub_intents` 长度为 1。

`Intent Proposal` 经过服务端校验、歧义处理、Analysis Mode/Skill 路由和本体路径规划后，由系统组装最终 DSL（单查询或子查询序列）。单查询示例：

```json
{
  "schema_version": "1.0",
  "ontology_version": "commerce-ontology@1.0.0",
  "semantic_version": "commerce@2026.11.01",
  "rule_version": null,
  "time_parser_version": "time@1.0.0",
  "scenario_id": "scenario.channel_campaign_review",
  "skill_id": "skill.semantic_query",
  "analysis_mode": "query",
  "root_concept_id": "ontology.Customer",
  "concepts": ["ontology.Customer", "ontology.Order"],
  "relation_path": ["ontology.Customer.placesOrder"],
  "model_id": "model.commerce",
  "attributes": [],
  "metrics": ["metric.paid_gmv"],
  "metric_variants": [],
  "dimensions": ["dimension.region", "dimension.channel"],
  "filters": [
    {"field_id": "dimension.order_date", "op": "between", "time_expression_raw": "上个月", "resolved_range": ["2026-10-01", "2026-10-31"]},
    {"field_id": "dimension.region", "op": "in", "value": ["华南"]}
  ],
  "orders": [{"field_id": "metric.paid_gmv", "direction": "desc"}],
  "limit": 100,
  "analysis_params": null
}
```

复合查询 DSL 为子查询序列：

```json
{
  "schema_version": "1.0",
  "parent_request_id": "req-20261106-010",
  "sub_queries": [
    {"sub_intent_id": "s1", "dsl": { /* 单查询 DSL */ }},
    {"sub_intent_id": "s2", "dsl": { /* 单查询 DSL，上下文继承 s1 */ }},
    {"sub_intent_id": "s3", "dsl": { /* 单查询 DSL，上下文继承 s1 */ }}
  ]
}
```

> 复合查询的每个子查询**独立编译、独立授权、独立执行、结果隔离组装**；不得共享中间结果集，不得合并为一条 SQL；任一子查询失败不阻止其他子查询返回（失败子查询单独返回原因码）。

`relation_path` 由本体规划器产生，不接受模型直接提交的任意路径。服务端持有结构化输出的完整 JSON Schema，设置 `additionalProperties: false`，并对候选 ID 进行版本和授权校验。

### 6.2 强制约束

- `analysis_mode` 为封闭枚举，首发至少含 `query`、`lookup`、`yoy_mom`、`funnel`、`attribution`、`retention`、`discovery`；
- `scenario_id` 可空，`null` 表示自由问数；非空时必须属于当前用户可访问且状态为 `published` 的 Scenario；
- `skill_id` 必填，必须来自全局/Scenario 绑定的已发布 Skill，且其 `analysis_mode` 与 DSL 一致；一个 mode 有多个 Skill 时必须由唯一路由规则选出，否则澄清/拒答；
- 自由问数也只可调用全局已发布 Skill，不能省略 Skill 校验；
- 最终 DSL 必须声明 `ontology_version`、`semantic_version`、`time_parser_version`；引用 `boolean_rule` 指标时必须声明 `rule_version`；
- `root_concept_id`、`concepts`、`relation_path`、`attributes`、`metric_variants`、场景主体 ID 只能引用当前本体版本中已发布的 ID；
- LLM 输出 `Intent Proposal`，不得输出最终 `relation_path`；最终路径由本体规划器生成并校验；
- 路径每一跳的起止类型、方向、基数、授权域和映射都必须通过校验；
- 所有资产只能使用 ID，不使用自由文本表名；
- 不允许 `sql`、`expression`、`join.on`、函数体、内联阈值和注释字段；
- `metrics`、`dimensions`、`attributes`、`metric_variants`、`filters` 必须属于 `semantic_version`；
- 过滤字段必须是可过滤维度或可过滤属性；
- 排序字段必须属于已选择的指标、维度或属性；
- `limit` 设置全局上限；`lookup` 单实体模式 `limit` 上限为 1；`lookup_batch` 上限为 Skill 声明的 `max_batch_size`；
- **相对时间必须携带 `time_expression_raw` 并由时间解析器产出 `resolved_range`；LLM 不得直接输出绝对日期（用户显式给出时 `source: explicit` 除外）；**
- **filters 操作符枚举：`eq`、`ne`、`in`、`not_in`、`between`、`not_between`、`gt`、`gte`、`lt`、`lte`、`exclude_entity`；`exclude_entity` 用于排除实体（如"不含测试订单"），必须引用已发布实体或标识属性；**
- **复合查询必须拆为 `sub_queries` 序列，每个子查询独立走本约束全部校验；不得合并 SQL、不得共享中间结果；子查询间只允许通过 `depends_on` 继承上下文（指标/维度/过滤/时间窗），继承后仍须逐项重新校验授权与 scope；**
- **`lookup` 模式允许 `relation_path` 为空、`metrics`/`dimensions` 为空，但 `attributes` 与 `metrics` 至少一个非空；其他模式仍要求至少一个 metric 或 dimension；**
- **`lookup` 模式必须通过唯一标识属性定位主体；`lookup_batch` 通过 `in` 定位多个主体，批量结果逐行做存在性与权限检查，单行不可用时该行返回统一"不可用"，不泄露差异；**
- **命中 `frozen_calibers` 的字段，DSL 值必须与冻结值一致；不一致即拒绝，返回 `SCENARIO_CALIBER_OVERRIDE`；**
- **DSL 中所有资产 ID、`relation_path`、`analysis_mode`、`skill_id` 必须落在 `scenario.ontology_scope` + `semantic_scope` + `allowed_analysis_modes` + `skills[]` 内；越界返回 `SCENARIO_SCOPE_VIOLATION`；**
- **Skill 的 `required_capabilities` 未满足返回 `SKILL_CAPABILITY_MISSING`；`allowed_scenario_ids` 不含当前 Scenario 返回 `SKILL_SCENARIO_NOT_ALLOWED`；`analysis_mode` 不一致返回 `SKILL_ANALYSIS_MODE_MISMATCH`；**
- **`metric.allowed_modes` 必须包含当前 `skill.analysis_mode`，否则返回 `METRIC_MODE_NOT_ALLOWED`；**
- **跨域组合：DSL 引用的资产跨多个 `domain_id` 时，必须通过 10.1 域组合策略检查；不允许的组合返回 `CROSS_DOMAIN_NOT_ALLOWED`；需审批的组合返回 `CROSS_DOMAIN_APPROVAL_REQUIRED`；**
- **累计敏感：同一 session 内对同一敏感字段/标签的逼近查询累计超阈值时，返回 `SENSITIVE_QUERY_SEQUENCE`，触发审批或拒答；**
- **`display_transforms` 只允许引用属性 `display_hints.allowed_transforms` 中的受控枚举；`duration_from_now` 等时间依赖转换进入缓存键；**
- DSL 通过 Schema 后仍需经过语义绑定和权限校验；
- 不能通过 DSL 直接指定物理库、Schema、表或列。

### 6.4 本体查询规划与 DSL 边界

解析器和本体规划器分工如下：

- LLM 从授权候选集中识别 `root_concept_id`、概念/关系/属性提及、指标/维度候选、口径变体提示和参数，并给出复合意图拆分建议；
- 服务端优先用 `resolved_entities` 解析多轮指代，用 `session_query_context` 合并增量修改，再进入概念消歧；
- 本体规划器根据类类型、关系方向、基数、映射状态、授权域、Scenario scope 和成本确定合法 `relation_path`；
- 有唯一最优路径时由规划器填入 DSL；存在多条等价路径时澄清；不存在合法路径时拒答；
- 编译器只接受规划器校验通过的路径，沿路径解析 Ontology Mapping 到 Model Join Path；
- DSL 的 `relation_path` 是逻辑业务关系 ID，不是物理连接表达式；不允许 `join_path_id` 覆盖或绕开本体路径校验；
- 场景构造器从同一条本体路径绑定主体、事件、触点和转化对象；主体标识只能引用本体属性 ID，禁止 DSL 自带物理 user_id 字段；禁止暗中换用其他实体关联；
- 路径终点集合必须覆盖 DSL 中 `metrics`/`dimensions`/`attributes`/`analysis_params` 引用的所有实体；不覆盖时规划器补全或拒答；
- 复合意图拆分由服务端决定：LLM 的 `sub_intents` 仅作建议；服务端校验每个子意图可独立成 DSL，否则澄清或拒答；子查询间不合并 SQL。

示例：用户问“按渠道统计上月下单客户的已支付金额”，本体绑定为 `Customer` → `placesOrder` → `Order`，指标为 `paid_gmv`，维度为 `channel`。若“渠道”在本体中既可能是客户注册渠道，也可能是订单归因渠道，系统必须追问口径，不能仅靠相似度选一个。

### 6.5 Schema 版本规则

DSL Schema、语义资产、Scenario、Skill、Rule、时间解析器、文案模板、Analysis Mode 构造器和 SQL 编译器分别版本化。兼容性规则：

- 新增可选字段：小版本；
- 修改字段含义、删除字段或改变值域：大版本；
- 编译器只接受声明支持的 Schema 版本；
- Scenario/Skill 引用资产时按 5.7 版本兼容判定；不兼容时阻断发布或使运行时失效；
- 审计记录保存原始 DSL，不只保存规范化结果。

## 7. 查询处理流程

### 7.1 请求上下文（含多轮与查询上下文）

每次请求先建立不可伪造的上下文：

```text
request_id
parent_request_id（子查询时）
session_id
turn_index
user_id
tenant_id
groups
allowed_domains
domain_combination_policy_version
policy_version
ontology_version
semantic_version
rule_version
time_parser_version
copy_template_version
model_version
client_type
trace_id
resolved_entities: [{class_id, id_value, source, turn_id}]
session_query_context: {
  metrics: [], metric_variants: [], dimensions: [], attributes: [],
  filters: [], time_window: {expression_raw, resolved_range},
  scenario_id, analysis_mode
}
session_scenario_state: in_scenario(scenario_id) | free | pending_confirm(scenario_id)
sensitive_query_counters: {sensitive_key: count}
```

上下文由认证系统签发，不能由 LLM、用户参数或前端自由修改。手动指定 Scenario 时，客户端只提交 `scenario_id`（及可选的用户确认标记），**不得提交 scope、frozen_calibers、allowed_analysis_modes、resolved_entities、session_query_context 等字段**。

`resolved_entities` 规则：

- 绑定 `user_id + tenant_id + session_id`，跨会话清空；
- 来源标记 `source`：`prev_turn`、`explicit`、`confirmed`；
- 锚点不携带被裁字段信息；实体删除、权限变更或 Scenario scope 变化导致锚点失效时，下一轮重解析或澄清；
- 上一轮拒答不阻止实体锚点延续，但下一轮若涉及被裁字段仍需重新走授权裁剪。

`session_query_context` 规则：

- 只存 ID 与结构化值（时间窗、操作符、值），不存 SQL、不存编译结果；
- 每轮增量修改（新增/覆盖/清除）后，**必须重新走完整 DSL 校验、scope 校验、权限编译和成本检查**；不得复用上一轮编译结果；
- 增量合并规则：用户显式新增同类条件 → 覆盖；用户说"再加上/只看" → 追加；用户说"去掉/不算" → 清除；用户未提及的类别 → 沿用；
- 若上一轮条件在本轮因权限/scope 变化不可用，增量时显式提示"上轮的 X 已不可用"，不得静默丢弃或静默保留；
- 上下文进入审计 `context_delta`；跨会话清空。

### 7.2 数据域路由与跨域组合检查

域路由属于自建能力，输入是用户身份、问题中的业务对象、候选资产和数据域元数据。路由输出可以是多个候选域及其置信度，不能在分数接近时强行早停。

**跨域组合检查**：当候选资产跨多个 `domain_id` 时，按 10.1 域组合策略检查；不允许的组合在入口或 DSL 校验阶段拒绝（`CROSS_DOMAIN_NOT_ALLOWED`），需审批的组合返回 `CROSS_DOMAIN_APPROVAL_REQUIRED` 并提示审批入口。

### 7.3 本体概念解析、指代消解、上下文合并与路径规划

1. 仅在已确认的 Scenario scope 或自由问数的用户授权全域内抽取和检索实体、关系、属性、指标、维度、口径变体和时间表达；
2. 由确定性过滤器先应用用户授权，再应用 Scenario 的 `ontology_scope`、`semantic_scope` 和排除项；
3. 多轮指代优先用 `resolved_entities` 解析；解析失败再走概念消歧；
4. 增量修改按 7.1 `session_query_context` 规则合并；合并后重新走后续校验；
5. 相对时间由版本化时间解析器解析（5.12），记录 `time_expression_raw` + `resolved_range` + `pattern_id`；未命中则澄清；
6. 结合数据域、同义词、口语别名、拼音别名、上下文和概念定义消歧；受限模糊候选只作澄清候选，不直接绑定；
7. 对存在歧义的概念、关系、口径（未定义/并列/变体不明）发起澄清；
8. 对唯一候选概念，由确定性本体规划器计算合法关系路径并校验类型、基数、权限、scope、映射和成本；
9. 只有合法路径唯一或有明确最低代价路径时才进入 DSL；路径并列时澄清。

LLM 不输出物理 Join，也不负责决定最终关系路径、绝对日期或口径变体。规划器的路径代价函数版本化，优先级固定为：显式用户指定关系 > 已审核的 Golden Path > 最短合法路径；不以向量相似度覆盖业务约束。

### 7.4 Scenario Entry：第一级路由（含会话沿用与冷启动）

入口优先级与结果矩阵：

| 进入方式 | 触发 | 行为 | 失败/冲突处理 |
|---|---|---|---|
| **会话沿用**（inherit） | `session_scenario_state = in_scenario(id)` 且用户未显式退出、问题未越界 | 沿用该 Scenario scope，不重新推荐 | 问题明显超出 scope → 触发"是否切场景/退出"澄清，**不临时扩 scope**；用户显式"退出场景" → 回 `free` |
| **手动指定**（manual） | 用户显式选择 `scenario_id` | 跳过推荐模型，直接加载该 Scenario 的已发布 scope | 无权限/已失效 → 拒答 `SCENARIO_MANUAL_UNAUTHORIZED`，**不静默回退自由问数**；问题超出 scope → 场景内澄清，**不临时扩 scope** |
| **AI 推荐**（auto） | 未手动指定、无会话沿用；`entry_hints` + 问题内容 + 域路由 | 生成候选；按 `entry_mode` 决定是否自动采用 | 唯一高置信 + `auto_if_confident` → 自动进入；否则回退自由问数并提示可选入口，记录 `SCENARIO_AUTO_LOW_CONFIDENCE_FALLBACK` |
| **冷启动地图**（cold_start） | 用户首次会话或长期未用 | 展示授权 scope 内 Scenario 列表 + 每场景 `cold_start_samples`（已发布 VQR/Golden Query 引用）+ 自由问数入口 | 用户点选后按 manual 处理；用户直接提问则按 auto/none 处理 |
| **自由问数**（none） | 用户拒绝推荐 / 未命中 / 低置信 / 显式退出 | 使用用户授权全域，不套 Scenario scope | 与场景内使用同一澄清机制；不额外限制 |

会话状态机：

```text
free --(manual|auto确认|cold_start点选)--> in_scenario(id)
free --(auto_if_confident 高置信)--> in_scenario(id)
in_scenario(id) --(用户显式退出)--> free
in_scenario(id) --(问题越界)--> pending_confirm(id) --(用户确认切换/退出)--> in_scenario(other)/free
in_scenario(id) --(会话结束)--> 销毁（跨会话不沿用）
pending_confirm(id) --(用户取消)--> in_scenario(id)
```

补充规则：

- 用户可确认推荐的 Scenario，确认后按手动指定同等效力；
- `entry_hints` 只参与入口推荐，不参与本体路径规划、权限授权或最终 DSL 组装；
- Scenario scope 只能进一步收窄授权候选，不可扩大用户授权；
- 会话内已确认的 Scenario 默认沿用，直到用户显式切换或问题明显超出 scope 触发"是否切场景"澄清；跨会话不沿用；
- 冷启动地图只展示已发布资产引用，不展示自由文本，不构成推荐强制入口。

### 7.5 检索瀑布与 Proposal 来源完整性校验

首发查询候选集按以下顺序形成：

1. 认证层按用户、租户和数据域做授权过滤，并做跨域组合检查；
2. Scenario Entry Router 按 7.4 确认 Scenario（含会话沿用、冷启动）或回退自由问数；
3. 已确认 Scenario 时按其 `ontology_scope`、`semantic_scope`、`allowed_analysis_modes` 和已发布 Skill 列表裁剪候选；自由问数时使用用户授权的全域集合；
4. 对裁剪后的集合做精确结构化匹配、术语/同义词/口语别名/拼音别名匹配；
5. **受限模糊候选**（编辑距离、子串、拼音近似）：仅作为澄清候选展示，不直接进入 DSL；模糊候选不得覆盖精确/同义词命中；
6. 有限本体关系规划；
7. VQR 候选匹配（发布后启用；命中后仍按 11.4 重编译）；
8. 高级候选召回（图谱扩展、向量 + BM25、rerank）按 M5 条件启用，且只能在用户授权与 Scenario scope 双重裁剪之后运行；scope 被裁掉的候选不能回灌给 LLM。

**Proposal 来源完整性校验**（对抗提示注入）：

- 每轮注入 LLM 的候选集附带 `context_hash`；
- LLM 输出的每个 ID 必须能在本轮候选集中找到；候选集之外的 ID 一律拒绝；
- 候选集来源不可被 LLM 扩写；LLM 不得引入新 `scenario_id`、`skill_id`、`analysis_mode`、`rule_id`、`metric_variant`；
- 若 Proposal 中出现候选集之外的 ID 或异常模式（如自称管理员、要求忽略规则），标记 `PROMPT_INJECTION_SUSPECTED`，走澄清或拒答，并完整审计。

### 7.6 Analysis Mode 与 Skill：第二级路由（含 discovery 与近似降级）

完成入口确认和 scope 裁剪后，才在受限候选集内识别 Analysis Mode：

```json
{
  "scenario_id": "scenario.channel_campaign_review",
  "analysis_mode_candidates": [
    {"mode": "attribution", "confidence": 0.91, "missing_params": []}
  ],
  "skill_candidates": ["skill.last_touch_attribution"],
  "needs_clarification": false
}
```

路由规则：

- `analysis_mode` 必须属于所选 Scenario 的 `allowed_analysis_modes`；自由问数则从全局内置枚举选择；
- Skill 必须在该 Scenario 已发布 `skills[]` 中绑定当前 Analysis Mode，且参数满足其固定 `params_schema_ref`；自由问数可调用全局已发布 Skill；
- `metric.allowed_modes` 必须包含当前 `skill.analysis_mode`，否则 `METRIC_MODE_NOT_ALLOWED`；
- 同一 Analysis Mode 有多个 Skill 且无法确定时，澄清或按明确定义的优先级选择；不能由 LLM 发明 Skill ID；
- Scenario scope 中没有能承担该模式的 Skill 时，拒绝该模式并给出可选问题/出口，不退化到自由 SQL；
- Scenario 推荐低置信回退自由问数的路径与 Scenario 内歧义澄清共用相同的候选解释和审计机制。

**discovery（引导式发现）**：

- 当 `needs_discovery: true` 或 `analysis_mode_candidates` 为空且无明确实体/属性意图时触发；
- 系统在当前授权 scope（含 Scenario scope）内返回受限候选入口清单：可用 Scenario 列表 + 每个 `cold_start_samples`（已发布引用）+ 可用 Analysis Mode 的 Golden Query 样例；
- 清单项必须可点击/可复制为下一轮提问；不构成强制入口；
- discovery 不进入 DSL 组装，不执行查询；审计记 `DISCOVERY`；
- discovery 展示的样例必须来自已发布 VQR/Golden Query，不得由 LLM 自由生成。

**近似降级声明**：

- 当请求的 Analysis Mode 在 scope 内无 Skill 承担，但存在 `approximation_of` 预声明近似关系时，系统**声明近似关系并征得同意**后降级；
- 近似关系必须在 Skill 资产中预声明（`approximation_of: [mode]`），不由 LLM 现场编；
- 降级后仍走完整 DSL 校验与权限编译；审计记 `MODE_APPROXIMATED` 与原请求 mode。

### 7.7 DSL 生成与校验（含口径降级、纠正、能力边界、澄清规范、文案模板）

1. LLM 只接收当前用户授权且已通过 Scenario scope 裁剪的本体概念、资产、属性、Analysis Mode 和 Skill 候选（带 `context_hash`）；
2. LLM 输出 `Intent Proposal`，Schema 校验、候选 ID 校验、来源完整性校验；
3. 确定性入口层确认 `scenario_id` 或采用 `null` 自由问数（含会话沿用判定）；
4. 在有效 scope 中完成指代消解、上下文增量合并、时间解析与概念消歧；歧义则澄清；
5. 本体规划器生成唯一合法关系路径；
6. 第二级路由选定合法 Analysis Mode 与该 Scenario 绑定的已发布 Skill（含 discovery 与近似降级判定）；
7. 复合意图拆分为子查询序列，每个子查询独立组装 DSL；
8. 服务端组装最终 Query DSL，校验本体、语义、规则、时间解析、Scenario、Skill、域组合、累计敏感和策略版本；
9. 校验 scope、frozen calibers、参数 Schema、粒度、关系约束和完整权限覆盖；
10. 预估查询成本，通过后交给确定性编译器。

任一步失败，只能澄清、引导、拒答或进入人工处理。错误响应不得泄露被裁剪资产的名称与存在性。

**口径未发布时的降级路径**：

- 用户给出临时口径时，系统不得即时执行；
- 若该口径可由已发布 Metric/Attribute 组合验证，则降级回答可验证部分，并说明"是否为 X 需按已发布 Rule 判定"；
- 若无法降级，则澄清并引导走 Rule/指标发布流程（11.5）；
- 降级回答必须标注"非判定结论"，不得输出是/否。

**纠正处理**：

- 用户显式否定上一轮结果（如"不是这个意思""我说的不是这个渠道"）时，系统回退到**上一轮澄清点**重新消歧；
- 本轮结果标记 `user_rejected`，进入纠正样本池（13.2 回归集来源）；
- 不得静默重试同一 DSL；不得将用户纠正当作新的独立问题而丢失上下文。

**能力边界拒答**：

- 当请求明显超出系统能力（预测、自由 SQL、画像生成、外部抓取等）时，返回 `OUT_OF_CAPABILITY`；
- 拒答文案必须说明"当前系统支持：取数、单实体查询、批量查询、布尔判定、漏斗/同环比/归因/留存、引导式发现；不支持：预测、自由 SQL、画像生成、外部抓取"；
- 能力边界文案来自 5.12 模板，版本化。

**澄清规范（四要素）**：

每个澄清必须含：

1. 歧义点说明（"你说的渠道指？"）；
2. 2–5 个候选（来自授权 scope，标注来源资产 ID）；
3. 默认建议（如 Golden Path 优先级、最常用口径）；
4. 可跳过/降级选项（"不确定可先看 X"）。

不满足四要素的澄清视为不合格，进入 13.2 `clarification_quality` 人工评分。

**原因码与文案模板**：

每个原因码必须绑定 5.12 已发布文案模板；模板禁止出现资产名、物理表、SQL、被裁字段名。原因码表见下。

| `CROSS_DOMAIN_APPROVAL_REQUIRED` | 6.2/7.2 域组合需审批 | 提示审批入口，不执行 |
| `SENSITIVE_QUERY_SEQUENCE` | 6.2/10.5 跨轮累计敏感超阈值 | 审批或拒答 |
| `PROMPT_INJECTION_SUSPECTED` | 7.5 候选集外 ID 或异常模式 | 澄清或拒答，完整审计 |
| `OUT_OF_CAPABILITY` | 7.7 能力边界外 | 拒答并说明能力边界 |
| `INTENT_UNDISCOVERED` | 7.6 discovery 已触发但用户未选择 | 保持 discovery 态，不拒答 |
| `TIME_EXPRESSION_UNRESOLVED` | 7.3 时间解析未命中 | 澄清相对时间 |
| `MODE_APPROXIMATED` | 7.6 近似降级已征得同意 | 正常返回，标注近似 |
| `USER_REJECTED` | 7.7 用户显式否定 | 回退澄清，进纠正样本池 |

原因码同时进入审计（12.1）和失败看板（12.3）。

## 8. 确定性查询编译器

### 8.1 编译阶段

1. 读取固定发布清单中的本体、Scenario、Skill、Rule、时间解析器、文案模板、语义、策略、SQL 方言和编译器版本；
2. 校验 `scenario_id`/`skill_id`、scope、frozen_calibers、`model_id`、指标粒度和 Join Path；
3. 校验 Skill 的 `required_capabilities`、`allowed_scenario_ids`、`analysis_mode`；
4. 校验 `metric.allowed_modes ∋ skill.analysis_mode`（`METRIC_MODE_NOT_ALLOWED`）；
5. 校验口径变体：`metric_variants` 必须属于主指标的已发布变体，且 `condition` 与变体定义一致；
6. 若引用 `boolean_rule` 指标：校验 `rule_id + rule_version` 已发布、`input_dependencies` 全部可用；
7. 校验相对时间：`time_expression_raw` 与 `resolved_range` 必须由同一 `time_parser_version` 产出，且 `resolved_range` 落在 `time_window` 允许范围内；
8. 校验 `display_transforms` 只引用属性 `display_hints.allowed_transforms`；
9. 校验跨域组合策略与累计敏感阈值；
10. 展开指标定义；对 `boolean_rule` 调用 Rule 注册中心求值，结果进入查询结构；
11. 进行粒度分析和必要的预聚合；
12. 解析已注册 Ontology Relation 到 Join Path；
13. 根据已校验的 Analysis Mode 和 Skill 编译 `analysis_params`；
14. 编译字段级、行级权限、存在性保护和标签敏感策略；
15. 生成查询结构；
16. 生成参数化 SQL；
17. 进行 SQL 方言校验和成本检查；
18. 生成规范化 SQL、执行参数和编译证明摘要。

复合查询按子查询逐项执行上述流程，**每个子查询独立编译、独立生成 SQL、独立 dry-run**；子查询之间不共享编译结果。

### 8.2 粒度、唯一性与批量安全

编译器必须拒绝或显式处理：

- 多对多 Join 未声明去重策略；
- 事实表之间直接 Join 导致的行放大；
- 指标粒度和维度粒度不兼容；
- 非唯一关系被当作一对一使用；
- 未定义的空值传播；
- 未声明的时区转换；
- 分母为零但未声明策略；
- `lookup` 单实体模式标识属性唯一性范围不成立时，拒绝或返回多结果并显式标注"多结果"；
- `lookup` 投影属性 `existence_sensitive: true` 且用户无读权限时，拒绝（`ATTRIBUTE_NOT_AVAILABLE`），不得以"无结果"暗示存在性；
- **`lookup_batch` 行数超过 `max_batch_size` 时拒绝；批量结果逐行做存在性与权限检查，单行不可用时该行返回统一"不可用"，不泄露差异；批量结果不因单行失败而整体失败；**
- **`display_transforms` 中时间依赖转换（如 `duration_from_now`）必须使用同一请求时间基准，结果进入缓存键。**

### 8.3 dry-plan 和 dry-run

- `dry-plan`：展示语义展开结果、规则求值、口径变体、时间解析、规范化 SQL、参数、执行计划和成本估计，不执行业务查询；
- `dry-run`：在真实数据库和同一身份上下文中校验 SQL、权限和资源约束，不返回业务行；
- 复合查询逐子查询 dry-plan/dry-run；
- 二者结果均写入审计附件；
- dry-run 与正式执行之间使用短生命周期执行令牌；
- 正式执行仍必须重新验证上下文、策略版本和资源限制。

### 8.4 资源控制

每个查询（含每个子查询）必须有：

- 超时时间；
- 最大扫描量；
- 最大返回行数；
- 成本上限；
- 并发队列；
- 取消机制；
- 禁止副作用语句；
- 失败分类：语义、权限、成本、数据库、数据质量、系统故障。

复合查询的资源上限按子查询数量与总量双重控制。

## 9. Analysis Mode 分析模式语义契约

### 9.1 lookup

必须固定：

- 标识属性及唯一性范围；
- 允许投影的属性集合（`lookup_projectable`）；
- 是否允许返回多结果（单实体 `limit ≤ 1`，批量 `limit ≤ max_batch_size`）；
- 存在性保护策略（`existence_sensitive`）；
- 批量结果的逐行可用性与差异保护；
- 受控展示转换（`display_transforms`）；
- 布尔判定指标的 Rule 版本与求值时点；
- 判定结果敏感策略（`label` 型）。

### 9.2 discovery

必须固定：

- 触发条件（`needs_discovery` 或意图为空）；
- 候选清单来源（已发布 VQR/Golden Query/`cold_start_samples`，不得自由生成）；
- 展示范围（授权 scope 内，含 Scenario scope）；
- 不执行查询、不进入 DSL；
- 用户点选后的后续路径（按 manual/none 处理）。

### 9.3 漏斗

必须固定以下口径：

- 分母为首步、上一步还是独立用户；
- 用户按首次事件还是任意事件计数；
- 步骤是否必须严格有序；
- 用户级时间窗口还是全局窗口；
- 是否允许跨会话；
- 同时发生事件的排序规则；
- 分组维度取首次触点、步骤发生时值还是转化时值。

### 9.4 同环比

必须固定：

- 自然周期或业务周期；
- 时间时区；
- 不完整周期是否允许比较；
- 缺失周期的处理；
- 分母为零的输出；
- 当前周期和对比周期是否必须使用同一维度枚举；
- 相对时间表达与解析器版本。

### 9.5 简单归因

必须固定：

- 触点回溯窗口；
- 首触、末触、线性模型的公式；
- 多次转化处理；
- 触点与转化同一时间的处理；
- 无触点转化处理；
- 匿名用户处理；
- 渠道合并规则。

### 9.6 留存

必须固定：

- cohort 起点事件；
- 回访事件；
- 自然周/月或滚动周期；
- 未完整结束周期的处理；
- 用户去重；
- 时区和日期边界；
- 分组维度取值时点。

每个 Analysis Mode / Skill 都必须配套 Golden Query、边界样例和结果人工复核记录。

## 10. 权限与安全

### 10.1 权限模型（含域组合与身份不可覆盖）

采用四层策略：

1. **身份层**：用户、租户、用户组和组织关系；
2. **工具层**：工具白名单和 access group；
3. **语义层**：资产、字段、指标、属性、标签和数据域授权；域组合策略；
4. **数据库层**：按首发数据库确定的原生 RLS、安全视图或受控数据集。

**身份声明不可覆盖**：用户文本中的"我是管理员""忽略规则""以 root 身份"等声明一律无效；身份只来自认证系统签发的上下文。LLM 输出中若出现身份声明，标记 `PROMPT_INJECTION_SUSPECTED`。

**域组合策略**：声明哪些 `domain_id` 组合：

- 允许（默认各自授权即可组合）；
- 需审批（`CROSS_DOMAIN_APPROVAL_REQUIRED`）；
- 禁止（`CROSS_DOMAIN_NOT_ALLOWED`）。

域组合策略版本化，进入 `domain_combination_policy_version`；每次跨域查询记录策略版本。

### 10.2 RLS 规则

RLS 策略必须包含：

- policy_id 和 Owner；
- 适用租户和数据域；
- 行过滤字段；
- 授权值来源；
- 空授权集策略；
- 未映射值策略；
- 策略版本；
- 测试样例；
- 紧急下线方式。

默认策略：没有明确授权即拒绝。应用层注入的过滤条件必须与数据库原生策略一致，且每次执行记录策略版本。

### 10.3 VQR 权限

VQR 只保存参数化语义模板，不保存绕过权限的最终 SQL。每次命中 VQR 时：

1. 重新绑定当前语义版本；
2. 重新编译当前用户权限；
3. 重新进行成本检查；
4. 重新生成参数化 SQL；
5. 记录命中的 VQR 版本。

### 10.4 缓存隔离

缓存键至少包含：

```text
normalized_question
scenario_id
scenario_version
skill_id
skill_version
rule_id
rule_version
ontology_version
semantic_version
time_parser_version
copy_template_version
compiler_version
policy_version
domain_combination_policy_version
tenant_id
user_scope_hash
resolved_entity_hashes
session_query_context_hash
query_parameters
batch_size
display_transform_time_bucket
freshness_bucket
```

`resolved_entity_hashes`、`session_query_context_hash` 为哈希（不存明文）；权限变化、语义变更、策略变更、Scenario/Skill/Rule 版本变化、时间解析器变化、展示转换时间基准变化或数据新鲜度超过阈值时必须失效。不能使用仅包含问题文本的全局结果缓存。

### 10.5 敏感字段、存在性保护、派生标签与跨轮累计

敏感策略分四类对象：

1. **字段值**：脱敏后返回 / 拒绝查询 / 审批后查询；
2. **字段存在性**：对 `existence_sensitive: true` 的属性，用户无读权限时统一返回 `ATTRIBUTE_NOT_AVAILABLE`，不得以"无结果/空值"暗示存在性；
3. **派生标签/分群结果**：`sensitive_level: label` 的判定结果默认拒绝直接返回原始判定，可返回聚合分布或脱敏后的分群描述；需要返回个体判定时走审批；
4. **跨轮敏感累计**：同一 `session_id` 内对同一敏感字段/标签的逼近查询（如逐步缩小范围、多次差分）累计计数超阈值时，触发 `SENSITIVE_QUERY_SEQUENCE`，审批或拒答；计数器进入 `sensitive_query_counters`，跨会话清空。

聚合结果也需要评估小样本泄露、差分查询和重复查询推断风险。越权尝试、敏感字段请求、存在性探测、跨轮差分尝试必须完整审计。

## 11. VQR 运营治理

### 11.1 生命周期

```text
候选 -> 草稿 -> 自动校验 -> 人工审核 -> 发布 -> 监控 -> 失效/回滚
```

### 11.2 入库条件

必须同时满足：

1. DSL Schema 合法；
2. 语义资产、Rule、Skill、时间解析器绑定稳定；
3. Golden Query 或结果校验通过；
4. 在目标数据库实际执行成功；
5. 权限测试通过；
6. 结果确实回答声明的问题；
7. Owner、版本、数据新鲜度和失效条件齐全。

用户点赞只能增加候选优先级，不能直接触发发布。

### 11.3 自动失效

以下任一条件成立，VQR 自动转为失效或待复核：

- 依赖指标、维度、事件、属性、口径变体废弃；
- 语义版本发生不兼容变更；
- 权限策略或域组合策略变更；
- Golden Query 回归失败；
- 结果口径被用户持续纠正；
- 数据源表结构变化；
- 数据新鲜度超过声明上限；
- 依赖的 Scenario scope、frozen_calibers 或 `allowed_analysis_modes` 发生不兼容变更；
- 依赖的 Skill 版本、`params_schema_ref`、`required_capabilities`、`allowed_scenario_ids` 或 `approximation_of` 发生不兼容变更；
- 依赖的 Rule 版本、`input_dependencies` 或判定条件发生不兼容变更；
- 依赖的时间解析器模式或文案模板发生不兼容变更。

### 11.4 Skill/Rule 生命周期及 VQR/Skill 运行时重校验（权威表述）

Skill 与 Rule 均采用注册审核制：`draft → schema/安全校验 → 人工审核 → published → monitor → deprecated/rollback`。Scenario 引用 Skill 必须锁定 `skill_id + skill_version + params_schema_ref`；Metric 引用 Rule 必须锁定 `rule_id + rule_version`。未发布、已废弃、签名/校验失败或不兼容版本一律拒绝执行。

**VQR 命中或 Skill 执行时，运行时统一按以下步骤重校验：**

1. 重新绑定当前 `scenario_id + scenario_version`、`ontology_version`、`semantic_version`、`rule_version`、`time_parser_version`、`policy_version`、`domain_combination_policy_version`；
2. 重新校验 Skill 的 `skill_version`、`params_schema_ref`、`required_capabilities`、`allowed_scenario_ids`；
3. 若涉及 `boolean_rule`，重新校验 Rule 已发布且 `input_dependencies` 可用，按当前 `rule_version` 求值；
4. 重新校验口径变体属于主指标已发布变体；
5. 重新编译当前用户权限（含字段级、行级、存在性保护、标签敏感、跨域组合、累计敏感）；
6. 重新进行成本与资源检查；
7. 由确定性编译器重新生成参数化 SQL（走 8.1 全流程）；
8. 记录命中的 VQR/Skill/Rule 版本、时间解析器版本、文案模板版本与策略版本。

VQR 是查询模板，Skill 是能力单元，Rule 是判定口径；Scenario 可以引用前两者。Scenario 可声明 `default_vqr_ids`，但不得持有预编译 SQL，也不得让 VQR 绕过重编译。

### 11.5 用户口径 → 资产发布流程

用户在对话中给出的临时口径不得即时执行。引导流程：

1. 系统识别到临时口径（`CALIBER_UNDEFINED`）；
2. 若可降级回答，返回可验证部分并标注"非判定结论"；
3. 用户可发起"口径发布申请"，填写口径描述、Owner、测试样例；
4. 走 Rule/Metric 注册审核流程（5.4、5.9），审核通过后发布；
5. 发布后 Scenario/VQR 可通过新 Rule/Metric 引用；
6. 发布前，同类问题持续走"降级 + 引导"路径。

- 口径未定义/并列/变体不明（`CALIBER_UNDEFINED`、`CALIBER_AMBIGUOUS`）；
- Scenario 入口未命中/误入（`SCENARIO_AUTO_LOW_CONFIDENCE_FALLBACK`）；
- Scenario 手动指定无权/失效（`SCENARIO_MANUAL_UNAUTHORIZED`、`SCENARIO_DEPRECATED`）；
- Scenario scope 过窄或配置错误（`SCENARIO_SCOPE_VIOLATION`）；
- frozen_caliber 覆盖尝试（`SCENARIO_CALIBER_OVERRIDE`）；
- Analysis Mode 识别错误；
- Skill 路由错误（`SKILL_*`）；
- 指标与模式不匹配（`METRIC_MODE_NOT_ALLOWED`）；
- 属性不可用/存在性保护命中（`ATTRIBUTE_NOT_AVAILABLE`）；
- Rule 未发布/依赖断裂（`RULE_NOT_PUBLISHED`、`RULE_DEPENDENCY_BROKEN`）；
- 跨域组合（`CROSS_DOMAIN_NOT_ALLOWED`、`CROSS_DOMAIN_APPROVAL_REQUIRED`）；
- 累计敏感（`SENSITIVE_QUERY_SEQUENCE`）；
- 提示注入疑似（`PROMPT_INJECTION_SUSPECTED`）；
- 能力边界外（`OUT_OF_CAPABILITY`）；
- 意图未发现（`INTENT_UNDISCOVERED`）；
- 时间表达未解析（`TIME_EXPRESSION_UNRESOLVED`）；
- 近似降级（`MODE_APPROXIMATED`）；
- 用户纠正（`USER_REJECTED`）；
- 复合查询子查询失败；
- 多轮指代消解失败 / 上下文合并失败；
- 参数缺失；
- DSL 非法；
- 权限不足；
- Join 粒度冲突；
- SQL 编译失败；
- 数据库执行失败；
- 结果质量异常。

同类失败连续出现时触发对应动作：补充同义词/口语别名、修改资产、增加场景约束、增加本体对象、更新 Rule、更新 VQR、补充时间模式、补充文案模板或新增回归样本。失败看板可按 `scenario_entry_mode`、`query_shape`、`turn_type`、`is_composite` 下钻。

## 13. 零号实验和正式评测

### 13.1 零号冒烟实验

使用 20 道刻意覆盖关键链路的题目：

- 8 道核心普通取数（含至少 2 道 `lookup`：属性直查 + 布尔判定；至少 1 道 `lookup_batch`）；
- 4 道 Scenario 入口 + Analysis Mode 分析（含至少 1 道多轮会话沿用、至少 1 道复合意图拆分）；
- 4 道歧义、缺失信息、口径未定义/并列、意图不明（discovery）；
- 4 道权限、安全和拒答问题（至少 2 道手动指定无权/错误 Scenario；至少 1 道 `ATTRIBUTE_NOT_AVAILABLE` 存在性保护；至少 1 道能力边界 `OUT_OF_CAPABILITY` 或提示注入 `PROMPT_INJECTION_SUSPECTED`）。

目标是验证链路、评分规则、审计和安全阻断，不用于估计总体准确率。

**硬阻断条件**：出现越权成功、敏感数据泄露、存在性泄露、跨轮差分泄露、跨域组合违规或应拒答而执行，停止进入下一阶段。

### 13.2 正式评估集

建立并冻结 `dev`、`validation`、`test`、`challenge` 四个集合。题目按任务、难度、输入分布、风险类型和来源分层。建议正式验收至少 200 题；需要稳定的分层比较时扩大到 500 题以上。

每道题保存：

- 规范问题；
- 可接受 Intent Proposal 和最终 DSL（复合题为子查询序列）；
- 允许的 Scenario/Skill/Rule 与语义资产；
- 入口来源（`scenario_entry_mode`：inherit / manual / auto / cold_start / none）与目标 `scenario_id`；
- `turn_type`：`single` / `multi_turn_followup` / `multi_turn_incremental` / `correction`；
- `query_shape`：`aggregate` / `lookup_attribute` / `lookup_boolean` / `lookup_batch` / `composite` / `discovery` / `scenario_mode`；
- `risk_type`：`normal` / `prompt_injection` / `differential` / `cross_domain` / `existence_probe`；
- scope 边界、frozen_calibers 和预期的裁剪候选；
- 期望结果或结果规则；
- 正确澄清/拒答/引导条件与期望原因码；
- 澄清质量评分（人工）；
- 必错项和禁错项；
- 测试身份与权限范围。

主指标按 `test` 集合报告；`challenge` 单独报告；不合并计算。13.4 分层必须按 `scenario_entry_mode`、`turn_type`、`query_shape`、`risk_type` 分列。

### 13.3 对照和消融

至少比较：

1. 当前 DataAgent 基线；
2. 直接 NL2SQL 基线；
3. Text2DSL + 确定性编译器；
4. 加入 VQR；
5. 无 Scenario 的授权全域自由问数 vs 进入正确 Scenario 后的 scope 收窄；
6. 手动指定正确 Scenario vs 自动推荐正确 Scenario vs 自由问数 vs 冷启动点选；
7. 手动指定无权/错误 Scenario 的拒答正确率与越权成功率；
8. 加入 Analysis Mode/Skill 路由；
9. 加入 `lookup`（单实体/批量/布尔）vs 仅聚合模式；
10. 加入多轮 `resolved_entities` + `session_query_context` vs 无锚点重解析 vs 仅实体锚点；
11. 加入复合意图拆分 vs 仅答首个子问题；
12. 加入 discovery vs 直接拒答；
13. 加入能力边界说明 vs 普通拒答；
14. 加入提示注入检查点 vs 无检查点；
15. 加入跨轮累计敏感检测 vs 仅单次检测；
16. 加入跨域组合策略 vs 仅各域独立授权；
17. 加入受限模糊候选澄清 vs 仅精确/同义词；
18. 加入混合召回；
19. 加入 RLS 和安全策略。

新旧系统使用同一封存测试集进行配对比较。

### 13.4 指标和统计

主指标：

```text
任务成功率 = 完成所有必需项且无禁错项的题目数 / 总题数
```

同时报告：

- 按 `scenario_entry_mode`、`turn_type`、`query_shape`、`risk_type` 分层的任务成功率；
- 结果语义正确率；
- 正确澄清率、澄清质量评分；
- 正确拒答率、过度拒答率；
- discovery 点选率与后续成功率；
- 复合查询子查询成功率与整体成功率；
- 越权成功率（分进入方式、分 `query_shape`、分 `risk_type`，含存在性探测、跨轮差分、跨域组合）；
- 敏感数据泄露率；
- P95 延迟、成本和超时率。

报告样本数、分层样本数和 95% 置信区间。小样本使用 Wilson 或 Clopper-Pearson 区间。新旧系统对同一题目比较，可使用配对 bootstrap 或 McNemar 检验。

阈值必须在查看正式结果前冻结。采用“硬门槛 + 最小实际提升”，不能用总体平均分抵消安全硬失败。

### 13.5 评测通过条件

- 核心任务达到功能门槛；
- 相比现有基线达到预设百分点提升；
- 主要困难层（含 manual / auto / none / cold_start、`lookup`/`lookup_batch`/`boolean_rule`、多轮、复合、discovery、各 `risk_type`）没有不可接受的退化；
- P95 延迟和成本满足预算；
- 严重越权和敏感数据泄露为 0；
- 手动指定场景下严重越权成功率为 0；
- 存在性泄露成功率为 0；
- 跨轮差分泄露成功率为 0；
- 跨域组合违规成功率为 0；
- 评测结果可由版本和数据哈希复现；
- 失败样本进入回归集或有明确的豁免记录。

## 14. 分阶段实施路线

### 阶段零：现状基线与前置决策

**目标**：摸清 DataAgent 当前行为和安全边界，完成进入架构替换前的决策。

**交付物**：

- 现有 NL2SQL 运行基线和 20 题冒烟集；
- AgentScope 1.0.11 兼容性及目标版本迁移 PoC；
- 首发查询数据库、SQL 方言和该数据库的 RLS/安全视图方案；
- 语义/本体/规则/时间解析器/文案模板版本、DSL、权限上下文、审计接口契约；
- 配置与凭据风险整改记录；
- 正式评测指标和门槛草案；
- Scenario 启用时点决策；
- 多轮会话状态机决策：`resolved_entities`、`session_query_context` 存储位置、跨会话清理策略、与审计的联动方式；
- Rule 注册表决策：规则求值部署形态、版本与审计契约；
- 时间解析器决策：模式资产维护方式、时区来源优先级、解析器版本策略；
- 文案模板决策：模板维护流程、多语言键规划、禁止占位符校验；
- 语言范围确认：首发中文（含英文术语混说），多语言/方言列为后续；
- 域组合策略决策：哪些域组合允许/需审批/禁止；
- fail-closed 判据清单：无 `policy_version`、无 RLS 策略命中、无 `ontology_version` 绑定、无授权域子图、Scenario scope 加载失败、Rule 未发布、时间解析器版本缺失、文案模板缺失时一律拒答。

**退出条件**：负责人批准首发数据库和权限边界；迁移决策有证据；正式评测门槛冻结；配置审查确认真实数据测试前的 fail-closed 条件；Scenario 启用时点、会话状态机、Rule 注册表、时间解析器、文案模板、语言范围、域组合策略已记录。

### 阶段一：本体 + 语义 + DSL 确定性查询纵切（含 lookup 最小闭环）

**目标**：以一个受控业务域，完成真正本体驱动的普通问数与最小直查闭环，替换自由 SQL 工具链。

**交付物**：

- 本体 Class/Property/Relation/Constraint/Mapping 元模型与版本化发布（含 `lookup_projectable`、`existence_sensitive`、`display_hints`、口语/拼音别名）；
- Customer、Order、OrderItem、Product、Event、Channel 首发本体样例（含 5.6 全部 relation_id、`Customer.email` PII、`Customer.register_time` 展示提示）；
- 本体概念消歧、有限关系路径规划与澄清机制（澄清四要素）；
- `ontology_version` + `semantic_version` 的类型化 DSL Schema（含 `attributes`、`display_transforms`、`lookup` 最小形态与 `lookup_batch`）；
- `lookup` Analysis Mode 与 `skill.entity_lookup`（单实体 + 批量）上线；
- `boolean_rule` Metric 与 Rule 注册中心最小闭环（至少 1 条 Rule）；
- 口径变体最小闭环（至少 1 个变体）；
- 时间解析器最小闭环（至少 3 个时间模式：上个月、上季度、近 7 天）；
- 文案模板服务最小闭环（原因码→模板映射，禁止占位符校验）；
- 本体路径到 Model/Join Path/Metric/Dimension 的映射器；
- 粒度与关系基数校验、确定性参数化 SQL 编译器；
- 数据域/字段/行权限接入，数据库级安全边界；
- PII 字段裁剪、存在性保护、`ATTRIBUTE_NOT_AVAILABLE` 验收；
- 批量 lookup 逐行差异保护验收；
- dry-plan/dry-run、成本约束和完整审计；
- 新旧查询链路的切换和回滚方案；
- 若阶段零决定阶段一启用 Scenario：单 Scenario 资产、入口路由、scope 裁剪、内置 Skill 绑定。

**退出条件**：LLM 无法通过工具提交自由 SQL 或绝对日期；本体路径和编译 SQL 可追溯；Golden Query 通过；未授权概念/关系/字段/行访问全部拒绝；`lookup` 单实体/批量/布尔判定闭环通过；口径变体与时间解析闭环通过；存在性泄露与批量差异泄露为 0；安全测试无越权。

### 阶段二：VQR 与语义运营闭环

**目标**：安全复用稳定查询并持续维护本体和语义质量。

**交付物**：

- VQR 生命周期与人工审核；
- VQR 绑定本体、语义、编译器、Scenario/Skill/Rule/时间解析器/文案模板和策略版本；
- 当前用户权限重编译、缓存隔离、失效和回滚；
- 本体/语义/规则/时间模式/文案变更影响分析；
- 失败看板、纠正样本和 Golden 回归集；
- 资产 Owner、审批人和发布流程；
- 用户口径 → 资产发布流程（11.5）入口。

**退出条件**：VQR 不绕过本体路径、权限或成本校验；不兼容资产变更能阻断发布或使依赖模板失效。

### 阶段三：Analysis Mode/Skill 构造器 + Scenario 资产化 + 多轮会话 + 复合意图 + 对抗防线

**目标**：并行工作流：(a) 内置 Analysis Mode 构造器；(b) Scenario 资产化与入口路由/冷启动；(c) 多轮会话与查询上下文；(d) 复合意图拆分；(e) 对抗防线（注入、跨轮差分、跨域组合、能力边界、discovery）。

**交付物**：

- (a) 按顺序：同环比 → 漏斗 → 留存 → 简单归因；每个独立完成口径契约、DSL Schema、确定性构造器、Golden Query、边界测试和性能验收；
- (a) 每个 Skill 完成注册、审核、参数 Schema、`required_capabilities`、`allowed_scenario_ids`、`approximation_of` 和实现版本；
- (b) Scenario 资产模型、入口路由（inherit/manual/auto/cold_start/none）、scope 裁剪、frozen_calibers、Skill 绑定、冷启动地图上线；
- (b) Scenario 发布/版本/失效/回滚流程与依赖资产影响分析；
- (c) 会话状态机、`resolved_entities`、`session_query_context`、增量合并、Scenario 沿用与退出、纠正回退；
- (d) 复合意图拆分子查询序列、上下文继承、结果隔离组装、部分失败处理；
- (e) Proposal 来源完整性校验、身份不可覆盖、跨轮累计敏感检测、跨域组合策略、能力边界拒答、discovery 引导式发现、近似降级声明。

**退出条件**：(a) 每个已发布 Analysis Mode/Skill 达到门槛；(b) 自定义 Scenario 可不改编译器上线，scope 越界被正确拒绝；(c) 多轮指代与增量合并达标、跨会话不串号、纠正可回退；(d) 复合查询子查询独立编译、结果隔离、部分失败可解释；(e) 注入疑似拦截、跨轮差分与跨域组合零泄露、能力边界拒答正确、discovery 点选后可继续。

### 阶段四：高级召回与本体扩展

**目标**：以真实失败样本证明需要后再增加检索和关系能力。

**交付物**：图谱多跳召回、向量 + BM25、rerank、实体歧义专项评测、本体扩展治理、口语/拼音别名扩充。仅当精确匹配、词典、受限模糊候选和有限路径未能满足召回时投入。

**退出条件**：相对无高级召回的配对评测证明收益，且误召回、延迟和安全指标不退化。

### 阶段五：外部资产交换和规模化

**目标**：建立迁移和规模化能力。

**交付物**：Ossie `0.1.1` 导出器、版本隔离、多租户资源队列、SLO、灾备和规模容量测试、多语言文案模板扩展。

**退出条件**：单域核心链路稳定且出现明确的移植/规模需求。

## 15. 向量检索选型

首发规模是几千到几万条语义/本体资产，默认先用结构化索引、同义词词典、口语/拼音别名、数据库全文检索和有限本体路径，不为“需要向量”而先新增独立存储。

只有当 M5 评测证明模糊召回有明确收益时，才引入向量检索：

- 若部署已使用 PostgreSQL，可评估复用 pgvector；
- 10 万–100 万档优先评估 pgvector + partial index；
- HNSW 图构建受 `maintenance_work_mem` 和可用内存影响；
- 过滤和多租户场景可评估 partial index 或分区；
- 规模达到千万级时再规划量化、分区和独立索引构建窗口；
- 不引用无一手来源的 Elasticsearch 性能对比。

无论采用何种检索，向量分数只能用于候选召回，不能覆盖授权过滤、本体类型/关系约束或确定性路径规划；受限模糊候选同理，只作澄清候选。

## 17. 主要风险和应对

| 风险 | 后果 | 应对 |
|---|---|---|
| DSL 允许自由物理结构 | 越权、不可审计、Join 错误 | 只允许资产 ID，禁止自由表名和 Join |
| RLS 只在应用层注入 | 漏径导致越权 | 数据库 RLS/安全视图作为最终边界 |
| 指标粒度不清 | 数值稳定但业务错误 | 资产声明粒度、Golden Query、Join 检查 |
| Analysis Mode / Skill 口径不完整 | 同一问题结果不一致 | 为每个 Analysis Mode / Skill 建立正式语义契约 |
| Scenario scope 配置错误或过窄 | 误拒答、体验差 | scope 变更走审核；失败看板监控 |
| 手动指定无权场景被静默降级 | 绕过场景边界 | 7.4 硬规则：拒答不降级 |
| frozen_calibers 被覆盖 | 口径漂移 | 6.2 强制校验 |

## 19. 最终验收标准

系统只有同时满足以下条件，才允许进入真实用户试运行：

1. **语义正确性**：核心任务和主要 Analysis Mode/Skill 达到预设任务成功率；
2. **确定性**：同一 DSL、Scenario/Skill/Rule/时间解析器/文案模板/本体/语义/策略版本、上下文和数据快照下，编译结果可复现；NL→Intent Proposal→DSL 的稳定性不在此承诺内，由"意图一致率"单独度量；
3. **权限安全**：越权查询、敏感数据泄露、存在性泄露、跨轮差分泄露、跨域组合违规、提示注入成功和应拒答而执行均为 0，含手动指定 Scenario 下的越权尝试；
4. **可审计性**：每次请求可以追溯到问题、资产、DSL、SQL、策略、Scenario/Skill/Rule/时间解析器/文案模板版本、入口方式、会话状态、上下文增量、子查询关系和原因码；
5. **可运营性**：失败样本可分类，Scenario、Skill、Rule、VQR、时间模式、文案模板和语义资产可审核、回滚和失效；
6. **工程可用性**：P95 延迟、成本、超时和并发满足预设 SLO；
7. **评测可信**：正式测试集冻结，结果包含按 `scenario_entry_mode`、`turn_type`、`query_shape`、`risk_type` 的分层统计、置信区间和失败案例；
8. **版本可复现**：模型、Prompt、Intent Proposal、最终 DSL、本体发布清单、Scenario/Skill/Rule/时间解析器/文案模板版本、编译器、策略和数据版本均可定位。

## 20. 结论

本方案的核心不是让 LLM 更擅长写 SQL，而是让版本化业务本体承担实体指代、业务关系路径、属性投影和查询约束，让 LLM 只识别意图并提出合法概念候选，再由本体规划器与确定性编译器完成关系路径、指标口径、判定规则、口径变体、时间解析、分析模式逻辑、权限过滤和 SQL 生成。

系统的可落地性取决于以下硬契约：

- 本体必须参与概念解析、关系规划、属性投影、DSL、编译、权限和审计，而不是只做实体目录；
- Analysis Mode 是封闭编译器枚举；Scenario 只收窄上下文和路由；Skill 是注册审核制能力单元；Rule 是判定口径唯一载体；Session Context 由服务端维护；五者不可混用；
- 简单问题必须有最小路径：`lookup` 单实体/批量、`attribute` 投影、`boolean_rule` 判定、受控展示转换，不能被迫套聚合范式；
- 复合意图必须拆为子查询序列：独立编译、独立授权、结果隔离，不合并 SQL、不共享中间结果；
- 多轮会话必须有服务端锚点与查询上下文：绑定 user+tenant+session，增量修改每轮重编译，跨会话不串号，纠正可回退；
- 用户提问谱系必须全覆盖：意图不明走 discovery，能力边界外显式说明，冷启动有地图，口语/拼音有受限模糊澄清；
- 口径变体、相对时间、否定/排除必须有确定性载体，LLM 不得现场定义或直接输出绝对日期；
- DSL 不能表达自由物理结构，LLM 不决定物理 Join、SQL、判定口径、口径变体或绝对日期；
- Scenario 与用户授权取交集，不能授权扩权；手动指定无权场景拒答不降级；frozen_calibers 不得被覆盖；
- Skill、Rule、VQR 均须按当前资产和权限重新验证并由确定性编译器生成 SQL；
- 字段存在性、派生标签、跨轮差分、跨域组合、提示注入属于安全边界，必须统一文案、脱敏、审批或拦截；
- 权限必须有首发数据库明确实现的最终边界；
- 每个 Analysis Mode/Skill 必须先定义业务语义再实现；
- 评测必须把 20 题冒烟与正式分层验收分开，按 `scenario_entry_mode`、`turn_type`、`query_shape`、`risk_type` 分层。

复审结论：本方案在本体职责、端到端查询闭环、最小查询路径、复合意图、多轮会话、口径变体、时间解析、判定规则、对抗防线、能力边界、DSL 边界、权限边界、Scenario/Skill 建模和实施依赖已补齐后，可作为架构定版；数据库选择、AgentScope 迁移目标版本、评测数值门槛、会话存储形态、Rule 求值部署形态、时间解析器形态、文案模板流程、语言范围扩展节奏和实际工作量仍需在阶段零由项目负责人基于部署环境确认，不在架构文档中伪造已决结论。

DataAgent 应按“现状与安全基线 → 本体/语义/DSL/确定性查询纵切（含 `lookup` 最小闭环、口径变体、时间解析、文案模板与最小 Scenario，若阶段零决定启用）→ VQR 与运营 → Analysis Mode/Skill 构造器 + Scenario 资产化 + 多轮会话 + 复合意图 + 对抗防线 → 高级召回 → 资产交换与规模化”的顺序推进。本体从阶段一开始参与解析、规划和编译，逐阶段验收，避免一次性建设不可验证的大系统。
