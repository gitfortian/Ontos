# 智能问数系统技术选型方案（v1.1）

**依据**：v1.4《基于本体语义的智能问数系统》架构方案（目标态契约）  
**审核输入**：`docs/review-ontology-query-plan-v1.4.md`、`docs/review-tech-selection-v1.0.md`  
**日期**：2026-11-06  
**状态**：待评审，供阶段零决策冻结  
**修订**：2026-11-06 一次复核（补部署形态锁定、RLS 连接池配置、跨轮差分规则、PoC #7/#8，修正交叉引用）；同日二次复核（两层计数器分工、新清单生效延迟、`risk` 窗口滑动、PoC #9、移出多服务拆分待决、标注 PoC 编号）；同日**阶段零决策冻结**：§11 第 1 项 = PostgreSQL 18、第 2 项 = AgentScope Java 2.1.0-BETA1、第 7 项 = 复用框架观测能力（全文版本同步）；同日**前端路线冻结**：React 首选、主路线 shadcn/ui + CopilotKit Headless（附录 A，直连 PoC 仍待验证）；同日**后端版本修正**：Spring Boot 由 3.x 修正为 **4.0.x（≥4.0.3，当前工程 4.0.9）**、运行时 JDK 锁定 **21**，全文同步 §1.2、§2、§7 PoC #3、§9、§10 台账与 §11 第 2 项  
**适用底座**：greenfield 目标架构，**独立新建系统**。v1.4 不预设复用 DataAgent 现有代码与选型；与存量系统的迁移、双轨切换、工具收敛、前端改造属于《阶段零/一实施规格》，不在本文档范围。**部署形态由 §1.2 锁定，阶段零仅做验证**：形态本身不是待决项，阶段零只验证并冻结副本数、扩缩容与一致性压测口径。

**原则**（按优先级）：

1. **契约驱动，而非组件驱动** —— 先满足 v1.4 的确定性、可复现、fail-closed、版本链、数据库层最终边界，再选组件；
2. **少一个组件优于多一个组件** —— 每新增一个依赖、扩展或运行时，必须证明它解决了 v1.4 中一个真实且现有手段解决不了的约束；
3. 能复用不造轮子；Java 生态优先；存储收敛 PostgreSQL；
4. 自研仅限核心差异化逻辑；
5. 不伪造已决结论：未锁定的数值、版本与形态一律进「待决事项」，由阶段零冻结。

### 1.2.1 首发部署形态（锁定）

| 维度         | 锁定值                                                     | 说明                                                       |
| ---------- | ------------------------------------------------------- | -------------------------------------------------------- |
| 单体 vs 多服务  | **单体 Spring Boot 应用**，按 §3 组件边界做模块化分包（身份/本体/编译器/执行器/审计） | 首发不拆多服务；**多服务拆分不属于本阶段待决项**，若未来触发须作为独立演进提案重新走架构评审，不在本文档范围 |
| 单副本 vs 多副本 | 开发/沙箱单副本；**生产 ≥2 副本无状态水平扩展**                            | 权威状态全部外置到 System DB，进程内只持有不可变发布快照                        |
| 对外协议       | **REST**（管理 / 查询 / 审批 API）+ **AG-UI over SSE**（流式类型化事件） | 内部不做 gRPC / 服务网格；未来外部集成原则见 §11 第 11 项                    |
| 会话亲和       | **不需要粘性会话**                                             | 会话权威状态在 PG，任意副本可处理任意 turn                                |

> **「必须复用、不重复造轮子」的边界**（§11 第 7 项冻结）：复用限于框架**库内能力** —— OTel 埋点、`streamEvents()` 类型化事件流、AG-UI 协议、Session 持久化、三态权限、Studio 作为开发/调试观测端、Spring Boot Actuator 健康检查；不自研 SSE 事件模型、不自研 trace 埋点、不自研审批前端通道。**不引入 AgentScope Service 独立控制面 / Go aistiod / Helm 部署形态**：2.1.0-BETA1 新增的 Docker / Compose / Helm / CLI / Runtime Host 属于控制面部署能力，与本节「单体 Spring Boot 应用」锁定冲突并额外增加运维组件。**业务审计仍按 v1.4 12 章独立落 PG `audit_log` 表**（需持久化、按权限访问、可回放），Studio 看板不可替代 —— 这不是重复造轮子，是合规必需。

**多副本一致性策略**（三项均为硬约束）：

1. **`published_snapshot` 加载**：表只 INSERT、不可变；每个副本启动时按 `manifest_id + content_hash` 从 PG 加载并校验 hash；运行时请求固定到单一清单，**不做副本间广播、不做缓存协商**，新清单靠请求级绑定生效而非推送；`/actuator/manifest` 暴露当前 hash 供健康检查横向比对，hash 不一致或加载失败的副本**拒绝服务（fail-closed）**。

   **新清单生效语义（可复现的分布式边界）**：
   - **业务请求必须携带 `manifest_id`**，由入口层从「当前生效清单」统一注入，**不允许业务请求缺省**（缺省会导致不同副本各用当前清单，产生 `relation_path` 漂移，破坏第 19 章可复现）；仅非业务探针可省略。
   - 副本若未加载请求所带的 `manifest_id`，**fail-closed 拒绝服务，不降级到旧清单**，也不临时回源加载后再接受该业务请求。
   - 运维发布新清单后，须等待该 `manifest_id` 出现在**全部**副本的 `/actuator/manifest` 中，方可切换入口流量；此前入口继续注入旧 `manifest_id`，两清单并存期间结果各自可复现、互不影响。
   - 该生效延迟窗口由健康检查周期决定，**建议 ≤ 30 秒**（阶段零冻结，见 §11 第 10 项），并写入运维手册；切换流量的检查命令与回滚动作同册记录。
2. **`session_state` 读写**：不落应用内存；统一 PG 表事务读写，唯一键 `(tenant_id, user_id, session_id)`，用 `turn_index` 作乐观锁（`UPDATE ... WHERE turn_index = ?`，影响行数为 0 即重试/澄清），保证同一会话并发 turn 不丢更新；跨副本无需同步，不要求会话亲和。
3. **`sensitive_query_event` 计数**：禁止进程内或本地缓存计数；所有事件在同一事务内落 PG，窗口聚合用事务内 SQL 判定（§4.8），跨副本天然一致；计数器哈希化后写入审计 `sensitive_query_counters_delta`。

> 阶段零需验证与冻结的只是：生产副本数、扩缩容策略、自建/托管选择、PgBouncer 池容量与超时、§1.2.1 三项一致性策略的压测口径，以及上文的**新清单生效延迟窗口** —— 见 §11 第 10 项。**形态本身已锁定，不是待决项。**

## 4. 关键设计决策

### 4.1 最终权限边界：PG 原生 RLS（v1.4 4.1、10.1、10.2）

所有 Query DS 业务表启用并**强制** RLS，应用使用**非 owner、非 superuser、非 BYPASSRLS** 的只读角色：

```sql
ALTER TABLE commerce.orders ENABLE ROW LEVEL SECURITY;
ALTER TABLE commerce.orders FORCE ROW LEVEL SECURITY;

CREATE POLICY orders_tenant_isolation ON commerce.orders
  FOR SELECT TO app_query_ro
  USING (
    tenant_id = current_setting('app.tenant_id', true)::bigint
    AND domain_id = ANY (current_setting('app.allowed_domains', true)::text[])
  );
```

强制约束：

1. 每个事务开头、在**同一连接、同一事务内**执行 `SET LOCAL app.tenant_id = ...`、`SET LOCAL app.allowed_domains = ...`；禁止普通 `SET`（PgBouncer/Hikari 事务池下会串租户）。
2. `current_setting(..., true)` 未设置时返回 NULL，策略求值为零行；应用层仍须在事务开始**显式断言上下文已签发**，缺失即 fail-closed 拒答，不依赖「零行」这种静默失败。
3. `tenant_id` / `domain_id` 建索引；`EXPLAIN` 中确认 RLS 谓词命中索引。
4. 字段级与存在性保护用 `security_barrier` 视图；`label` 型判定结果走脱敏视图；**不使用 `SECURITY DEFINER`** 视图或函数绕过 RLS。
5. `policy_version` 与 `domain_combination_policy_version` 随发布清单冻结，每次执行写入审计。
6. 运维旁路角色 `BYPASSRLS` 独立、默认不授予应用，仅用于迁移与应急，且操作单独审计。
7. **连接池配置与静态检查**（下节展开）为强制项，`pool_mode`、重置语句、事务边界、禁止裸 `SET`、健康检查五项缺一不可。

#### 4.1.1 PgBouncer / Hikari 具体配置（阶段零验证后冻结）

```ini
# pgbouncer.ini —— Query DS 连接池
pool_mode = transaction          ; 必须；session 模式会泄漏 SET 上下文
server_reset_query = DISCARD ALL ; 连接归还时清理 session 级状态
```

```yaml
# 应用侧 Query DS 数据源
spring:
  datasource:
    hikari:
      auto-commit: false         # 所有查询必须运行在显式事务内
      connection-init-sql: "SELECT 1"  # 不做任何 SET；上下文由 RlsContextTemplate 注入
```


| 项              | 配置                                                                                                                                                      | 作用 / 校验点                                                                                                                 |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| 池模式            | `pool_mode = transaction`                                                                                                                               | 事务结束后连接即归还；配合 `SET LOCAL` 保证上下文不出事务                                                                                      |
| 重置语句           | `server_reset_query = DISCARD ALL`                                                                                                                      | 防御性清理 session 级残留（如误用普通 `SET`）。它执行 `RESET ALL` / `DEALLOCATE ALL` 等，应用须容忍 prepared statement 失效；**它是兜底，不替代 `SET LOCAL`** |
| 事务边界           | `autoCommit = false` + Spring `@Transactional`                                                                                                          | 保证 `SET LOCAL` 与业务 SQL 在**同一连接、同一事务**内；禁止 autocommit 下的单条查询                                                              |
| 禁止裸 `SET` 静态检查 | CI 用 ArchUnit / Checkstyle 自定义规则扫描源码与 SQL 字面量中的 `SET `（不含 `SET LOCAL`）、`Statement.execute("set...")`；所有上下文注入唯一下沉到 `RlsContextTemplate`                  | 命中即构建失败；防止有人在事务外写 `SET app.tenant_id` 造成跨请求串号                                                                            |
| 连接健康检查         | 归还断言 `current_setting('app.tenant_id', true) IS NULL`；启动探针校验 `pool_mode`、`server_reset_query`、当前角色非 owner / 非 `BYPASSRLS`、目标表 `forcerowsecurity = true` | 任一不符即 **fail-closed 拒绝启动**；探针结果进审计                                                                                       |
| 池容量            | `default_pool_size` / `max_client_conn` / 连接超时                                                                                                          | 阶段零按并发目标冻结，与 §4.4 并发队列联动                                                                                                 |

> 注意：`SET LOCAL` 在事务提交/回滚时自动失效，`DISCARD ALL` 处理的是连接归还时的 session 级状态。两者是互补的两道防线，不能只配其一。

### 4.2 资产发布流水线：把「可复现」做成结构保证

```
Git（唯一可发布真源，草稿态）
  └─ CI：JSON Schema 结构校验
       └─ OntologyPublishValidator：引用完整性 / 基数 / 映射一致性 / 唯一键
            / 跨域边授权 / 正反向 Golden Path 样例 / 版本兼容判定
            └─ 生成不可变发布清单（含 content_hash 与全部版本号）
                 ├─ INSERT 到 PG published_snapshot（只追加，不可 UPDATE）
                 └─ 应用加载为进程内不可变快照（邻接表 + 资产索引 + 策略表 + 文案模板）
                      └─ 运行时按 request 固定到单一 manifest_id
```

运行时请求固定到一个已发布清单，禁止混用未兼容版本；`manifest_id + content_hash` 进入 DSL、审计与缓存键。任何资产变更都产生新清单，旧清单保持可读以支持回放。**管理界面只提交变更单，不直写运行时表**，从而保证 v1.4「草稿不得被查询运行时读取」。

### 4.3 确定性编译器：jOOQ DSL 构建，JSqlParser 辅助

| 子能力                                  | 实现                                                                                                               |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------- |
| SELECT 结构、绑定参数、PG 方言渲染               | `DSL.using(SQLDialect.POSTGRES)` 的**无代码生成模式**：`table(name(...))` / `field(name(...))`，避免与用户动态接入的 Model schema 冲突 |
| 规范化 SQL + 参数列表 + 编译证明摘要              | 自研（v1.4 8.1 第 18 步）                                                                                              |
| Join Path 展开、粒度安全校验、权限条件合并、口径变体、规则求值 | 自研                                                                                                               |
| 已有 SQL 片段合法性、表/列血缘提取、副作用语句拦截         | JSqlParser（仅解析，不构建）                                                                                              |
| DSL Schema 校验                        | JSON Schema + 自研业务校验（ID 在 scope 内、候选集 `context_hash`、ID/值/操作符/数量四维完整性）                                           |
| 成本闸门                                 | `EXPLAIN (FORMAT JSON)` 的 `Total Cost` / `Plan Rows`（**相对值，需与实测扫描量校准**）                                          |

> jOOQ 开源版以 ASL 2.0 授权、覆盖 PostgreSQL 等开源数据库。若未来 Query DS 扩展到 Oracle / SQL Server 等商业库，需商业许可或退回自研 AST 渲染层（§9 风险）。

**PG 单方言的收益**：递归 CTE 与窗口函数可直接实现 9.3–9.6 的漏斗、留存、同环比、归因口径契约，不再受 MySQL 5.7 类语法限制；这条应作为锁定 PG 的正式论据写入立项材料。

### 4.4 成本与资源控制（v1.4 8.4 落地）

- 每子查询独立设置 `statement_timeout`、`lock_timeout`、`idle_in_transaction_session_timeout`；
- 编译期 `EXPLAIN (FORMAT JSON)` 成本闸门 + 最大扫描行数估算；
- 编译器注入 `LIMIT`，配合流式读取控制最大返回行数；
- `pg_cancel_backend()` / `pg_terminate_backend()` 实现取消；`pg_stat_activity` / `pg_stat_statements` 支撑并发队列与慢查询看板；
- 禁止副作用语句（JSqlParser 解析校验 + 只读 DB 角色双保险）；
- 复合查询按子查询数量与总量双重控制；
- 失败分类：语义、权限、成本、数据库、数据质量、系统故障。

### 4.5 检索瀑布（v1.4 7.5）

1. 认证层按 user / tenant / 数据域授权过滤，并做跨域组合检查；
2. Scenario Entry Router 确认 scope 或回退自由问数；
3. 已确认 Scenario 时按 `ontology_scope` / `semantic_scope` / `allowed_analysis_modes` / `skills[]` 裁剪候选；
4. **精确结构化匹配**（`class_id` / `property_id` / 同义词、缩写、口语别名的唯一索引）；
5. **中文与模糊召回**：应用侧分词写入 `asset_candidate.search_tsv`（`tsvector` 生成列 + GIN），`pg_trgm` 处理编辑距离、子串与拼音近似；**结果仅作澄清候选，不进 DSL**；
6. 有限本体关系规划（进程内快照）；
7. VQR 候选匹配（命中后按 11.4 重编译）；
8. M5 之后、且配对评测证明收益时，才启用 pgvector + rerank；向量分数不得覆盖授权过滤与确定性路径规划。

中文分词的**自定义词典与 Synonym 资产同源维护**（含 `colloquial_aliases`、`pinyin_aliases`），不另建 PG 侧词典，避免两份真源漂移。示例：

```sql
ALTER TABLE asset_candidate
  ADD COLUMN search_tsv tsvector
  GENERATED ALWAYS AS (to_tsvector('simple', coalesce(tokens_text, ''))) STORED;
CREATE INDEX idx_asset_fts  ON asset_candidate USING GIN (search_tsv);
CREATE INDEX idx_asset_trgm ON asset_candidate USING GIN (display_name gin_trgm_ops);
CREATE INDEX idx_asset_py   ON asset_candidate USING GIN (pinyin_text gin_trgm_ops);
```

`tokens_text` 由应用侧分词器写入；`to_tsvector(regconfig, text)` 为 IMMUTABLE，可用于生成列。

### 4.6 路径规划与复合意图

进程内不可变快照加载为邻接表（JGraphT 或自研 BFS），与 `ontology_version` 原子绑定：

- 7.3 规划器在 Java 内完成类型、方向、基数、有效时间、授权域、Scenario scope、成本、Golden Path 优先级与并列澄清判定；代价函数版本化；
- 路径终点集合覆盖 DSL 中所有 `metrics` / `dimensions` / `attributes` / `analysis_params` 引用实体；
- 复合意图的 `depends_on` 用 JGraphT 拓扑排序决定子查询顺序，每个子查询独立走 DSL 校验、独立编译、独立授权、结果隔离组装，不合并 SQL、不共享中间结果；
- 结果依赖与上下文依赖分开处理（结果依赖需显式声明，且以授权+脱敏后的子结果作输入）。

**为什么不放数据库图扩展**：本体图是几百节点、`max_path_hops: 3` 的元数据图；内存 BFS 微秒级、零 DB 往返；派生图索引的刷新时机会与发布快照产生不一致，直接违反第 19 章「同一 DSL + 版本集下编译结果可复现」。

### 4.7 策略、审批与权威会话状态

|                                                                                       |                   |                                                                                                                                                                                    |
| ------------------------------------------------------------------------------------- | ----------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **域组合策略**（v1.4 10.1）：版本化 `domain_combination_policy` 表，\`(domain_a, domain_b) → allow | approval_required | deny`，默认「各自授权即可组合」；发布时冻结为内存快照，Java 判定返回 `CROSS_DOMAIN\_*\` 原因码，策略版本与判定结果进审计。若未来策略复杂到需要规则语言，评估 **OPA 独立服务 REST**（官方支持、decision log 完整）或 Cedar 类确定性授权引擎；**不使用 Rego→Wasm→Chicory 链**。 |

|                                                              |          |         |                                                                                                                     |
| ------------------------------------------------------------ | -------- | ------- | ------------------------------------------------------------------------------------------------------------------- |
| **审批工作流**：独立 `approval_request` 表 + 状态机（\`pending → approved | rejected | expired | cancelled`），含审批人、SLA、**超时默认拒绝**、撤销、审批结论入审计。AgentScope 的 `RequireExternalExecutionEvent\` 仅作为「等待前端回传确认」的同步通道，不是审批后端。 |

**会话权威状态**：独立 `session_state` 表，唯一键 `(tenant_id, user_id, session_id)`，存 `resolved_entities`、`session_query_context`、`session_scenario_state`、`turn_index`、`context_delta`；服务端状态机维护，绑定身份、跨会话清空、每轮增量修改后重走完整校验。对 Tool 只暴露只读最小投影，**绝不从 Agent Session / AgentState 反序列化权威状态**。AgentScope Session（PG 后端扩展）只存对话历史与 checkpoint。

**交互层**：用 AgentScope **2.1.0-BETA1** 的 `streamEvents()`（v2 系列 32 类类型化事件）+ AG-UI 协议下发澄清四要素、discovery 候选、冷启动地图、审批入口、复合子结果、纠正回退与原因码渲染；三态权限（`ALLOW / CONFIRM / REJECT`）承接工具白名单与「近似降级征得同意」。这一层替代自定义 SSE 事件模型，显著减少自研量。

**观测复用（§11 第 7 项冻结）**：trace / metrics / logs 直接复用框架 OTel 埋点与 Studio 观测端，健康检查复用 Spring Boot Actuator，**不自研 SSE 协议、不自研埋点、不自研审批前端通道**；复用边界与排除项见 §1.2.1。**业务审计仍独立落 PG `audit_log`**（原始问题、DSL、SQL、版本链、原因码、子查询关系、dry-plan/dry-run 附件），按 v1.4 12 章要求持久化、按权限访问、可回放 —— Studio 看板是观测视图，不承担审计职责。

### 4.8 跨轮敏感累计与差分规则框架（v1.4 10.5）

`sensitive_query_event` 表每请求一行：`request_id / user_id / tenant_id / session_id / sensitive_key / sensitivity_class / scope_hash / filters_hash / result_cardinality / pattern_tag / occurred_at / reason_code / context_delta`。事务内写入 + 窗口聚合判定，全部落 PG，禁止进程内计数缓存（§1.2.1）。

> **与 v1.4 的一致性及两层分工**（消除「两个计数器如何合并」的歧义）：
>
> - `sensitive_query_counters`（**session 级**）按 7.1 / 10.5 **跨会话清空**，负责**同一会话内的逼近判定**，超阈值按 v1.4 原文触发 `SENSITIVE_QUERY_SEQUENCE` → 审批或拒答；
> - **user+tenant 级滑动窗口不清空**，负责**跨会话规避判定**（每轮开新 `session_id` 仍可累计），修补 v1.4 未覆盖的规避路径；
> - **两层都参与风控判定，但各自独立计算 `risk`、各自与 `T` 比较，互不累加**；**任一层超阈值即触发 §4.8.3 动作**（OR 关系，取动作档位较高者）。不累加可避免切换会话时 `risk` 跳变，同时**完整保留 v1.4 10.5 的会话内判定语义**；
> - 「本会话已查询敏感字段 N 次」这类**交互反馈**只读取 session 级计数，不参与判定合并，也不写入风控结论。

#### 4.8.1 窗口长度与 `sensitive_key` 分层（建议初值，阶段零冻结）

`sensitive_key = {asset_id}#{sensitivity_class}`，按资产敏感级别分层：

| 层  | 对象                             | 示例                           | session 级窗口 | user+tenant 级滑动窗口 | 累计阈值 `T` |
| -- | ------------------------------ | ---------------------------- | ----------- | ----------------- | -------- |
| L0 | `public` / `internal` 非敏感      | 普通维度                         | 不计数         | 不计数               | —        |
| L1 | `PII` 字段值                      | `ontology.Customer.email`    | 会话生命周期      | **24h**           | 8        |
| L2 | `existence_sensitive: true` 属性 | 邮箱 / 手机号存在性                  | 会话生命周期      | **24h**           | 4        |
| L3 | `label` 型派生判定 / 分群             | `metric.high_value_customer` | 会话生命周期      | **7d**            | 3        |

事件保留期建议 **90 天**（合规保留期由阶段零确认）；计数器哈希化后写入审计 `sensitive_query_counters_delta`。**`T` 是单层阈值**：session 层与 user+tenant 层各自用自己的 `risk` 与同一个 `T` 比较，两层不合并、不累加。

#### 4.8.2 逼近模式判定（可判定规则）

两层按各自取数键独立取事件序列、逐请求打 `pattern_tag`（每请求只取最高权重，避免重复放大）：

- **user+tenant 层**：按 `(user_id, tenant_id, sensitive_key)` + 表内滑动窗口取序列；
- **session 层**：按 `(tenant_id, user_id, session_id, sensitive_key)` + 会话生命周期取序列。

两层使用**同一套** `pattern_tag` 判定规则与权重，各自算出自己的 `risk`。

| 权重 | 标记                   | 判定条件                                                                           |
| -- | -------------------- | ------------------------------------------------------------------------------ |
| 1  | `plain`              | 普通敏感字段访问                                                                       |
| 2  | `narrowing_sequence` | 连续 ≥3 次请求的 `filters_hash` 单调变化且 `result_cardinality` 非增；或相邻两次仅变更一个过滤条件（逐步缩小范围） |
| 3  | `differential_pair`  | 两次请求的 `filters` 集合差恰为 1，且 `result_cardinality` 差 < `k`（建议 `k=5`），构成差分对         |
| 3  | `existence_probe`    | 对同一 `sensitive_key` 以不同实体标识重复请求、且结果统一返回「不可用」（对齐 v1.4 8.2 存在性保护与批量差异保护）         |

累计风险值：`risk = Σ 权重`（**仅对窗口内未过期事件累加**，滑动与过期规则见下）。`pattern_tag`、命中规则版本、`risk` 及所属层级（session / user+tenant）一并写入审计，保证可回放。

**窗口滑动与事件过期**（防止 `risk` 只增不减）：每次请求时**先剔除 `occurred_at < now() - window` 的事件，再累加剩余事件权重**；窗口长度按 `sensitivity_class` 分层（L1/L2 为 24h、L3 为 7d，见 §4.8.1），session 级窗口边界为会话生命周期。两层按各自窗口边界独立滑动、独立计算，互不累加。**事件保留期 90 天仅用于审计回放，不参与实时 `risk` 计算**；实现上须以带时间谓词的聚合查询取窗口内事件，不得用「累计计数器 + 定时清零」近似，否则跨窗口边界会误判。

#### 4.8.3 超阈值动作分级

| 条件（两层 `risk` 独立比较，见 §4.8 分工）            | 动作                                        | 原因码 / 审计                          |
| --------------------------------------- | ----------------------------------------- | --------------------------------- |
| 两层 `risk` 均 < `T`                       | 正常返回（仍按 10.5 脱敏）                          | 记事件                               |
| L1 且任一层 `risk ≥ T`                      | 停止返回个体值，转**审批**（`approval_request`），说明可申请 | `SENSITIVE_QUERY_SEQUENCE` + 全量审计 |
| L1 且任一层 `risk ≥ 2T`，或 L2 任一层 `risk ≥ T` | **拒答**，本会话该 `sensitive_key` 临时冻结          | `SENSITIVE_QUERY_SEQUENCE` + 安全看板 |
| L3 任一层 `risk ≥ T`                       | **拒答** + 引导审批入口（个体判定本就需审批）                | `SENSITIVE_QUERY_SEQUENCE` + 全量审计 |
| 命中 `existence_probe` 或任一越权尝试            | **硬阻断 + 实时告警**，不进入审批                      | 独立安全事件，对齐 v1.4 13.1 硬阻断           |

两层同时超阈值时取**动作档位较高者**，不做 `risk` 数值相加。所有分支都不得泄露「是哪一个条件先触发」的差异信息；对外统一文案来自已发布 Copy Template。规则版本随发布清单冻结，变更需走 11.3 依赖失效流程。

### 4.9 缓存（v1.4 10.4）

缓存落 PG 表，键至少含：`normalized_question`、全部版本号、`manifest_id/content_hash`、`scenario_id`、租户与 `user_scope_hash`、`resolved_entity_hashes`、`session_query_context_hash`、`query_parameters`、`batch_size`、`display_transform_time_bucket`、`freshness_bucket`、**`timezone` 与 `time_anchor_date`**。权限、策略、资产版本、解析器、时间基准或数据新鲜度变化即失效；禁用仅含问题文本的全局结果缓存。

## 附录 A. 前端技术路线（2026-11-06 冻结）

> **决策状态**：项目负责人已冻结 —— **React 首选**、主路线 **shadcn/ui + Tailwind v4 + Radix + CopilotKit Headless**。本附录只锁定选型、依赖事实与验收判据（PoC #10）；组件详细设计、交互稿、状态管理细节仍属《阶段零/一实施规格》（§1.3 边界不变）。

### A.1 决策依据（事实已核实）

1. **后端协议已定死前端第一决策**：`agentscope-agui-spring-boot-starter`（§1.2）输出**标准 AG-UI 协议事件**（`RUN_*` / `TEXT_MESSAGE_*` / `TOOL_CALL_*` / `CUSTOM` / HITL interrupt / state）。CopilotKit 是 AG-UI 协议的作者，`@ag-ui/client` 是其底层依赖，两端协议天然对齐；自研 SSE 解析与 §11 第 7 项「必须复用、不重复造轮子」冲突。
2. **Headless 模式保证单一设计系统**：CopilotKit 官方 Headless 模式（`useAgent` / `useCopilotKit` 等 hooks，不用自带样式的 `CopilotChat`）提供生成式 UI、工具渲染、HITL 与只读 shared state 能力；官方示例即以 shadcn/ui primitives 手搓界面，全前端只有**一套设计系统**。
3. **能力映射到 v1.4 交互需求**：HITL 行内选择卡片 ↔ 澄清四要素 / 近似降级征得同意；`useFrontendTool`（async handler 恢复挂起 tool Promise）↔ 审批回传；`CUSTOM` 事件 ↔ discovery 候选、冷启动地图、复合子结果、纠正回退、原因码渲染；只读 shared state recipe ↔ v1.4 7.1「上下文不可由客户端自由修改」。

### A.2 分层选型

| 层 | 选型 | 说明 |
| --- | --- | --- |
| 协议 | **AG-UI**（CopilotKit 内置 / `@ag-ui/client`） | 与 Java 端 starter 同协议，不自研 SSE 解析 |
| 对话与结构化交互 | **CopilotKit Headless** + 业务组件挂 `CUSTOM` 事件 | 澄清四要素、discovery、冷启动地图、审批回传、复合子结果、纠正回退、原因码渲染 |
| 基础组件 | **shadcn/ui + Tailwind v4 + Radix**（copy-paste，源码自有） | 单一设计系统，样式零运行时开销，源码自有可完全掌控 |
| 数据展示 | **TanStack Table**（虚拟滚动 / 列固定 / 导出）+ **ECharts** + Monaco 或 CodeMirror | 执行计划树、SQL 高亮自研 |
| 表单 / 状态 | React Hook Form + Zod、TanStack Query、Zustand | Zod schema 与后端 `inputSchema` 语义对齐 |
| 工程 | Vite + TypeScript + pnpm | 纯静态构建产物，由 Spring Boot 单体托管静态资源，**不引入独立前端服务** |

### A.3 PoC #10（硬判据，未通过前前端工程不启动）

见 §7 #10：**纯浏览器直连 Java `/agui/run` SSE、零额外服务端进程；六类事件在 shadcn 界面完整重建；断线重连幂等；`RUN_STARTED.input` 前端脱敏验证**。不通过则退回 `@ag-ui/client` + 自研渲染层（shadcn 基础组件层两条路线不变）。

### A.4 三条安全约束（主路线与退路均须执行，进实施规格验收清单）

1. **前端脱敏**：AgentScope AG-UI 兼容说明明确「`RUN_STARTED.input` 保留原始请求（含被拒内容），记录或转发事件的消费方须自行脱敏」—— 前端日志、OTel 前端 trace、错误上报、第三方埋点必须先过滤，不得依赖后端已脱敏（对齐 v1.4 10.5 / 12.1）。
2. **shared state 只读**：AG-UI state 配置为**服务端只读投影**；用户选择经结构化 action 回传、由服务端合并，前端不得直接写 `session_query_context`（对齐 v1.4 7.1「上下文由认证系统签发，不能由客户端自由修改」）。
3. **ID 与文案分离**：澄清候选的资产 ID 只放事件 payload 用于回传，**不渲染为可见文本**；前端不拼装含资产名、物理表、SQL、被裁字段名的提示文案（对齐 v1.4 5.12 文案模板禁令）。
