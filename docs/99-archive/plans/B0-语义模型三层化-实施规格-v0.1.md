## 1. 范围与不做的事

### 1.1 范围

把「指标 / 维度直绑物理表字段」改为「引用本体业务对象属性」，使 **Property 成为唯一持有物理映射的资产**：

- `Metric{table, column}` → `{objectId, propertyId, aggregation}`
- `Dimension{table, column}` → `{objectId, propertyId}`
- 发布清单升 **v20**，v19 及以前保持可激活、可编译（双形态窗口）
- 编译产物 SQL **逐字不变**（E1），DSL / 审计 / 前端引用的资产 ID 全部不变

### 1.2 不做的事（非目标，明确写死）

| 不做 | 理由 |
|---|---|
| **不引入 Model 层** | 影响分析 §2.4 / §11 D-3：B0 是「物理名收敛到属性」的最小改造。事实粒度继续由「聚合属性归属表 + 对象主表断言」隐式承载 |
| **不预留 `model` 空段或空字段** | fail-closed 下空段会引出「是否必填 / 空段是否合法」歧义，还要给 `ManifestStructureValidator` 加豁免规则，收益为负 |
| 不改 DSL Schema | `QueryDsl` 只引用资产 ID，与物理绑定无关（影响分析 #9/#10/#15/#16 平移） |
| 不改审计 JSON 结构 | `resolvedJoins` 的物理列来自 `Relation.fromColumn/toColumn`，不在本次范围（#24） |
| 不改前端 VO | `AssetChipVO{id,name}` 零物理名（#33） |
| 不做多方言 / 多数据源 | 依赖 Model 层，不在 B0 |
| 不做数据源接入变更 | 物理表列不变（E2） |

### 1.3 与 M8 的关系

**无依赖**。M8 属「上线与规模化」，须等产品真正化之后实施；B0 独立排期、独立验收（影响分析 §11 D-1）。B0 完成不构成 M8 的放行条件，反之亦然。

## 3. 设计

### 3.1 数据模型 / Schema

#### 3.1.1 Metric v20

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` / `name` / `summary` / `aliases` | 同 v19 | 是 | 业务化命名规格不变 |
| `objectId` | string | 常规指标必填 | 引用已发布 concept，如 `concept.order` |
| `propertyId` | string \| null | 受控 | 常规指标必填；**对象级计数时为 null** |
| `aggregation` | enum | 常规指标必填 | `SUM / COUNT / COUNT_DISTINCT / AVG / MIN / MAX` |
| `ruleId` | string | 二选一 | 布尔判定指标；此时 `objectId`/`propertyId`/`aggregation` 全空 |
| `allowedModes` / `allowedDimensions` / `sensitive` / `caliberVariants` | 同 v19 | 是 | 语义不变 |

**互斥规则（fail-closed，`ManifestStructureValidator` 逐条实现）**

| # | 规则 | 违反时 |
|---|---|---|
| R1 | `ruleId` 非空 ⇒ `objectId` / `propertyId` / `aggregation` 必须全空 | 拒绝：布尔判定指标不得带聚合绑定 |
| R2 | `ruleId` 空 ⇒ `objectId` 与 `aggregation` 必填 | 拒绝：常规指标缺对象或聚合 |
| R3 | `propertyId` 为空 ⇒（**限常规指标**，`ruleId` 为空）必须 `aggregation ∈ {COUNT, COUNT_DISTINCT}` **且** `objectId` 的 concept 有 `identityProperty` | 拒绝：对象级计数只允许计数类聚合（`SUM`/`AVG`/`MIN`/`MAX` 无属性可作用），且对象须有标识属性 |
| R4 | `propertyId` 非空 ⇒ 属性必须存在 **且** `property.conceptId == objectId` | 拒绝：属性不属于该对象（禁止跨对象借用） |
| R5 | **同时**出现物理名（`table`/`column` 非空）与语义绑定（`objectId`/`propertyId` 非空） ⇒ 拒绝 | 拒绝：混装；形态判定见 §3.1.3（v19 形态只有物理名、v20 形态只有语义绑定，互斥） |
| R6 | `objectId` 对应的 concept 不存在或未发布 ⇒ 拒绝 | 拒绝：对象未发布 |
| R7 | **指标**的 `objectId` 有值但 concept 无 `identityProperty` ⇒ 拒绝（维度不适用，维度不承担 FROM） | 拒绝：无主表，无法做 FROM 断言（§3.3.1） |

> R3 的「对象级计数」是 v20 新增能力，**B0 迁移不使用**（`metric.order_count` 继续挂 `property.order.order_no`，保 SQL 逐字等价，见 §3.3.2）。
> 两种计数语义在编译期分别落为：`COUNT` → `COUNT(<identity.column>)`（行数）；`COUNT_DISTINCT` → `COUNT(DISTINCT <identity.column>)`（去重对象数）。B0 **结构与编译都实现**（与 §8 D-3 一致），但**不进迁移、无 Golden 覆盖**，由单测断言产物形态。

#### 3.1.2 Dimension v20

| 字段 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `id` / `name` / `summary` / `aliases` / `sensitive` | 同 v19 | 是 | 不变 |
| `objectId` | string | 是 | 引用已发布 concept |
| `propertyId` | string | 是 | 属性必须存在且 `property.conceptId == objectId` |
| `table` / `column` | — | 禁止 | 出现即拒绝（R5 同款） |

#### 3.1.3 形态判定（读取侧唯一入口）

清单加载时按以下顺序判定形态，**不允许"猜测"**：

```
含 table 或 column（非空）
  ├─ 同时含 objectId 或 propertyId → 拒绝（混装，DSL_INVALID / 结构违规）
  └─ 仅含物理名            → v19 形态（兼容窗口内可编译）
不含 table / column
  ├─ 含 objectId            → v20 形态
  └─ 两者皆无              → 拒绝（无任何绑定）
```

判定实现收口为 `SemanticManifest.Metric#bindingForm()`（返回 `V19_PHYSICAL` / `V20_SEMANTIC` / `REJECT`），编译链与校验器共用，**不得各自实现一套判定**。

### 3.3 关键流程

#### 3.3.1 编译推导链（E1 的构造性等价证明）

现有实现（`SqlCompiler` L1386–1396）：

```java
private static Name assetColumn(String table, String column) {
    if (column != null && !column.contains(".") && table != null && !table.isBlank()) {
        return columnName(table + "." + column);
    }
    return columnName(column);
}
```

v19 与 v20 两条路径的产物逐字相等，**这是构造性证明，不是经验判断**：

| 形态 | 调用 | 中间值 | 产物 |
|---|---|---|---|
| v19 | `assetColumn("orders", "amount")` | `columnName("orders" + "." + "amount")` | `DSL.name("orders", "amount")` |
| v20 | `assetColumn(property.column = "orders.amount")` | `columnName("orders.amount")` | `DSL.name("orders", "amount")` |

原因：**`property.column` 本就是限定名（含点），`metric.column` 是裸列名**——两条路径最终都走 `columnName("<table>.<column>")`。新增单参重载 `assetColumn(Property)` 即可，旧双参重载在兼容窗口内保留给 v19 形态。

**调用面**：`SqlCompiler` 共 13 处 `assetColumn` 调用，其中 12 处（metric/dimension 路径）改为属性推导，1 处（L260，lookup 编译）本就传 `property.getColumn()`、**不动**。逐行清单见 §3.4。

#### 3.3.1.1 证明覆盖面：哪些路径不需要证明（实测界定）

上面的等价证明只覆盖「消费 `metric.table`/`metric.column` 的路径」。下列路径**本就不消费**这两个字段，故三层化对其**零影响**，不需要额外证明——但必须在文档里点名，否则评审者会误以为遗漏：

| 路径 | 实际输入（实测） | 为什么不受影响 |
|---|---|---|
| retention cohort 的 `FROM`（L477） | `eventTable = tableOf(timeProperty.getColumn())`（L434） | 事件表本就由属性推导，与 `metric.table` 无关 |
| retention cohort 的维度列（L474/L490） | `assetColumn(dimension.getTable(), dimension.getColumn())`——**是 `assetColumn` 直接调用**，不是间接推导 | 属 12 处改造点之内，已被 §3.3.1 覆盖 |
| attribution cohort 的 `FROM`（L688） | `DSL.table(DSL.name("cohort_first"))`——CTE，非物理表 | 不涉及任何资产物理名 |
| attribution cohort 的维度列（L685/L697） | 同 retention，`assetColumn` 直接调用 | 属 12 处改造点之内 |
| `JoinPathResolver.conceptByTable`（L164–176） | **只读 `ontology.getProperties()` 的 `property.column`**，不读 metric/dimension | 映射表内容不变；其**入参** `rootTable`/`targetTable` 来自 L45/49/52/55，改后仍等于 `tableOf(property.column)`（E1 已证相等），故 `get()` 结果不变 |

**结论**：不存在「不在证明范围内的第三条路径」。评审若担心 cohort 的 FROM 会随 metric 漂移，结论是**不会**——retention 用事件表、attribution 用 CTE，两者都不看 `metric.table`。

但 W2 仍应为这 4 处（L474/L490/L685/L697）各加一条「v19 vs v20 产物相等」单测断言，因为它们是 `assetColumn` 的直接调用点，属于 12 处改造面，不能只靠 Golden 间接覆盖。

**FROM 推导（决策 D-1，见 §8）**：

```
FROM 表 = tableOf(property.column)                      // 聚合属性归属表
断言   = tableOf(concept.identityProperty.column)        // 对象主表
若二者不等 → 拒绝（DSL_INVALID "对象跨表聚合需 Model 层，B0 不支持"）
```

v19 实测：6 个 concept 的 `identityProperty` 与各指标聚合属性同表，断言全部通过（影响分析 §2.3）。

| 情形 | 规则 | 本批适用 |
|---|---|---|
| **属性与其包装维度同名** | **允许**。维度是属性的业务包装，同名是 v19 既有惯例（实测 3 组先例：`dim.order_date`/`property.order.order_date` 同为「下单日期」，`dim.customer_tier`/`property.customer.tier` 同为「客户等级」，`dim.product_category`/`property.product.category` 同为「品类」） | `property.order.channel` 用「渠道」、`property.order.region` 用「区域」，与 `dim.channel` / `dim.region` 对齐 |
| **属性与「不同物理列」的同名资产** | **必须加限定词**。否则语义不同却同词，检索与澄清会指向错列 | `property.order.customer_id`（`orders.customer_id`）不得叫「客户编号」——那是 `property.customer.customer_id`（`customer.id`）的名字；`property.order.refund_amount` 不得叫「退款金额」——那是 `metric.refund_amount`（聚合值）的名字，原值与聚合值同名会混 |

> **为什么不能一刀切「全部避开」**：实测 v19 词表中跨类型同词共 **10 处**，其中 6 个 term 正是「维度 ↔ 其底层属性同列同名」。若强行要求新增属性避开「渠道」「区域」，会造成同一物理列的两个资产（`dim.channel` 与 `property.order.channel`）命名分裂——这比同名更糟。判据应是「**是否指向同一物理列**」，不是「是否同词」。
> `lookupProjectable=false` 的两项（客户编号、退款金额）是 fail-closed 保守取值：B0 不放开个体级投影，业务需要时单独评审放开。

### 5.5 词表冲突审计（W3，E2 的可执行判据）

**为什么要单独一条**：`MentionIndex`（session L55–90）把 metric / dimension / concept / property 四类的 `name` + `aliases` 全部塞进同一个 `termIndex`（`Map<String, List<IndexEntry>>`，**设计上允许一对多**）。所以「0 冲突」既做不到也没必要——真正要防的是**同一个词指向不同物理列**。

**判据定义**

| 概念 | 定义 |
|---|---|
| 命中集 | 某个 `term` 在四类资产中命中的全部资产 |
| 可解析物理列 | `property` → 自身 `column`；`metric` / `dimension`（v20）→ `propertyOf(propertyId).column`；`concept` → 无列，不参与判据 |
| **真冲突** | 同一 `term` 的命中集里，去重后的**可解析物理列 > 1** |
| 非冲突 | ① 命中多个资产但都指向同一列（维度与其包装属性，如 `dim.order_date` 与 `property.order.order_date`）；② 命中同一资产两次（`name` 与 `alias` 重复，如 `metric.order_count` 的「订单数」）；③ 只有 1 个资产有可解析列 |

**v19 基线实测（2026-11-12，105 个 term）**

- 跨类型同词 10 处：**6 个 term 是维度 ↔ 其底层属性同列同名**（合规）+ 1 处同资产 name/alias 重复（合规）+ 1 处仅一个资产有列（合规）+ **2 处真冲突**（下述）
- **真冲突 2 处**（既有问题，B0 不负责修，但不得增加）：
  - 「渠道」→ `dim.channel`（`orders.channel`）× `property.channel.name`（`channel.name`）——正是影响分析 §3 的 `dim.channel` 陷阱在词表层的表现
  - 「渠道ID」→ `property.channel.channel_id`（`channel.id`）× `property.event.channel_id`（`event.channel_id`）

**验收方式**：写 `scripts/b0-term-audit.mjs`（读清单 JSON，复刻 `MentionIndex` 的 `strip` + 非空过滤规则，输出「term → 资产 × 列」表与真冲突清单），在 W3 与 W5 各跑一次：

- v20 清单真冲突数 **≤ 2**（基线），且新增的 4 个属性不出现在任何真冲突的命中集里；
- 反向对照：`dim.region` 与 `property.order.region` 同为「区域」但列相同，应被判定为**非冲突**（用于证明判据自身有效）。

**不要**断言「每个 term 只命中一个资产」——那与 `MentionIndex` 的一对多设计相悖，且既有 6 个合规同名词条会直接把它打成 FAIL。

**回退路径**：保留 v19 清单与旧编译路径（双形态窗口内），出问题即 `activate` v19 + 关闭 v20 发布入口；**不需要回滚数据库**（无 schema 变更、无数据迁移，只换资产形态）。

## 8. 设计决策（待负责人确认）

| # | 决策 | 建议 | 备选 | 影响 |
|---|---|---|---|---|
| **D-1** | FROM 表归属 | **聚合属性归属表 + 「= 对象主表」断言**：`FROM = tableOf(property.column)`，断言等于 `tableOf(concept.identityProperty.column)`，不等即拒绝 | 纯 b) 只按属性表推导（不校验对象主表）；纯 a) 引入 `concept.primaryTable` 字段 | 前者零新字段且 fail-closed；纯 b 会让跨表对象悄悄跑偏。**断言失败语义**：新增 `OBJECT_TABLE_MISMATCH = 1_002_000_047`，文案「对象的聚合属性与主表不在同一物理表，B0 不支持跨表聚合: {objectId} / {propertyId}」，日志带 `objectId`/`propertyTable`/`identityTable` 三字段（§3.2）。**否决纯 a 的实质危害**：`primaryTable` 会让物理绑定出现**第二个入口**（Property 之外），未来多数据源/多方言/Model 层扩展时它与 `property.column` 可能不一致，届时要么再改一次元模型、要么在编译期做二次校验 |
| **D-2** | 对象主表来源 | **复用 `concept.identityProperty`**（v19 六个 concept 全部具备，实测无缺口） | 新增 `primaryTable` 或 `primaryPropertyId` | 零新字段；副作用是「无标识属性的对象不能作聚合主体」，与粒度要求一致。**该约束两处实现**：发布侧 R7 产 `Violation`（fail-fast）、编译侧 FROM 断言兜底（防历史清单绕过发布校验），同一语义、同一文案口径。**备选 `primaryPropertyId` 的取舍**：它比 `primaryTable` 更兼容三层化（引用属性而非物理表），是未来「主标识 vs 副标识」出现时的自然扩展；v19 无此需求，故暂不引入 |
| **D-3** | 对象级计数 | **保留为 v20 能力，但 B0 迁移不使用** | 迁移时就用（`metric.order_count` 改 `propertyId=null`） | 若迁移即用，`COUNT(orders.id)` 会变 `COUNT(identity)`，破坏 E1；故迁移不用。**「保留」的范围**：元模型（R3 允许 `propertyId=null` + `{COUNT, COUNT_DISTINCT}`）与编译实现**都做**，但**不进迁移、无 Golden 覆盖**，改由单测断言产物形态（`COUNT(<identity.column>)` / `COUNT(DISTINCT <identity.column>)`）。不采用「只留元模型、编译报未实现」——那会让**发布通过的资产查不了**，比多写一个分支更糟 |
| **D-4** | 双形态退役时点 | **v20 生效满 30 天 + 连续两次全量回归无形态失败 + 负责人签字** | 固定日期（如 M8 发布前）；不设退役（永久兼容） | 固定日期可能早于稳定；永久兼容会让判定逻辑长期双份维护。「形态失败」已定义为三类（v19 不可用 / v20 不可用 / 两形态产物不等，见 §3.3.3）。**M8 提前时的处理**：退役时点**不跟 M8**——M8 上线检查清单把「双形态窗口是否已退役」列为独立检查项，未退役不阻塞 M8，但须在 M8 验收报告标注「窗口仍在，退役条件见 §3.3.3」；避免退役条件被 M8 进度绑架、也避免 M8 被退役条件绑架 |

**D-1 的 v19 等价性依据**：6 个 concept 的 `identityProperty` 与所有指标聚合属性同表（影响分析 §2.3 实测），故断言在 v19 全量通过，不影响迁移。

> **正文与决策的关系**：§3.3.1（FROM 归属）、§3.3.2（对象级计数不使用）、§3.3.3（退役条件）已按上表**建议方案**编写。若负责人改判，须同步修改对应正文段落并在修订记录留痕，**不得只改 §8 表格**。
