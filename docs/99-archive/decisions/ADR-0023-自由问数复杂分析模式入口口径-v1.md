> **版本**：v1

## 背景

2026-11-12 mimo 复杂度子集诊断中，FUNNEL 0/4、RETENTION 0/3、ATTRIBUTION 0/4、LOOKUP_BATCH 0/2。
失败样本多表现为模型按提示词输出 `out_of_capability`，而评测期望自由问数直接进入对应分析模式。

根因不是执行器不能编译这些模式，而是系统提示词 v3 第 47–48 行仍写着：

> `funnel` / `retention` / `attribution` / `lookup_batch` 由场景与 DSL 入口提供，自由问数不支持；遇到这类诉求输出 `out_of_capability=true`。

这与 M6 后的引擎能力、test 集 v5 / 复杂度子集的期望不一致，导致模型按旧口径 fail-closed。

## 决策

1. **FUNNEL、RETENTION、ATTRIBUTION、LOOKUP_BATCH 允许自由问数入口。**

   - 用户可以在 `/api/v1/ask/runs` 用自然语言表达这些分析诉求。
   - 只要候选资产、维度、事件定义、Rule、时间窗与授权满足，编排器应进入对应 `analysis_mode`。
   - 不满足时仍按现有 fail-closed / 澄清规则处理，不允许编造参数或绕过安全闸门。

2. **提示词 v3 中「自由问数不支持」的表述作废。**

   - 后续实现不得把本决策解释为“提示词可以不改”。
   - 需要提示词升版（建议 v4）补齐四类模式的目标形态、参数边界与示例，并保持只引用候选集 ID。
   - 提示词升版前，复杂模式自由问数的低通过率应归因为**提示词 / 候选表达缺口**，不能归因为模型无法执行。

3. **执行侧安全边界不变。**

   - 本决策只开放语义入口，不放宽任何查询执行、RLS、跨轮累计、审批、敏感查询、审计或成本闸门。
   - 若候选资产不支持某个模式、事件定义缺失、Rule 未发布或时间窗缺失，仍按现有结构化错误 fail-closed。

4. **评测口径不变。**

   - test 集 v5 与 E7 复杂度子集 v1 中上述模式的 `expected.terminal=query` 继续有效。
   - 后续小批量复测用同一口径；不得把提示词旧口径造成的 `out_of_capability` 改判为通过。

## 影响

- **正面**：自由问数能力与 M6 引擎能力对齐，减少“系统可查但模型拒绝”的假阴性；复杂度子集后续能更准确区分模型问题与资产 / 提示词问题。
- **负面**：提示词升版前，这类题会继续失败；提示词变长可能增加 token 成本，需要在小批量复测时观测。
- **对 C-1**：本决策不解除 [ADR-0019](../../01-decisions/ADR-0019-M7有条件通过E7评测挂账.md) 的 C-1，也不改变原 test 集 v5 全量 ×3 的正式验收口径。

## 备选方案与否决理由

| 备选 | 否决理由 |
|---|---|
| 维持“场景 / DSL 入口 only”，测试期望改为拒绝 | 与 M6 已交付的执行能力和 test 集 v5 矛盾；会把可服务诉求变成产品可用性缺口 |
| 按模式分档，仅开放 FUNNEL / ATTRIBUTION | 增加解释成本；RETENTION / LOOKUP_BATCH 同样有自然语言入口需求，暂无证据需要单独禁止 |
| 立即改提示词并直接全量复测 | 违反 ADR-0022 的 API 安全模式与负责人“先小批量”要求；应先零 token 定表达再小批验证 |
