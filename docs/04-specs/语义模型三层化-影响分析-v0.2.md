### 0.3 结构性差异（核验方案依据时发现，已单列 §2.4）

核验 #7「上游依据锚定」时通读 v1.4 §5.1，发现方案定义的是**四层**（Ontology → Ontology Mapping → **Model** → Metric/Dimension），而本分析目标形态是**三层**，省略了 **Model 层**（逻辑数据集 / 事实粒度 / 允许 Join Path / SQL 方言）。

- **不影响本分析的三档判定**：#7 结论反而更强——三层化是**回归方案定义**而非架构变更（方案的 Mapping 本就把物理映射从指标里分离出去）。
- **但必须显式登记**：事实粒度在 B0 后仍隐含在「聚合属性归属表」推导中，不由 Model 声明。ADR-0016/0018 的粒度判定行为等价（#17 已论证），可语义载体仍隐含；不写明边界，未来多事实表/多方言会重现同一问题。
- **处置**：§2.4 给出层级对照表；B0 非目标口径已于 §11 D-3 定档（不引入 Model 层、不预留空段），`Model` 登记为后续候选（触发点：首次出现多事实表同指标，或第二种 SQL 方言）。

## 2. 目标模型与工程约束

### 2.1 目标形态

物理（Query DS）→ 本体（业务对象 / 属性，**属性唯一持有物理映射**）→ 指标 / 维度（只引用 `objectId + propertyId`）。

- `Metric{table,column}` → `{objectId, propertyId, aggregation}`；`Dimension{table,column}` → `{objectId, propertyId}`；
- 对象级计数：`{objectId, aggregation:COUNT, propertyId:null}`，受控例外——必须 COUNT 且对象有 `identityProperty`（负责人已拍板）；
- `ruleId` 型布尔指标分支保留（无物理列，结构校验二选一）；
- DSL / 前端 / 审计引用的资产 ID 全部不变。

### 2.2 工程约束（本分析新增，建议写入 B0 规格）

**约束 E1 · 编译产物 SQL 文本逐字等价**：`assetColumn()` 输入来源从 `metric.table/column` 改为 `property.column` 推导，但输出限定名必须逐字不变。以 Golden 三份（`Golden集-v2` / `M3-Golden` / `M6-Golden`）逐字比对为验收手段——成立则证据失效面从「SQL 重固化」收敛为「清单 hash 变化引发的重跑」，成本大幅下降。

**约束 E2 · 迁移保持物理列不变**：资产迁移按**物理列归属对象**，不按业务名对齐（见 §3 的 `dim.channel` 陷阱）；`dim.channel` 等 ID 不变、展示名不变。

### 2.3 对象跨表 FROM 归属（新设计项，规格阶段定）

v19 实证：6 个 concept 的属性各自单表（order→`orders`、customer→`customer`、order_item→`order_item`、product→`product`、channel→`channel`、event→`event`），迁移无跨表问题。工作假设（二选一，规格定）：

- **a) 对象显式声明主表（推荐）**——聚合 FROM 用主表，属性允许跨表但须经关系可达；
- **b) 按聚合属性归属表推导 FROM**。

v19 迁移两者等价；差异只在引入跨表对象后才显现，故列为设计项而非破坏项。

### 2.4 与 v1.4 方案层级的对照（差异登记，本次落地新增）

v1.4 §5.1 定义的完整链路是 **4 层**：Ontology（Class/Property/Relation）→ **Ontology Mapping** → **Model**（逻辑数据集、事实粒度、物理关系实现、允许 Join Path、SQL 方言）→ Metric / Dimension。本分析的目标形态是 **3 层**：

| v1.4 层 | 本分析对应 | 状态 |
|---|---|---|
| Ontology Class / Property / Relation | L1 本体（属性持物理映射） | 落地 |
| Ontology Mapping | 并入 Property 的 `column` 字段 | 简化（未独立成段） |
| **Model**（逻辑数据集 / 事实粒度 / Join Path / 方言） | **无对应**，粒度仍由 `metric` 隐式承载 | **不在 B0 范围** |
| Metric / Dimension | L2 指标维度（只引用 objectId + propertyId） | 落地 |

**结论**：B0 是「把物理名收敛到属性」的最小改造，**不是**完整实现方案的语义层——`Model` 层（显式事实粒度、逻辑数据集、多方言）明确**不在 B0 范围**。

**为什么必须显式登记**：ADR-0016（品类×订单事实指标粒度边界）与 ADR-0018（订单项级指标）的粒度判定当前依赖 `metric.table` 的隐式语义；三层化后改由「聚合属性归属表」推导，行为等价（见 #17），但**语义载体仍是隐含的**。若不在 B0 规格写明这一边界，未来接入第二个事实表 / 多方言 / 一个指标跨多个逻辑数据集时，会重现「物理名散落在语义资产里」的同一问题。

**处置（已定档 §11 D-3）**：B0 规格 §1 非目标写明「不引入 Model 层，事实粒度继续由指标聚合属性隐式承载」，且不预留 `model` 空段；`Model` 登记为后续候选（触发点：首次出现多事实表同指标，或第二种 SQL 方言）。

## 3. 实证基线：v19 资产映射覆盖（2026-11-12 实测）

对 `ontos-assets/first-release-v19.json` 全量比对 `metric/dimension` 物理列与 `property.column`：

| 类别 | 总数 | 已有 Property 承载 | 需补 Property |
|---|---|---|---|
| 指标 | 9（含 1 个 `ruleId` 型） | 6（`gmv` / `paid_gmv` / `gmv_created` / `order_count` / `avg_order_value` / `order_item_quantity`） | **2**：`distinct_customers`（`orders.customer_id`）、`refund_amount`（`orders.refund_amount`） |
| 维度 | 5 | 3（`order_date` / `customer_tier` / `product_category`） | **2**：`dim.region`（`orders.region`）、`dim.channel`（`orders.channel`） |

迁移需新建 4 个属性：`property.order.customer_id` / `property.order.refund_amount` / `property.order.channel` / `property.order.region`。

**陷阱实证**：`dim.channel` = `orders.channel`（订单表冗余渠道字段）≠ `property.channel.name` = `channel.name`（渠道维表名称）——按业务名对齐会映射错并改变查询语义，故立 E2 约束。

**口径保持实证**：`metric.order_count` 迁移后保持 `COUNT(orders.id)`（挂 `property.order.order_no`，其实测映射即 `orders.id`），不启用对象级计数，保 SQL 逐字等价。

**Property 敏感分级实证**：`sensitivity ∈ {INTERNAL, PII, PUBLIC}` + `existenceSensitive` + `lookupProjectable` + `filterable` + `conceptId`——属性级敏感模型真实存在（R3 结论坐实）。

### 3.1 迁移期新增属性的命名冲突（本次落地新增）

补建的 4 个属性有两组与既有属性「同义不同体」，业务名若直接沿用会污染检索与澄清候选（名称、别名都进检索词库）：

| 新属性 | 既有易混属性 | 差异 | 命名处置 |
|---|---|---|---|
| `property.order.customer_id`（`orders.customer_id`） | `property.customer.customer_id`（`customer.id`） | 前者是订单上的客户外键，后者是客户主键；两者都像「客户编号」 | 新属性业务名须加限定（如「下单客户编号」），别名不得与既有属性重叠 |
| `property.order.channel`（`orders.channel`） | `property.channel.name`（`channel.name`） | 前者是订单冗余渠道值，后者是渠道维表名称（§3 陷阱同源） | 新属性业务名用「订单渠道」，避免与「渠道名称」混淆 |

其余两个（`property.order.refund_amount`、`property.order.region`）在 v19 无同名属性，无冲突。

该风险不影响 §9 的三档判定（属迁移实施细节），但**必须写入 B0 迁移验收**：新增属性的 `name`/`aliases` 与检索词库做一次全量冲突扫描。

## 11. 决策记录（负责人 2026-11-12 定档）

### D-1 · B0 与 M8 解耦，独立排期

**负责人判定**：M8 属「上线与规模化」（网关 / 部署 / 灰度回滚 / SLO / 灾备），须等产品真正化之后才实施；B0 作为其前置会被无限期推迟，故 **B0 独立排期、独立验收**。

**判定不改变三档结论**：破坏仍为 0，§9 五条附条件全部保留。

**排期候选与建议**（负责人决策，本文只给依据）：

| 时点 | 优点 | 代价 | 建议 |
|---|---|---|---|
| **A. 立即启动**（C-1/C-2 因 token 预算暂停的窗口期） | 资产规模最小（9 指标 / 5 维度，仅补 4 属性），迁移成本最低；后续评测只锚定一次 v20 | 需一次性投入完整改造面（§9：5 类改造 + 18 夹具 + 迁移脚本 + 45 项证据重跑） | **推荐** |
| B. 等 C-1/C-2（E-7 LLM 评测）清完再启动 | 评测不中断 | 评测先锚 v19、B0 后再锚 v20，45 项证据要重跑两次 | 不推荐 |
| C. 等 M8 完成后 | 不干扰上线 | 资产规模最大、迁移最贵；M8 前端（数据词典 / 发布链路）会先按旧结构落一遍再改 | 不推荐 |

**推荐 A 的两条硬依据**：① 评测证据的重跑成本与清单形态绑定，B0 越早做，重跑次数越少；② 每新增一个指标/维度，都要先在旧形态写一遍 `table/column`、迁移时再改一遍，成本随资产数线性上升。

**已确认（负责人 2026-11-12 追加）**：B0 按**独立工作包**管理——**不占 M 编号、不参与主关键路径、不设阶段依赖**，独立排期独立验收。已登记于 [roadmap §2 末「B0」节](../03-plans/roadmap/Ontos开发计划-阶段性功能拆解-v1.md)：阶段总览表下方加「独立工作包」指引，B0 本身不进总览表（避免被阶段解析当作 M 阶段）。

### D-2 · ADR-0021 不立，改引 M4 / M6 既定模型

**判定**：不新立「平台四角色与资产审批发布模型」ADR。

**依据**：

- M4 已定档角色模型：`policy_snapshot`（不可变 JSONB 快照，2 个种子角色如 `role.analyst`），并明文规定「若需新角色，走 `policy_snapshot` 新版本承载，**不改表结构**」——再加一层四角色模型属重复建模。
- M6 已有 `ontos-module-catalog` 承载 scenario / skill / vqr 生命周期与审核人记录，资产审批发布有实现基础，缺的是流程编排而非模型。

**处置**：本文上游依据改引 M4 实施规格与 M6 实施规格；若产品化确需「审核人与发布人强制分离」等四眼约束，触发点 = M8 决定引入审批工作流时，届时单独立 ADR，**与 B0 无依赖**（B0 是语义结构改造，与角色模型正交）。

### D-3 · Model 层写为非目标，不预留空段

**判定**：B0 不引入 Model 层；**不预留 `model` 空段或空字段**。

**依据**：

- fail-closed 环境下空段会引入「是否必填 / 空段是否合法」的歧义，`ManifestStructureValidator` 还要新增豁免规则，收益为负。
- B0 的 `Metric{objectId, propertyId}` 与 Model 层**正交**：将来引入 Model 时，只需让 Concept 声明 `primaryModelId`（或由 Model 反向引用 Concept/Property），Metric 结构不必再改——即 B0 不会成为死路。

**处置**：B0 规格 §1 非目标写明「不引入 Model 层，事实粒度继续由指标聚合属性隐式承载」；规格另加一条**扩展预留原则**：未来 Model 层只增不改 Metric/Dimension 结构。`Model` 登记为后续候选，触发点 = 首次出现多事实表同指标，或第二种 SQL 方言。
