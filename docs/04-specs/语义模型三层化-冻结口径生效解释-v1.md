## 2. 逐条生效解释

### 2.1 retention / attribution 规格 v1.1 —— 主体表与映射可达性

**原条文锚点**：L17、L51（「首发按 funnel 同型只支持主体表维度」）、L100（「其他已发布维度按映射可达性放行」）、L124（「映射表经路径可达，与 QUERY 分组/过滤同规」）。

**B0 后解释**：

1. 「主体表」「映射可达」中的**表**不再取 `Metric.table` / `Dimension.table`，一律由属性物理列推导：
   `tableOf(property.column)`（`property.column` 是含点限定名，如 `orders.amount` → `orders`）。
   收口点为 `BindingResolver.resolveSemantic`，编译器/校验器不得各自判形态。
2. **指标**额外受「属性表 = 对象主表（`concept.identityProperty` 所在表）」断言约束，不满足抛
   `OBJECT_TABLE_MISMATCH = 1_001_000_010`；**维度**只判可达、不做该断言（B0/R7 口径，允许跨表维度走 JOIN）。
   例：`dim.channel_name` 挂 `concept.channel / property.channel.name`，经 `Order.attributedToChannel` JOIN 可达，合法；
   `dim.channel` 挂 `concept.order / property.order.channel`，是订单表冗余列，同样合法但只碰一个业务对象。
3. cohort 的 FROM 不受影响：retention 用 `eventTable`（事件 `timeProperty` 推导）、attribution 用 `cohort_first` CTE，
   两者都不读指标物理绑定；`JoinPathResolver.conceptByTable` 只读 `ontology.properties`。
4. **E2 迁移判据**：判断「是否同一物理列」按 `property.column` 逐字比较，**不按业务名**。
   `dim.channel`（`orders.channel`）与 `channel.name` 是不同物理列，即使中文名都含「渠道」也不得合并。

### 2.2 M3 实施规格 v1 —— 口径变体「同表」条文

**原条文锚点**：L66「`condition` 字段必须属于该指标同表且在该指标 `allowedDimensions` 内」。

**B0 后解释**：

1. 「同表」= `tableOf(variantCondition 字段绑定属性.column) == tableOf(指标绑定属性.column)`，
   比较的是**物理限定表**，不是 `objectId`、不是业务名、不是 `dimension.id`。
2. `validateCaliberVariants` 经 `propertyById` 解析；属性缺失或无法解析即判违规（fail-closed，不默认同表）。
3. 变体「不覆盖指标口径的聚合与列」条文不变；v20 下聚合列由指标属性推导，E1 已证与 v19 逐字等价。
