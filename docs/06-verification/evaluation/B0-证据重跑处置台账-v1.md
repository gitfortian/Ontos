## 1. 口径裁决：ADR-0015 决策 4 的适用边界

ADR-0015 决策 4 原文：「若生效清单、题目/gold 集或 runner 版本发生变更，必须重跑并给证据升版本，原记录失效」。B0 确实变更了生效清单（v19 → v22），但**不能把这句话读成「全仓 33 份证据一律重跑」**：

1. 证据是**时点事实记录**，append-only。锚定 `2026.11.08-eighth` 的历史阶段证据记录的是当时那个清单下的运行结果，改写或重跑它们等于篡改历史，**违反治理规范**。正确处置是保留原件、在台账注明「历史存档，不代表当前生效清单」。
2. 决策 4 约束的是**当前生效清单下仍然有效的活跃基线**。B0 上线时已按此重跑并固化 Golden 三份（27+6+10，见实施规格 §10.9）。
3. 需要 live 服务 / 模型三件套 / 压测环境的证据，重跑前提是环境就绪；M7 的 E3（LLM 路径评测）本就按 ADR-0019 挂账为 C-1，不得借 B0 之名提前宣称闭环。

因此本台账采用**四类分层处置**，不虚报「32 条全部重跑」。

## 5. 本轮顺带发现并修复的缺陷（影响证据可信度）

`QueryServiceImpl.attachScenarioAudit` 此前**只挂在缓存命中审计 `buildCacheHitAudit`**，主执行/预检路径的通用 `buildAudit` 从未调用，导致 `EXECUTE` / `DRY_PLAN` / `DRY_RUN` / `COMPILE` 审计行的 6 个场景扩展列全空。B0 上线时「审计扩展列修复证据」实测到 `EXECUTE | scenario.sales` 是走了缓存命中分支，掩盖了主路径缺口。本轮已把 `attachScenarioAudit` 统一挂到 `buildAudit`（显式传 `PublishedManifest`，不做隐式 active 查询），并补两条单测覆盖「显式声明」与「会话继承」两条路径。原有 `B0-审计扩展列修复证据-v1.json` 记录的是修复前/局部通道的事实，保留原件；主路径修复的证据由本轮单测与后续 live 复验承载。

## 6. 结论

- ADR-0015 决策 4 在 B0 语境下按「活跃基线重跑 + 历史证据存档 + 环境依赖挂账」闭环，**不虚报 32/33 全量重跑**。
- 本轮真实复跑：Golden 三份（27/6/10，0 失败）+ 全量后端/治理/前端检查；v22 清单的 Golden 重锚沿用 B0 上线证据。
- 7 份 C 类证据按触发点挂账，逐项给出负责人与交付证据；B 类历史快照不改写。

> **并行义务点名**：OBL-M4 / OBL-M7 维持 `done`，`deferred 0`；本台账为独立工作包 B0 的证据面收口，不占阶段编号、不新增或关闭并行义务。
