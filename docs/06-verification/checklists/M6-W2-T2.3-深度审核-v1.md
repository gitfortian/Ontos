## 1. 结论

**通过（路由不启用）。** 五态决策为纯函数（不读库、不写库、无 LLM），三态迁移封闭枚举并全表锁定；pending_confirm 建立与确认复用 M5 澄清回传校验（伪造候选被拒）。**按 ADR-0004 §2.1，三触发条件当前 2/3（条件 ③ scope 裁剪归 T2.4），Scenario Entry Router 不接入瀑布，v13 只发布元数据**——这正是闸门要求的状态，核对记录已冻结。

## 3. 发现与处置

| # | 级别 | 发现 | 处置 |
|---|---|---|---|
| T23-1 | **P2** | **新会话无状态行时状态写入静默失效**：`UPDATE session_state` 对不存在的行影响 0 行，路由决策看起来成功但没落库 | `persist` / `confirm` / `exit` 写库前统一 `ensure` 行存在 |
| T23-2 | P3 | `scenario_state` 写入无乐观锁（M5 投影同规） | 同会话并发由 run 的 turn 占用前置约束；跨会话键隔离；登记不改 |
| T23-3 | P3 | Router 遇清单内非法 `entryMode` 会抛 `IllegalArgumentException`（500 而非业务码） | 清单结构校验已封闭枚举，运行时不可达；T2.4 接线时若有真实路径再转业务码 |
| T23-7 | **P2** | **确认消费与状态写入非原子**：`confirm()` 先 `consumeClarificationChoice`（清候选）再 `updateScenarioState`（写状态）两条 UPDATE——中间失败留下 pending_confirm 无候选的卡死会话（confirm 无候选可验、exit 仅 IN_SCENARIO 有效） | mapper 新增 `consumeClarificationAndUpdateScenarioState`：候选归属校验 + 清候选 + 写状态**同一条 UPDATE**；真库验证同候选重复消费 `UPDATE 0`（并发竞态 fail-closed） |
| T23-8 | **P2** | **显式进入不清残留候选**：pending_confirm 中直传已授权场景 → ENTER 只写状态，旧 `pending_clarification` 永久残留（confirm 因状态已变被拒，候选无出口） | `updateScenarioState` 一律顺带 `SET pending_clarification = NULL`（空候选写入必然是离开 pending 的迁移，语义安全）；真库验证显式进入后 `cleared=t` |
| T23-9 | P3 | Router.reject() 携带的退出候选是死数据（apply 转异常后丢弃） | 登记：T2.4 若需 API 响应携带恢复选项再启用，当前不误导 |
| T23-4 | P2 契约确认 | **显式切换（IN_SCENARIO→IN_SCENARIO）不走 pending_confirm 直接生效**：规格 §3.2 只规定了 inherit 越界走 pending；显式切换语义未定 | 按 §5.7 manual 语义实现「已授权+已发布即可显式切换」，并在迁移表登记同态切换；**登记待 T2.4 复核**——对抗探针（T5.2）须覆盖「场景内直传其他场景 ID」，若验收判定需要确认流，升迁移表为 pending |

## 5. 复核口径

- **路由是纯函数**：决策与持久化分离，瀑布接线（T2.4）只做输入组装与输出去向，不再内嵌业务判断。
- **闸门优先于完成度**：T2.3 完成不等于路由启用；启用条件以 ADR-0004 核对记录为准，不因代码就绪而放宽。
