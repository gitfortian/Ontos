## 3. 发现与处置

| # | 级别 | 发现 | 处置 |
|---|---|---|---|
| R-A | P3 表述（更正） | **首次审核 T15-1 的机制理由不成立**：原文称「只过滤 cohort 会把被过滤主体的后续行为算回转化」，但 `step_N` 是 `INNER JOIN cohort ON cohort.subject = event.customer_id`——主体集合在 JOIN 时已被限定，step 再加同一组主体维度条件是**语义冗余**，不是正确性必需 | **更正**：实现的正确性依据改为「满足规格 §3『每个步进 CTE 的 WHERE 追加同一组过滤条件』的字面要求 + 纵深防御（防后续重构把某一步改成不派生自 cohort）」；不夸大原结论，代码不变 |
| R-B | P3 输入卫生（登记） | `validateFilterValues` 只校验值与算子数量，不拒绝 **null / 空白值**：`values:[null]` 会走到 `field.eq((Object) null)`（jOOQ 渲染 `is null`），`values:[""]` 生成 `= ''`——两者都**静默返回空结果**而非拒绝 | **登记（跨模式）**：修它会改变 QUERY / YOY_MOM 的既有行为（从「静默空结果」变「明确拒绝」），属全局输入卫生收口，需单独立项并补全模式回归；本次不夹带 |
| R-C | P3 确定性（登记） | 编译产物对 **filters 顺序敏感**：同一组条件换序会生成不同 SQL（缓存键含 `queryParameters` → 不命中，不影响正确性）。「同输入同输出」仍成立 | **登记**：与 QUERY 同型；若将来做缓存命中率优化，按规范化排序处理（需 ADR，因为会改 SQL 逐字 Golden） |
| R-D | 确认无问题 | filters 维度**确实进入策略判定**：`prepareWith` 遍历 `queryDsl.getFilters()` 走 `DIMENSION` 策略 check 并进敏感收集器（比分组维度多一层）；`limit` 与 filters 叠加无新风险；多租户由 RLS 承担 | 无需处置；敏感 guardrail 未含 filter 维度一项维持 T15-2 登记 |
