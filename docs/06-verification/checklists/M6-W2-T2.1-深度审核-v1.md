## 1. 结论

**通过。** V15 在三张生命周期表 + `audit_log` 十一列扩展上按规格落地，ArchUnit 新增两条边界规则并通过；模块边界与「运行时只读清单、不依赖 catalog」一致。审核发现 3 项 P2：发布时间约束在 retire 时丢时间戳、JSONB 列缺少形状闸门、ArchUnit 规则未做故障注入验证；三项均已在提交前修复/验证。

| 核对项 | 结论 |

## 3. 发现与处置

| # | 级别 | 发现 | 处置 |
|---|---|---|---|
| T21-1 | **P2** | 首版 `CHECK ((status='published') = (published_at IS NOT NULL))` 会在 `published → retired` 时**强制清空发布时间**，审计丢失发布时点 | 改为两条约束：`published/retired 才允许非空` + `published 必填`；本地回滚 V15（drop 表/列 + 删 flyway 历史）后重放，验证 retired 保留时间戳、draft 带时间戳被拒 |
| T21-2 | P3 | `updated_at` 仅默认值，无触发器自动更新 | 与 `rule` / `copy_template` 同规，由应用层写入；T2.2 服务实现时统一设置，不引入 DB 触发器 |
| T21-3 | P3 | 生命周期表无版本历史行 | 与 ADR-0004 §2.3 rule 表同构；回滚以清单历史（不可变）为依据，不复制版本表。T2.2 回滚实现须从清单读取旧版本，不得依赖本表 |
| T21-4 | **P2** | **JSONB 列无形状闸门**：`definition` / `dsl_template` / `params_schema` 写入 `"scalar"` / `[]` 也会被接受，错误形状要到下游解析才炸 | 补 6 条 CHECK：scenario definition 必须 object；skill 两个数组列必须 array；vqr dsl_template/params_schema 必须 object、invalidation 必须 array。真库 3 个错误形状全部被拒 |
| T21-5 | **P2** | **只验证了「升级库」，没验证「全新库」**：V15 依赖 V1 的 audit_log，若前序迁移有缺口，新环境部署才会暴露 | 建空库 `ontos_migtest`，单会话按 V1→V15 顺序执行 **14 个迁移全部成功**；核对三表 12 条 CHECK、audit 11 列；验证后删库 |
| T21-6 | **P2** | **ArchUnit 规则只证明「不违规时通过」，没证明「违规时会拦」** | 故障注入：在 server 测试源临时放 `com.ontos.module.query` / `ontology` 两个引用 catalog 的探针类，`ArchitectureTest` 精确报出两处违规；删除探针后 9 条规则复跑通过 |
