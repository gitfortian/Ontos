## 结论

**通过。** 注册制四要素落地：清单 skills 段是资产源（published 才可执行）、implementation_ref
去版本前缀解析内置 handler（注册但无映射 = fail-closed 拒绝）、受控工具注册表能力判定、
编译期校验四条全部先于 handler 解析。**M3 回归不回退**：`/skills` 列表与 entity_lookup 执行
契约保持（list() 仍只列可执行能力，skillId 无前缀命名保留）。

## 发现与处置

| # | 级别 | 问题 | 处置 |
|---|---|---|---|
| T32-1 | P2 | **list() 双键重复**：entity_lookup 声明两个命名空间（LOOKUP.entity + LOOKUP_BATCH.batch）后 `handlersByBuiltinRef.values()` 把同一 handler 迭代两次，/skills 列表出现重复条目 | list() 按 skillId 去重（Map.putIfAbsent）；回归断言锁定 size=1 |
| T32-2 | P2 | **清单 v14 的 skillId 命名失配**：规格 v1.4 §5.8 示例用 `skill.entity_lookup` 前缀，但 M3 运行时实际是 `entity_lookup`——照抄示例会让既有执行链路 404 | v14 对齐实际运行时命名 `entity_lookup`（回归保护优先于规格示例——规格示例是示意，进度留痕） |
| T32-3 | P2 | **未知能力测试的 stub 缺口**：executeSkill 改为清单驱动后先查生效清单——原测试只 stub 了 validateManifest，getActiveManifestOrNull 返回 null → 报 MANIFEST_NOT_FOUND 而非 DSL_INVALID（失败但暴露了校验顺序：空清单时业务整体不可用，行为正确） | 测试补 stub；行为本身正确（空清单 fail-closed 先于能力判定） |
| T32-4 | P3 | rule.evaluate 的判定源是「清单 rules 段存在 published」——规格原文是「Rule 注册中心**可用**且规则已发布」；清单源是可用性的静态代理，运行时 Rule 服务健康检查未接 | 登记：T3.3/T5.x 编排接线时把健康探测并入受控注册表；当前清单代理对首发部署形态足够 |
