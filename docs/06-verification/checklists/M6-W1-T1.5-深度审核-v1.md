## 1. 范围与方法

**代码范围**：`DslValidator.validateFunnel`（移除 filters 拒绝 + 主体表校验 + 值数量校验）、
`SqlCompiler.compileFunnel`（filters 条件构造；cohort 与每个 step CTE 同时 JOIN 主体表并追加条件）、
`FunnelValidatorTest`（旧的「拒绝 filters」用例改判为「接受主体维度过滤」+ 2 个越界负例）、
`FunnelCompilerTest`（2 个编译断言）、`scripts/verify/m6-golden.mjs` 的 funnel 段。

**方法**：① 规格 §3 逐条对照；② 攻击者/边界（非主体维度、未发布维度、值数量不符、时间维度）；
③ 人工审阅编译产物；④ 真库「有过滤 vs 无过滤」对比；⑤ 全量基线 + M2/M3/M6 三段 Golden 回归。

## 2. 结论

**判定：通过**（1 项设计要点落实 + 3 项登记）。

### 2.1 规格逐条对照

| 规格条款 | 实现 | 结论 |
|---|---|---|
| 放开顶层 filters = 全局过滤，与 QUERY 语义一致 | `validateFunnel` 接受 filters；编译器把它并入条件集合 | 符合 |
| **每个步进 CTE 的 WHERE 追加同一组过滤条件** | cohort 与每个 `step_N` 都 JOIN 主体表并追加同一组条件（不是只过滤 cohort） | 符合（见 T15-1 说明） |
| 不引入步级过滤 | 无步级字段，filters 只存在于顶层 | 符合 |
| filters 字段复用既有 FILTER 结构，`fieldId` 须为已发布维度且映射表经路径可达 | `semantic.requireDimension` + 主体表等同校验（`FUNNEL_DIMENSION_UNSUPPORTED`）+ `validateFilterValues` | 符合 |
| `time_expression_raw` / `cohort_window` 仍由 analysisParams 承担，filters 不承接时间语义 | filters 无时间通道；时间维度映射订单/事件表，被主体表校验天然拒绝 | 符合 |
| 正例 + 越界负例 ≥4（§5） | Golden funnel 段 **2 正 + 3 负**（非主体维度 / 未发布维度 / EQ 值数量不符） | 符合 |

### 2.2 关键设计点（T15-1）

**只在 cohort 加过滤是不够的**：`step_N` 按 `subject` 与 `cohort` 关联，但事件扫描本身不带主体属性条件——若不过滤，
「被过滤主体」的后续行为会被关联回 cohort 的 subject（同一 subject 已被排除时不会，但若 cohort 因其它条件保留了该主体、
而 filter 条件在 cohort 未生效时会漏）。为了让规格「所有步进 CTE 共享 WHERE」成为可验证事实而非近似，
实现选择**在每个 step CTE 都 JOIN 主体表并追加条件**，并用单测断言 `"customer"."tier" = ?` 精确出现 2 次
（cohort + step_2），防止后续重构退化成「只过滤 cohort」。
