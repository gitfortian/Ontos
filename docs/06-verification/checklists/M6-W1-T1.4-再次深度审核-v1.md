## 1. 复审视角与方法

与首次审核（规格对照 + 边界 + 真库）不同，本次按四类视角重走：

1. **契约精读**：逐字重读 §2.2 八项，特别核对「UNATTRIBUTED 桶只收已知主体的无触点转化」这一限定语；
2. **故障注入**：渠道主数据缺失 / 触点 `channel_id` 为空 / 转化 `order_id` 为空 / 同订单多条转化事件 / 触点时间为 NULL；
3. **攻击者视角**：换掉 `metricId` 为未开放 ATTRIBUTION 的指标、`subjectPropertyId` 指向非主体属性、重复维度、limit 截断桶；
4. **性能与机制**：相关子查询的索引依赖、缓存键是否覆盖时间窗（查明 `queryParameters` 含回填后 timeRange + `timeAnchorDate`，无跨期复用风险）。

## 3. 发现与处置

| # | 级别 | 发现 | 处置 |
|---|---|---|---|
| R-A | **P2 语义（已修）** | **`UNATTRIBUTED` 判定错位**：首版用 `coalesce(channel_name, 'UNATTRIBUTED')`，把「**有触点但渠道主数据缺失**」的转化也算进无触点桶——违反 §2.2「该桶仅收已知主体的无触点转化」；同时 `touched_events` 按 `channel_name is not null` 计数也会少计。这类数据（触点渠道 id 在 channel 表无对应行）不会报错、只会静默改口径 | **已修**：`attributed`/`facts` 透出 `attributed_channel_id`；桶改为 `case when attributed_channel_id is null then 'UNATTRIBUTED' else coalesce(channel_name, attributed_channel_id) end`（有触点但主数据缺失时回退显示渠道 id，可诊断）；`touched_events` 改按 `attributed_channel_id is not null` 计数。Golden 重新回填、真库复验结果不变（正常数据无触点缺失） |
| R-B | P2 性能（登记） | `event` 表仅有主键与 `tenant_id` 单列索引；归因的 last_touch 相关子查询按 `(customer_id, event_type, occurred_at)` 过滤，真实规模下会退化为「按租户全表扫描 × 转化数」 | **登记**：归 W5/T5.1 压测出真实规模结论并评估复合索引（`(tenant_id, customer_id, event_type, occurred_at)`）；当前 demo 数据量未触发，M6 前不动 Query DS 表结构 |
| R-C | P3 口径（登记） | 同一订单存在多条同类转化事件时，`converted_events` 按事件 id 计、指标值按转化行累加 → 会重复计入 | **登记**：§2.2-3「每笔转化独立归因（订单/事件粒度）」按事件粒度实现属契约行为；重复事件属数据质量问题，由 M7 评测的 data-quality 断言兜底 |
| R-D | P3 一致性（登记） | `dim.channel` 输出值取 `channel.name`，而 QUERY 模式该维度取 `orders.channel` 冗余列；两者值域需一致（当前 seed 一致）。若漂移，同一维度 ID 会出现两套值 | **登记**：随 T2.2 的清单发布校验补「渠道主数据 name 与订单冗余列值域一致性」检查项；当前不做隐式转换 |
