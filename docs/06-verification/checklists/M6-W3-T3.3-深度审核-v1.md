**通过。** 近似降级机制全链路闭环：预声明（清单 `approximationOf`）→ 触发（场景模式拒绝时查近似承担者）→

+ originalMode）。**真服务端到端 3/3**：场景确认闭环（T32-8 修复验证）、近似降级执行（query 终端、
真实数据行）、审计落库（originalMode=funnel 留痕）。

## 发现与处置（端到端驱动）

| # | 级别 | 问题 | 处置 |
|---|---|---|---|
| **T32-8** | **P1** | **场景确认断链（ask 全链路）**：编排只消费澄清候选（清 pending），**从未调 `confirm` 做状态迁移**——pending_confirm 确认后永远不进 in_scenario（T2.4 端到端只验到 pending 落库，没验确认后迁移） | 消费点按前缀分流：`scenario:` → confirm（授权集 + published 再校验 + 迁移）；`approx:` → 近似执行。端到端验证确认 → in_scenario |
| T33-1 | P2 | **候选覆盖**：`TerminalAssembler.persistClarification` 把透出候选（assetId 槽放了 candidateId）覆盖写入，破坏场景通道写的正确候选（confirm 的 `scenariosById.get(assetId)` 必然 miss → 1004000003） | persistClarification 跳过 scenario/approximation 类型候选 + **空列表早退**（初版过滤后仍空覆盖写 NULL，二次修复） |
| T33-2 | P2 | **近似同意轮被新歧义澄清拦截**：同意轮检索产生新澄清 → planner 优先 clarification 提案 → 近似分支拿到非 query 提案 | planner 增 `approximationConsumed`——同意轮跳过歧义澄清（用户已决策） |
| T33-3 | P2 | **槽位词表不一致**：编排透传整盒提案槽位（含 analysis_mode/filters）→ QuerySkill 白名单拒绝 | QuerySkill 槽位对齐提案词表（snake_case + analysis_mode 忽略）+ 编排**精确挑选**近似槽位（不透传整盒） |
| T33-4 | P2 | **近似消费取 assetId 为 null**：M5 `consumeClarificationChoice` 返回的 candidate.assetId 恒 null（record 构造只填 candidateId） | approxSkillId 从回传键剥前缀（`approx:<skillId>` 即承担者 ID） |
| T33-5 | P3 | **FUNNEL 提案触发端依赖 LLM**（确定性 planner 只产 query/lookup）——端到端的近似触发用手工候选构造，同意→执行→审计段已真服务验证 | 触发端机制已单测覆盖（approximationCarriersFor 三过滤）；LLM 提案 E2E 待模型可用后补（登记） |

## 教训（审核留痕）

1. **候选持久化双通道冲突**：场景通道（PendingChoice.assetId=裸 ID）与透出层（RetrievedCandidate.assetId=candidateId）写同一 JSONB 列——语义不同的候选不允许互相覆盖，persistClarification 按类型分流 + 空早退；
2. **端到端驱动修复**：T32-8/T33-1~4 全部由真服务验证暴露，单测 fixture（全带 skills 段/正确候选）测不出集成裂缝；
3. **M5 consume 返回值不可用**：ClarificationCandidate.assetId 恒 null——消费后需要 asset 信息时从回传键推导。
