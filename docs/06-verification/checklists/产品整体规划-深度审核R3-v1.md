## 0. 审核范围与方法

**范围**：从「用户打开产品」到「上线给真实用户」的全链规划——roadmap M0–M8、上位方案 v1.4 的上线检查（§18）与最终验收（§19）、M7 挂账口径（ADR-0019）、M8 两包（产品前端规格已冻结 / 上线与规模化未立规格）、E-7 在途工作、以及上述全部与仓库实际状态（代码、证据、台账）的一致性。

**六维方法**：
① **账实相符**——冻结/活文档的表述 vs 实际证据；
② **交付链完整性**——用户视角端到端（登录→对话→模型→数据→治理），每环必须有任务归属；
③ **上线门禁覆盖度**——§18 五大清单（功能/安全/可审计/可靠性/运营）与 §19 八条逐条对照归属；
④ **新发现风险归属**——E-7 期间暴露的四个新风险（workspace P1、token 超预算、降级路径、取值词表）是否有决策载体；
⑤ **评测口径纪律**——×3 轮跑之前口径是否冻结（对应规划风险 R7「门槛先冻结」）；
⑥ **规划盲区扫描**——产品运营面（非工程能力项）是否被任何里程碑覆盖。

## 1. 总评

**主体判断：骨架健康，问题集中在两个区域。**

「定顺序、定边界、定闸门」的 roadmap 纪律在 M0–M7 得到了**可审计的执行**——每阶段验收报告 + 证据链 + ADR 留痕、并行义务 `deferred 0`、九个阶段无一「口头通过」。这不是客套：对照 v1.4 §19 八条，「确定性 / 权限安全 / 可审计 / 版本可复现」四条已有实打实的证据支撑（Golden 逐字一致、对抗五类 0 违规、审计回放、全版本锚定）。

问题集中在：
- **(a) M7 收口之后 E-7 快速推进造成的台账漂移**——ADR-0019 与 M7 报告 v1 写「T2.1–T2.4、T3.2 全部未开工」，实际 T3.2 已 6/6 全拒完成、T2.1/T2.2/T2.4 完成、T2.3 部分完成（F-1）；**×3 轮的运行口径至今未冻结**（F-2）——这直接违背本项目自己立的 R7「门槛先冻结」纪律；
- **(b) 「引擎近尾声」暴露的产品运营面归属缺口**——上线前真正欠的不是编译器和评测，而是 workspace 隔离（F-4）、成本路线（F-3）、降级路径质量（F-5）、用户口径发布流程（F-6）、数据接入边界（F-8）、租户运营面（F-9）——**这些在 roadmap M8 行「网关/部署/灰度/SLO/灾备」的工程清单里大多没有名字**。

12 项发现中 4 项 P1 全部落在这两区。**结论：规划不需要推翻，需要的是「收口期的账实同步 + M8 上线包立项补全」。**

## 3. 逐项展开

### F-1（P1）台账账实漂移：C-2 实质已闭环，台账仍写「未开工」

- **实际状态**（E-7 启动后已提交的证据链）：
  - T2.1 锚定：[模型服务锚定 v1](../evaluation/模型服务锚定-v1.md) 已冻结（mimo-v2.6-flash，三件套就绪）；

  - T2.3 对比：[LLM 对比降级路径证据 v1](../evaluation/LLM对比降级路径证据-v1.json)（265 配对，34.7% vs 10.6%，McNemar χ²=53.6 p<0.001）——**部分完成**（单轮口径，×3 全量对比随 C-1）；
  - T2.4 代理表：意图一致率代理口径已计算（部分集：指标命中率 17.5%、时间命中率 88.7%、过澄清率 47.2%）；

**影响**：① 发布门禁的真实阻塞面被台账高估（C-2 已闭环，只剩 C-1）；② 负责人若按台账做预算/排期决策，建立在过时事实上；③「5 个工作日」时限的起算点实际已过半（锚定 2026-11-11 完成，T2.x 主体完成）。

**裁决与处置**：

- ADR-0019 与 M7 报告 v1 是**冻结文档**，不得原地改——按纪律等 C-1 收口后一次性升 v2；中间态账实差异以本审核文档 + 进度快照 §16–§19 留痕承担「不误导」职责。若负责人希望在 ×3 之前也有正式口径，可选 ADR-0019 升 v1.1（纯账实同步，不改条件项语义）——列入决策批 D-A 附带项。

### F-2（P1）×3 轮评测口径未冻结——违背 R7「门槛先冻结」纪律的现行风险

**事实**：ADR-0019 C-1 写「test 集 ×3、分层 + Wilson……」**但未锁运行配置**。E-7 期间配置在四个维度上发生过变化：
1. 清单：v18 → **v19**（补「客户数/订单数」别名）；
2. 提示词：system.md v3（补分析模式段 + lookup/yoy/filter 示例）；
3. 候选域：`full`（全量词表）→ `retrieval`（= 对账口径，提示词与对账一致性修复）；
4. Agent 工作区：共享（12KB 记忆累积，P1 隐患配置）→ 一次性干净工作区。

不同组合的结果差到不能混谈：单轮全量 32%（v18+共享记忆）vs 定向 30 题 66.7%（v19+提示词 v3）vs 70%（判据 v2.1 重判）；token 31.2k → 15.9k。

**影响**：×3 是 C-1 的正式证据——若跑之前不冻结口径，① 结果与历史数据不可比（评测纪律 R7：门槛先冻结、集与 gold 带版本哈希）；② 跑完可被质疑「选了好看口径」；③ 共享 workspace 配置若被误用，等于把 P1 隐患写进正式证据。

**裁决建议（D-A，负责人拍板）**：冻结为——**清单 v19 + 提示词 v3 + 候选域 `retrieval` + 一次性干净工作区 + runner 判据 v2.1 + 30 题预演门槛（≥60% 才启动 ×3）**。冻结载体建议随 ADR-0019 v1.1 或 M7 报告 v2 附录；冻结后 ×3 的结果即正式口径，不再解释配置。

### F-3（P1）token 成本超冻结 SLO 两倍，处置决策缺位

**事实**：[SLO 与成本预算 v1](../evaluation/SLO与成本预算-v1.md) 冻结「单题 token ≤8,000（P95 ≤6,000），超限记 FAIL，不静默截断」。实测：v18 口径均值 **20.7k/题**；最优口径（干净工作区 + 检索域）**15.9k/题**——超上限 **2 倍**。SLO 自身预留了升版通道（「金额待 W2 模型确定后填，升 v1.1」）但**不改变 token 上限**。
当前处置是进度 §16 的「不追溯放宽、登记未达标 + 优化项」——但优化项（候选词表裁剪 / 提示词分段缓存 / 评测场景关闭 MemoryConsolidator）**没有任何任务编号、里程碑归属和负责人**。

**影响**：×3 跑出来的成本结论**注定 FAIL**（E6 真实模型口径 + E7 成本统计）——先花 9–10M token 跑完再决策，等于花大钱确认一个已知结果；这对 SLO 纪律本身也是伤害（冻结值被实测直接打穿而无正式处置）。

**裁决建议（D-B，二选一，×3 之前必须定）**：
- **路线 a（优化优先）**：立「成本压缩专项」——目标单题 ≤8k（P95 ≤6k）。候选手段按预期收益排序：评测场景关闭 MemoryConsolidator（实测每 ask 固定 +2 次调用）、候选词表裁剪（检索域已就绪）、提示词分段/缓存。验收 = 30 题复测 token 均值达标。预估 0.3–0.5M token 实验成本。**若达标，×3 结果全绿可能性大增**；
- **路线 b（SLO 升版）**：正式升 SLO v1.1/v2，把 token 上限改到实测水平并写明理由（产品接受单题成本、reasoning 模型特性）——纪律上允许，但等于把「未达标」制度化，且 8k 是产品成本承诺的一部分。
- **不建议**：不决策直接跑 ×3。

### F-4（P1）workspace 记忆隔离无决策载体

**事实**：进度 §19 登记 P1——`.agentscope/workspace/MEMORY.md` **全局共享、跨会话累积**（实测 12KB）：混杂所有用户/会话话术（多租户下 = 跨租户泄露向量；单租户 = 跨用户泄露），且含模型自总结的**错误协议**（编造错误码）污染后续会话，同时是输入 token 膨胀主因。当前载体只有两处非正式留痕：进度快照 §19 + [产品前端规格](../../03-plans/stages/M8/产品前端-实施规格-v1.0.md) W-B2 的一句「与 workspace 记忆隔离方案（P1）联动定档」。**没有 ADR、没有决策点编号、没有里程碑定档**——而它是 M8 多租户部署的硬前置。

**裁决建议（D-C）**：立 **ADR-0020**，三选一定档：
- a. 按租户（+用户）隔离 workspace 目录（隔离彻底，成本 = 目录管理与清理策略）；
- b. 默认关闭 MemoryConsolidator 记忆固化（最省、行为最稳，牺牲跨会话记忆能力——当前产品价值证据本就不足）；
- c. 保留但脱敏 + 定期清空（折中，脱敏规则要新立，复杂度最高）。
**建议 b**（评测与首版产品都不依赖跨会话记忆；上线后再按真实需求立 a）。与 W-B2（登录）联动：登录态上线后全局共享 workspace 即成活跃泄露面，**两者必须在 M8 发布前一起闭环**。

### F-5（P2）降级路径 10.1%，无处置决策

**事实**：[降级路径评测证据 v1](../evaluation/降级路径评测证据-v1.json)：同一 276 题题集，agent 关闭的确定性检索路径**严格通过率仅 10.1%**（大量澄清 + 从不设时间窗）。E-7 归因确认这不是评测判据问题，是路径自身欠账——**ask 降级路径从未按 276 题标准验收过**。当前只在证据与进度 §16 里登记，无处置决策。
**影响**：模型故障时的产品体验 = 90% 的问法得不到答案（fail-closed 但大面积澄清/拒答）。这是产品可用性的真实短板，也是「双保险」叙事的漏洞。
**裁决建议（D-E）**：二选一——a. 立优化任务（降级路径支持时间窗 + 澄清质量对齐，预估 2–3 天纯代码）；b. 接受为已知降级态，产品文案明确「模型不可用时能力受限」（零成本，但要在前端规格的拒答文案里体现）。**至少要选 b**（现状是既不修也不告知）。

### F-6（P2）§18 运营项「用户口径→资产发布流程可走通」无实现无载体

**事实**：v1.4 §11.5 定义了用户口径反馈到资产发布的流程入口；§18 运营清单明确要求「用户口径发布流程可走通」。代码检索 `ontos-module-*` 无任何实现（无 `caliber_feedback`/口径发布相关类）；roadmap M8 交付物清单（网关/部署/灰度/SLO/灾备）**不含此项**——即 §18 有这条门禁，但没有任何里程碑任务承载它。
**处置**：归 M8 上线规格（F-7）；最小闭环可以只是「失败看板纠正样本 → 人工审核进回归集」（M7/W4 已有）的产品化入口，不必做全自动。

### F-7（P2）M8 上线包规格未立——多数挂账项的归属容器缺失

**事实**：项目纪律（roadmap §7 注）：「进入每个阶段前单独产出该阶段的实施规格」。M8 事实上已是**两包**：产品前端（规格 v1.0 已冻结，D9 待落）+ 上线与规模化（**无规格**）。而 F-4（workspace 定档后的工程落地）、F-5、F-6、F-9、§18 逐条关闭、§19 八条报告、网关认证、灰度回滚、灾备、SLO 告警——全部应落在上线包，目前**没有容器**。
**处置**：工程批——按 M7 规格的格式起草「M8 上线与规模化-实施规格 v0.1」（决策点 + 任务分解 + E 判据），把本审核 F-4/5/6/8/9/12 逐项写入对应工作包。建议在产品前端 W0–W2 期间起草，不阻塞前端。

### F-8（P2）真实数据接入与新鲜度：未声明的前提依赖

**事实**：全链运行在 demo seed（ontos / ontos_queryds 双库）；「数据从哪来、怎么更新、新鲜度对用户如何呈现」**没有任何里程碑覆盖**；v1.4 §2.3 非目标清单也未把「数据接入/ETL」列为非目标（列的全是能力类非目标）。
**影响**：产品上线给真实用户时，这是第一个被问到的问题（「数据是什么时候的」——前端十问法有呈现位，数据侧无治理位）。若 Ontos 定位是「平台、数据接入是客户侧前提」，也应当**显式声明**，否则就是隐式盲区（和产品前端盲区同构）。
**裁决建议（D-F）**：确认产品边界——数据接入/新鲜度治理在范围内（M8 上线规格立任务）还是范围外（M8 上线规格显式声明为前提依赖 + 前端十问法文案口径）。

### F-9（P2）用户/租户运营管理面无归属

**事实**：当前身份靠请求头注入（X-Ontos-Tenant/User）；M4 交付了策略快照/审批/审计的**判定**能力，但「开户、改角色、改资产授权」的运营流程（哪怕是最小路径：SQL 脚本或极简管理页）没有规划。产品登录（W-B2）上线后，账号从哪来是运营第一天的问题。
**处置**：归 M8 上线规格（首版最小运营路径即可：预置账号脚本 + 策略快照更新流程说明）。

### F-10（P3）根 README 基线漂移——**当场修复**

实测（本轮 `check-docs` + surefire 汇总）：`mvn test` **668**（README 写 658——候选域收敛 +4）、docs **153 文档 / 1513 链接**（README 写 148/1477——产品前端立项 +5 文档）。**本轮已修**（见 §5）。根因是 E-7 高强度迭代期提交以证据为准、README 更新滞后两次提交——**收口期文档同步纪律要前置**（列入教训）。

### F-11（P3）roadmap M8 行未反映产品前端包

已知项（D9 待定档），不算新发现；列入 D9 落定动作清单：M8 行改「产品前端（[规格 v1.0](../../03-plans/stages/M8/产品前端-实施规格-v1.0.md)）+ 上线与规模化」两包表述 + 本轮 F-7 的规格立项时点。

### F-12（P3）「澄清质量评分可采集」无口径

§18 要求「澄清质量评分可采集」；现状有澄清**量**统计（过澄清率 47.2% 等）但**质量评分**（候选相关性、默认建议采纳率等维度）未定义冻结。低优先，归 M8 上线规格（可先用「澄清后 1 轮内转 query 终态率」做代理）。
