## 0. 定档与外部参考

### 0.1 立项理由（负责人 2026-11-13）

负责人定调：**OpenBKN 的「数据源与建模完全拆开」思想要主动借鉴，这是产品走向成熟的必要**。据此把触发点从「被动出现」（B0 §11 D-3：第二数据源承载业务查询 / 多事实表同指标 / 第二种方言时才启动）改为**主动建设**。偏离登记见 [ADR-0026](../../../01-decisions/ADR-0026-数据视图层引入与B0触发点提前.md)——不是推翻 B0 D-3 的结论，而是把启动条件从「问题出现」改为「负责人决策」，**事实粒度 / Join Path / SQL 方言三面仍维持触发点纪律不变**（见 D4）。

### 0.2 OpenBKN 蒸馏（2026-11-13 二次阅读 bkn-studio / bkn-samples 供应链样例）

| 思想 | OpenBKN 做法 | 本规格落点 |
|---|---|---|
| 双网络产品级拆分 | **领域知识网络**（对象/关系/指标/行动）与**数据资源知识网络**（连接/Catalog/数据视图/索引）是两个独立模块；建模界面不出现主机/端口/表名，对象详情只显示「关联资源名称」 | 数据源页升级为资源侧工作区（连接 + 数据视图）；建模页列选择器改「视图资产选择器」——建模人员只见视图资产名 |
| 扫描产物资产化 | Catalog Discover 把连接里的表固化为**数据视图资源**（可检索、有状态、有构建任务），不是实时摸库 | 扫描结果固化为 `data_view` 资产（列快照 + contentHash），目录浏览保留但建模引用一律走视图资产 |
| 唯一接触点 = 绑定 | 对象类 ↔ 数据视图（`bind_kn_resources.py` 先 `--dry-run` 校验 `bind:true` 全部可解析，再正式落） | 绑定校验规则：`viewId` 存在 + `column` 在视图列快照中；草稿校验与发布校验同一套规则 |
| 资源侧独立治理 | 连接/凭据/扫描/索引全部在资源网络管理，领域侧零感知连接轮换 | 凭据已在 B2（ADR-0025）；视图列漂移经重扫描更新，运行时仍锚定清单快照 |

**不借鉴（写死，防被「对齐 OpenBKN」带回）**

| 不借鉴 | 理由 |
|---|---|
| 资源全文/向量索引层 | Ontos 是 NL→DSL→SQL 的确定性问数，检索走 MentionIndex（语义资产的 name/aliases），不需要对物理目录做 RAG 索引 |
| 事实粒度 / Join Path 声明进资源层 | B0 §11 D-3 触发点纪律不变：多事实表同指标或第二方言出现时再议（§8.4） |
| Action / 行动层 | 同 B1 §0.2 口径：Ontos 不是动作执行平台 |

### 0.3 定档决策（负责人 2026-11-13 确认：「按建议来」——D1–D4 全部按建议案生效）

| # | 决策 | 建议案 |
|---|---|---|
| D1 | 视图资产生命周期 | **资源事实即时生效 + 发布快照进清单**：`data_view` 表 active/retired 两态（不走语义资产四态）；资源侧创建/更新即时生效于校验与建模选择；合成发布时把当前 active 视图集合**快照**进新清单（保持清单不可变 + 运行时封闭）。理由：视图描述物理世界，物理变了视图就该更新，无需人工审核；但运行时确定性要求映射锚定清单 |

| D3 | 建模入口改造 | 建模页信息项的列选择器改为「**视图资产选择器**」（先选视图 → 再选视图内列，来自快照而非实时摸库）；数据源页保留目录浏览（资源侧功能），「建信息项」改为「固化视图（如未固化）→ 预填 viewId + column」 |
| D4 | 范围边界 | 本期**不含**：资源索引层、事实粒度声明、Join Path 声明、按源执行（datasetId 执行链）、密钥轮换。三面触发点维持 B0 D-3 纪律 |

### 0.4 深度评审修补留痕（2026-11-13，外部 agent 评审 4 条 + 本会话逐条核实）

| # | 评审意见 | 核实结论 | 处置 |
|---|---|---|---|
| P0-1 | 视图列漂移（rescan）与已发布清单的冲突处理未定义 | **部分成立**。核心语义其实已自洽：运行时锚定清单旧快照（含旧列快照）不受漂移影响；新草稿引用已删列被 R-View 2 拒。**真实缺口**：rescan 的 diff 结构与「被引用列被删」的管理面告警/阻断 UI 未定义 | §3.2 rescan 契约补 diff 结构与漂移三级处置；§4 T7 补红框提示 |
| P0-2 | datasource 模块扫描需要 query 模块的连接池，存在跨模块依赖/循环依赖风险 | **不成立**（对 B2 已实现代码的误读）。事实：扫描连接由插件**自持**——`JdbcDataSourcePlugin` 走 `DriverManager` 短连接（connectTimeout=10s 显式声明），不进池、不经执行链；datasource 模块 pom 仅依赖 common/spi/ontology（PublishGuard 接口）/starter-web；**ArchUnit 已禁止** datasource → query/system/session/agent/catalog 依赖并全绿。评审建议「由 query 提供 DataSourceMetadataService」反而会制造被禁止的依赖方向，不采纳 | §2 补「模块依赖边界」澄清，防实施者被带偏 |
| P1-1 | 迁移列快照不应强依赖现网扫描，应从 v22 清单反推 | **成立，理由修正**。评审以「防 E1 失败」为由——方向错位：E1 判据是 SQL 字符串逐字等价，只消费 `view.table + property.column` 两个字符串，列快照**不参与 SQL 生成**。真正理由是**引用完整性**：若测试库结构不一致，扫描快照缺列会把迁移后的 v22 资产判死于 R-View 2 | §3.4 迁移改为「v22 清单反推初始快照（列名集合，物理类型空缺标注 unknown）+ 真实扫描仅作 enrichment 补类型/hash」 |
| P1-2 | 视图 ID 命名规范缺失（`dwd_order_info` 类物理名直接进 ID） | **成立** | §3.1 补视图 ID 生成规范：默认按物理名规范化生成（小写/非法字符转下划线/超长截断加 hash 尾），创建时可手改；name 必填为业务名 |

## 1. 范围与不做的事

### 1.1 范围

1. **数据视图资产**：`data_view` 表（V23）+ 扫描固化（从注册数据源 / 当前查询库）+ CRUD + 列快照与 contentHash + active/retired 生命周期。
2. **清单 `dataViews` 段**：`ManifestPayload` 新增段；合成发布快照当前 active 视图集合；发布校验新增视图规则（R-View 1–3）。
3. **`Property` 引用升级**：`column`（限定名）→ `viewId + column`（裸名）；草稿/发布/编译三处契约同步；旧形态 `column` 限定名**退役**。
4. **编译链改造**：`SqlCompiler` 等 `tableOf(property.column)` 调用点改为 `viewOf(property.viewId).table`；新增 `DataViewResolver`（清单 dataViews 段解析，模式对齐 `BindingResolver`）。
5. **绑定校验**：R-View 1（viewId 存在）/ R-View 2（column 在视图快照中）/ R-View 3（视图 retired 后不可被新草稿引用），并入 `ManifestStructureValidator` 既有 Violation 通道（不为 R-View 新增专用错误码，沿 B0 口径）。
6. **前端**：数据源页新增「数据视图」分区（扫描向导 / 列表 / 列快照详情 / 状态）；建模页列选择器改造；「建信息项」跳转预填升级为 viewId + column。
7. **迁移**：v22 → v23 清单迁移（六表视图自动生成 + Property 平移），Golden 三份 E1 逐字等价复验。

### 1.2 非目标（本期不做）

| 不做 | 归属 / 理由 |
|---|---|
| 按源执行（`datasetId` 化执行链、执行时按源选连接/方言） | Phase 2 后半（B2 §7）；触发点 = 注册源承载业务查询 |
| 资源全文/向量索引 | 不借鉴（§0.2） |
| 事实粒度声明、Join Path 声明 | B0 D-3 触发点纪律不变 |
| 视图列漂移的自动阻断 | 本期只「重扫描提示重新校验」；自动阻断涉及运行时保护，另立 |
| 视图 Join / 多表视图（跨表 Join 的逻辑视图） | 本期视图 = 单表/单视图镜像；跨表逻辑视图与 Join Path 一起留触发点 |

## 3. 设计

### 3.1 数据模型 / Schema

**视图 ID 生成规范（P1-2）**：ID 默认按物理表名**规范化生成**——小写化、`[^a-z0-9_]` 转下划线、连续下划线合并、超 40 字符截断并追加 6 位 hash 尾；创建时允许手改（唯一性由主键约束兜底，冲突报 `1_006_000_108` 同款）。`name` 必填为业务名（如「订单表」），UI 主显 name、ID 仅内部映射与审计。**禁止**直接使用未规范化的物理名（含大写/特殊字符/数仓前缀原样）作为 ID 尾段。

**V23 迁移：`data_view` 表**

```sql
CREATE TABLE data_view (
    id                TEXT        NOT NULL,           -- view.orders（前缀约束 ck_dv_id_prefix CHECK (id LIKE 'view.%')）
    name              TEXT        NOT NULL,           -- 业务名：订单表
    source_config_id  TEXT,                           -- 来源注册数据源（可空 = 当前查询库）
    source_schema     TEXT        NOT NULL,
    source_table      TEXT        NOT NULL,           -- 物理表名（编译唯一消费点）
    columns_json      JSONB       NOT NULL,           -- 列快照 [{name,type,nullable}]
    content_hash      TEXT        NOT NULL,           -- 扫描快照哈希（列集合+类型）
    status            TEXT        NOT NULL DEFAULT 'active'
                      CHECK (status IN ('active', 'retired')),
    created_by        TEXT        NOT NULL,
    created_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at        TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (id)
);
CREATE UNIQUE INDEX uk_dv_source ON data_view (source_config_id, source_schema, source_table)
    WHERE status = 'active';
```

设计说明：
- **两态生命周期**（active/retired）：视图是资源事实，不走语义草稿四态（D1）。变更 = 重扫描覆盖 columns_json/content_hash（updated_at 前进）；retired = 语义侧显式退役（仍被引用时拒绝，R-View 3）。
- **同源同表唯一**：同一数据源同一 schema 同表的 active 视图唯一（uk_dv_source）；重复扫描 = 覆盖更新，不产生新资产行。
- **不存凭据**：来源只存 configId 引用；凭据仍在 datasource_config（ADR-0025）。

**`ManifestPayload` 新增段（清单 dataViews）**

```json
"dataViews": [
  {
    "id": "view.orders",
    "name": "订单表",
    "schema": "public",
    "table": "orders",
    "columns": [ { "name": "id", "type": "integer", "nullable": false } ],
    "contentHash": "…"
  }
]
```

- 合成发布时把**当前全部 active 视图**快照进 payload（与 semantics 合成同一事务）。
- `Property` 结构升级：`column` 由限定名（`orders.amount`）改为 `viewId`（`view.orders`）+ `column`（`amount`）。旧字段形态在 v22 清单迁移后退役。

### 3.2 接口契约（datasource 模块 /data-views）

| 端点 | 说明 |
|---|---|
| `POST /api/v1/catalog/data-views/scan` | 扫描固化：入参 `{configId?|current, schema, table}` → 插件读列 → upsert `data_view`（同源同表覆盖更新）；返回视图 VO |
| `GET /api/v1/catalog/data-views` | active 视图列表（含列数、hash、来源） |
| `GET /api/v1/catalog/data-views/{id}` | 视图详情（含列快照） |
| `POST /api/v1/catalog/data-views/{id}/rescan` | 重扫描：列漂移检测 + 覆盖更新。**返回体必须含 `diff`**：`{addedColumns, removedColumns, typeChangedColumns, contentChanged}`；若 `removedColumns`/`typeChangedColumns` 中的列被**生效清单属性或待发布草稿**引用，响应带 `referencedRemoved` 列表（供前端红框告警） |

**列漂移三级处置（P0-1）**：
1. **运行时不动**：已发布查询锚定清单旧快照（视图列快照随 payload 快照化），漂移不影响运行中的编译产物——这是 D1 快照语义的直接推论；
2. **新引用 fail-closed**：rescan 后新草稿引用已删列 → R-View 2 拒（快照里没有就是没有）；
3. **管理面告警**：`referencedRemoved` 非空时，数据源页视图行亮红（「N 个生效属性引用的列已消失」），建模选择器中对应列标红禁选；**修复动作 = 语义侧修订属性（走既有草稿流）或恢复物理列**，本期不做自动阻断发布（登记后续项）。
| `DELETE /api/v1/catalog/data-views/{id}` | 退役（retired）：仍被生效清单属性引用时拒绝（引用检查走清单 payload） |

全部走 `PublishGuard` 管理面闸门。错误码沿用 1_006 段追加（视图不存在/重复退役等），**校验规则类不新增专用码**（沿 B0：结构校验只产 Violation，汇总 `PUBLISH_VALIDATION_FAILED`）。

### 3.3 关键流程

**扫描固化**：选源（注册源或当前查询库）→ 插件 `catalog.columns(schema, table)` → 生成/覆盖 `data_view`（contentHash = 列集合+类型的 SHA-256）→ 视图即时可用于校验与建模选择。

**绑定校验（沿 B1 合并视图机制）**：
- 草稿校验合并视图 = 生效清单 + 待发布批次（语义资产）+ **当前 active data_view 表**（资源事实即时可见）；
- R-View 1：`property.viewId` 在合并视图 dataViews ∪ active data_view 中存在；
- R-View 2：`property.column` ∈ 该视图列快照；
- R-View 3：引用 retired 视图的新草稿拒绝（retired 不在 active 集）。

**合成发布**：`SemanticAssetSynthesisService` 扩展——payload 合并时附 `dataViews` 快照（active 全量）；`PublishServiceImpl` 校验不变（R-View 并入结构校验）。

**运行时编译**：`DataViewResolver`（新，模式对齐 `BindingResolver`）从 `PublishedManifest.dataViews` 构建 `id → (schema, table, columns)` 映射；`SqlCompiler` 等处 `tableOf(property.column)` 全部替换为 `dataViewResolver.tableOf(property)`；缺失/歧义 fail-closed（编译错误码 1_002 段新增 `DATA_VIEW_MISSING`，沿 B0 先例的专用编译码口径）。

### 3.4 迁移与 E1 可构造性证明

v22 → v23：
1. 为清单引用的 6 张物理表自动生成 6 个视图资产（`view.orders` 等，schema=public）。**列快照初始来源 = v22 清单反推**（从全部 `property.column` 拆出「表 → 列名集合」，保证引用完整性、不依赖现网库结构——测试/生产环境不一致时 E1 与 R-View 2 都不会误伤）；物理类型标注 `unknown`，**真实扫描仅作 enrichment**（补类型与 contentHash，见 T6）。
2. 全部 `Property.column` 平移：`"orders.amount"` → `viewId="view.orders"`、`column="amount"`；`te.last_quarter` 等非属性引用不动。
3. **E1 逐字等价**：编译生成 `schema.table.column` 的字符串拼接改为 `view.table + "." + property.column`——迁移后 `viewOf(viewId).table` 与旧 `tableOf(column)` 对同一属性产出**相同字符串**，Golden 三份（27+6+10）逐字等价可构造（与 B0 同款证明模式，B0 已在 6 条路径实测逐字相等）。
4. cohort 路径（`eventTable` L434/477、attribution CTE L688）：event 表视图化后 `eventTable` 改由 `viewOf(event 属性的 viewId).table` 推导——同一字符串证明同样成立。

## 8. 冻结口径影响（逐条点名）

1. **E1 SQL 逐字等价**：受影响（正向保障，见 §3.4）——迁移验收的主判据。
2. **M2/M3 冻结**（Join+filters 双 CTE、validateMode 先于路径规划、聚合拒绝 lookup、rows 不带 __identity、lookup 同形、变体与指标同表）：**编译行为不变**——只换「property → 表名」的解析来源，SQL 字符串逐字相同，冻结口径全部保持。
3. **Mentions 索引**：property 的 name/aliases 检索不受影响（列/视图变化不进词库）。
4. **发布清单不可变**：保持——视图快照进 payload 后，同一 manifest_id 内容永不更新。
5. **v22 资产**：迁移平移，语义内容零改动（只有 column 拆成 viewId+column）。
6. **B0 D-3（Model 层非目标）**：由 ADR-0026 修订——**数据视图 = Model 层「逻辑数据集」子集先行**；事实粒度 / Join Path / 方言三面仍留触发点，不视为 D-3 失效。
