## 3. 设计

### 3.1 数据模型 / Schema

**清单 payload v2 结构**（`ManifestPayload` 扩展，版本兼容按 v1.4 §6.5——新增可选字段为小版本）：

```
payload
├── semantic            （现有：metric / dimension，扩展口径变体引用）
├── ontology            （现有骨架 → 扩展 Property / Relation / Constraint / Mapping / Event / Enum / Synonym）
├── rule[]              （ADR-0004 2.3：布尔判定规则，随清单冻结）
├── copyTemplate[]      （ADR-0004 2.5：原因码 → 文案，错误码只映射 template_id）
├── timeExpressionPattern[] （v1.4 §5.12 资产；解析器实现归 M2）
└── scenario[]          （元数据：entry_mode / scope / 关联资产；路由归 M6，M1 只校验引用完整性）
```

**资产真源与存储口径**（协调技术选型 §4.2「Git 为唯一可发布真源」与 ADR-0004 2.3「System DB rule 表」）：

- 资产真源 = 仓库内 `ontos-assets/` YAML 文件（Git 版本管理，草稿态）；管理界面/端点**只提交变更单与预检，不直写运行时表**；
- System DB 新增**审核工作台表**：`rule` / `copy_template`（`status = draft | reviewing | published | retired`，登记变更单与审核流），发布时以 Git 真源校验后冻结进清单；**M1 最小语义**：变更单只登记意图与评审结论，YAML 由开发者随 Git commit 提交，发布时校验「工作台已登记 ↔ YAML 实际内容」一致性，未登记的变更拒绝发布（闭环成立但不在 M1 造资产编辑器）；
- 运行时判定**只读清单快照**（进程内，与 ontology/semantic 一致），不读草稿表——草稿不得被查询运行时读取（v1.4 §5）；
- 新增 `publish_record` 表：发布人、时间、`manifest_id`、dry-run 报告引用、来源 commit；
- 不可变约束复用现有 `reject_published_snapshot_mutation` 触发器，零新增。

**Query DS 建模**（对照 ADR-0004「与 demo 清单的差距」表）：`customer` / `orders` / `order_item` / `product` / `event` / `channel` 6 表 + 演示数据；现有 `sales_order` 在首发清单发布后**退役为 PoC 夹具**（ADR-0004 结论）。

**本体元模型 Java 类型**：扩展现有 `SemanticManifest` / `OntologySnapshot` / `OntologyGraph`——关系边带类型、基数、方向、授权域、Golden Path 标注；`display_hints`、`existence_sensitive`、`lookup_projectable`、敏感等级、口语/拼音别名全部进类型（字段清单引用 v1.4 §5.2/§5.3，不在此复制）。

**业务化字段规范**（[业务化命名规格 v1](../../../04-specs/ontology-业务化命名-规格-v1.md)，双层命名：内部标准术语不动，对人只说人话）：每条资产必填 `name`（业务名）/ `summary`（一句话说明）/ `aliases`（常见叫法 ≥1），三个字段进清单、进检索词库、进澄清候选；资产描述不得出现标准术语与物理表名；数量关系以自然语言文案展示（1:N →「可以有多个」）；关系动词（正向/逆向）与变体并入关系资产。**业务化是功能不是装修**——业务表述即 #5 召回与 M5/M6 澄清的词汇来源。

### 3.2 接口契约

**保持不变**：`GET /api/v1/ontology/manifests/{current,id}`、`POST /api/v1/query/{compile,execute}`、审批/审计端点、`/agent/ontos`。

**新增（admin 域，身份由认证上下文保护，生产走网关）**：

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/v1/ontology/publish` | 发布：`{dryRun: boolean, sourceRef}`；dry-run 返回预检报告（校验违规清单），确认后 INSERT `published_snapshot` 并返回 `manifest_id + content_hash`。**fail-closed 说明**：M4 策略快照落地前，非 local profile 下该端点随全局策略默认 403（fail-closed），生产发布由网关授权的运维身份执行 |
| GET | `/api/v1/ontology/manifests/{id}/diff/{baseId}` | 两个清单的资产级 diff（新增/修改/ retired） |
| GET | `/api/v1/ontology/assets` | 按类型浏览已发布资产（metric/dimension/class/relation/rule/…） |
| GET | `/api/v1/ontology/impact` | 资产影响反查：引用该资产的清单、Rule、Scenario 元数据 |
| GET | `/api/v1/ontology/paths` | 规划调试（只读）：给定起止类返回路径候选或歧义标记，供探针与前端调试 |

**内部 SPI**：`OntologyPathPlanner.plan(fromClass, toClass, constraints)` → `PathCandidate[]`（唯一 / 并列歧义 / 无路径）；调用方（M2 编译器、M5 检索）只依赖该接口。

### 3.3 关键流程

**发布流水线**（技术选型 §4.2 落地形态）：

```
Git ontos-assets/ 变更 → 提交变更单（审核工作台） → POST /publish dry-run
  → JSON Schema 校验 + OntologyPublishValidator 强化（引用完整性/基数/Golden Path 正反样例/唯一键/资产下限）
  → 预检报告（违规清单，零违规方可确认）→ 确认发布 → INSERT published_snapshot（不可变触发器生效）
  → 副本按 manifest_id 加载校验哈希 → GET /manifests/current 验证 → publish_record 落审计
```

**路径规划**（v1.4 §7.3 的 M1 子集）：DSL 引用实体 → 按 domain 授权子图过滤 → 邻接表 BFS（跳数 ≤ 3，版本化）→ 类型/方向/基数/有效性校验 → Golden Path 优先 → 唯一路径输出；**路径并列返回歧义标记，不私自选择**（澄清交互归 M5）。

**请求状态机**（ADR-0004 2.2，8 态口径）：`RECEIVED → CLARIFYING/PROPOSED/REJECTED → …` 状态只由服务端推进；每次迁移落 `audit_log`（from/to/触发原因/request_id）；终态不可回退；同 `request_id` 幂等。

### 8.2 结构决策（2026-11-07，负责人已确认）

1. 模块布局：**扩展 `ontos-module-ontology`**（assets/publish/planner 按包隔离），不新增 `ontos-module-catalog`；M6 资产运营膨胀时再评估拆分并发新 ADR；
