## 3. 设计

### 3.1 数据模型

#### 3.1.1 为什么用统一表而不是像 V15 分表

V15 的 `scenario_definition` / `skill_definition` / `vqr_definition` 分表，是因为三者有大量**列级**约束（`entry_mode`、`analysis_mode`、`dsl_template`）需要 DB 层护栏。

五类语义资产的差异**全部落在 definition 内部**（concept 的 `identityProperty`、property 的 `column/valueType`、relation 的 `from/to`、metric 的 `aggregation/allowedModes`），生命周期字段完全同构。分表会产生五套几乎相同的 repository 与 service，且未来加 `event` / `rule` 还要再复制一次。故本规格用**统一表 + `asset_type` 判别列 + JSONB**，把差异交给 `ManifestStructureValidator`。

**代价与护栏**：DB 层无法对 definition 内部字段做列级约束，只有 `jsonb_typeof = 'object'` 形状闸门；字段级正确性由草稿校验与发布校验双重保证。这是有意取舍，§7 R1 给出拆表回退路径。

#### 3.1.2 V21 DDL（草案）

```sql
-- Ontos System DB：B1/W1 语义资产草稿表（B1 规格 §3.1）
--
-- 边界：本表只服务管理面草稿/评审；运行时仍只读已发布清单的 ontology / semantic 段。
-- draft / reviewing / retired 永远不得被查询运行时读取（与 V15 同规）。
-- 生命周期与 rules.status 同构：draft → reviewing → published → retired。

CREATE TABLE semantic_asset_definition (
    asset_type      TEXT        NOT NULL
                    CHECK (asset_type IN ('concept', 'property', 'relation', 'metric', 'dimension')),
    id              TEXT        NOT NULL,
    name            TEXT        NOT NULL,
    summary         TEXT        NOT NULL DEFAULT '',
    status          TEXT        NOT NULL DEFAULT 'draft'
                    CHECK (status IN ('draft', 'reviewing', 'published', 'retired')),
    owner           TEXT        NOT NULL,
    reviewer        TEXT,
    version         TEXT        NOT NULL,
    -- 乐观锁：每次 saveDraft +1；写入必须带 expectedRevision（B1 §3.3.3）
    revision        BIGINT      NOT NULL DEFAULT 0
                    CHECK (revision >= 0),
    -- 资产内容：结构与 ManifestPayload 对应段一致，由 ManifestStructureValidator 校验
    definition      JSONB       NOT NULL,
    published_at    TIMESTAMPTZ,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at      TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (asset_type, id),
    CONSTRAINT ck_sad_published_at
        CHECK ((status IN ('published', 'retired')) OR published_at IS NULL),
    CONSTRAINT ck_sad_published_at_required
        CHECK (status <> 'published' OR published_at IS NOT NULL),
    CONSTRAINT ck_sad_definition_object
        CHECK (jsonb_typeof(definition) = 'object'),
    -- 类型与 ID 前缀必须一致：拦住「类型填 metric、ID 写 dim.x」这类错位。
    -- relation 的 ID 前缀是 ontology.（历史命名，见 B0 影响分析 §2.4；
    -- 不改 ID 以免破坏 v22 引用锚点，故在此显式登记）
    CONSTRAINT ck_sad_id_prefix CHECK (
        (asset_type = 'concept'   AND id LIKE 'concept.%')   OR
        (asset_type = 'property'  AND id LIKE 'property.%')  OR
        (asset_type = 'relation'  AND id LIKE 'ontology.%')  OR
        (asset_type = 'metric'    AND id LIKE 'metric.%')    OR
        (asset_type = 'dimension' AND id LIKE 'dim.%')
    )
);
CREATE INDEX idx_sad_type_status ON semantic_asset_definition (asset_type, status);
CREATE INDEX idx_sad_updated_at ON semantic_asset_definition (updated_at DESC);
COMMENT ON TABLE semantic_asset_definition IS '语义资产草稿/评审生命周期（管理面）；运行时只读已发布清单';
COMMENT ON COLUMN semantic_asset_definition.definition IS '资产内容 JSON（concept/property/relation/metric/dimension 各自结构）；字段级校验由 ManifestStructureValidator 承担';
COMMENT ON COLUMN semantic_asset_definition.revision IS '乐观锁版本；saveDraft 必须携带 expectedRevision，冲突返回 1_005_000_104';
COMMENT ON COLUMN semantic_asset_definition.published_at IS '发布时间；published 必有、retired 保留、draft/reviewing 必无';
```

#### 3.1.3 字段口径

| 字段 | 口径 |
|---|---|
| `name` / `summary` | 从 definition 顶层冗余，供列表查询；由 service 在 `createDraft` / `saveDraft` 时解析写入，不作为真源（不采用 V15 的 `syncDefinition` 回写：语义资产 definition 内没有 status/owner 字段可同步） |
| `version` | 资产语义版本，创建时缺省 `0.1.0`；P0 不递增，发布时由 P1 决定 |
| `revision` | 仅用于并发控制，与 `version` 无关 |
| `reviewer` | `submitReview` 不写；`review` 通过时写（P1） |
| `published_at` | P0 不会出现 published 状态，约束按 V15 预留 |

### 3.2 接口契约

#### 3.2.1 端点总表

| 方法 | 路径 | 用途 | P0 |
|---|---|---|---|
| POST | `/api/v1/catalog/assets/{assetType}/drafts` | 创建草稿 | 是 |
| PUT | `/api/v1/catalog/assets/{assetType}/{id}/draft` | 保存草稿（带 expectedRevision） | 是 |
| GET | `/api/v1/catalog/assets/{assetType}/{id}` | 草稿详情 | 是 |
| GET | `/api/v1/catalog/assets/{assetType}` | 列表（status / keyword 过滤，分页） | 是 |
| POST | `/api/v1/catalog/assets/{assetType}/{id}/validate` | 校验草稿（不落库） | 是 |
| POST | `/api/v1/catalog/assets/{assetType}/{id}/submit-review` | 提交审核 | 是 |
| POST | `/api/v1/catalog/assets/{assetType}/{id}/withdraw-review` | 撤回审核（REVIEWING → DRAFT） | 是 |

`assetType` 取值：`concept` / `property` / `relation` / `metric` / `dimension`；非法值直接 `1_005_000_105`，不做大小写归一化。

列表接口参数：`status`（可选，四态之一）、`keyword`（可选，匹配 id/name）、`page`（默认 1）、`pageSize`（默认 20，上限 100）。分页返回 `PageResult<SemanticAssetSummaryVO>`，摘要不含 `definition`，避免列表返回大字段。

**owner 来源（安全约束）**：`createDraft` 的 `owner` 只取 `RequestContextHolder.require().userId()`，**请求体不接受 owner / reviewer / status**；这三个字段由服务端状态机写入。请求体出现这些字段一律 `1_005_000_107`（fail-closed，不静默忽略——静默忽略会让调用方误以为设置生效）。

#### 3.2.2 关键请求 / 响应

**创建草稿**

```json
POST /api/v1/catalog/assets/metric/drafts
{
  "definition": {
    "id": "metric.order_amount",
    "name": "订单金额",
    "summary": "订单成交金额合计",
    "aliases": ["订单额"],
    "objectId": "concept.order",
    "propertyId": "property.order.amount",
    "aggregation": "SUM",
    "allowedModes": ["QUERY"],
    "allowedDimensions": ["dim.region"],
    "sensitive": false
  }
}
```

响应：

```json
{ "code": 0, "data": { "assetType": "metric", "id": "metric.order_amount",
  "status": "draft", "revision": 0, "version": "0.1.0" } }
```

**保存草稿**：`PUT .../draft`，body 为 `{ "definition": {...}, "expectedRevision": 0 }`；`revision` 不匹配返回业务码 `1_005_000_104`。HTTP 状态沿用项目统一 `CommonResult` 约定（200 + 业务码），不单独设 409——现有 controller 无 `@ResponseStatus`，新增例外会破坏前端统一解包。

**校验**：`POST .../validate`，body 可省略；省略时校验已存草稿，传入时校验入参（用于「保存前预检」）。响应：

```json
{ "code": 0, "data": { "valid": false,
  "violations": [ { "location": "metric.metric.order_amount", "message": "propertyId 引用的属性不存在或未发布: property.order.amount" } ] } }
```

`valid=false` 仍返回 HTTP 200（校验结果不是服务错误）；只有入参形状非法（缺 definition / ID 不一致）才抛 `1_005_000_107`。

**提交审核**：`POST .../submit-review`，body `{ "expectedRevision": 3 }`；先校验，`valid=false` 返回 `1_005_000_106` 并附 violations。

#### 3.2.3 鉴权

controller 层调用 `PublishGuard.requirePublishAllowed(assetId)`（装配点把它接到 system 的 `PolicyService.checkManagementAllowed`）：dev profile 放行，其余 403。这是 P0 的已知限制——**非 dev 环境该功能不可用**，等 ADR-0021 角色模型落地后替换为管理面角色校验。必须在接口注释与规格中同时标注，避免误以为已可生产使用。

`owner` 取 `PublishGuard.currentPublisher()`（认证上下文 userId），service 只接收 actor 参数、不依赖 web 上下文。

#### 3.2.4 错误码（catalog 段 `1_005_000_xxx`，现有 001–008 不复用）

| 码值 | 常量 | 语义 |
|---|---|---|
| `1_005_000_101` | `ASSET_NOT_FOUND` | 资产不存在 |
| `1_005_000_102` | `ASSET_ALREADY_EXISTS` | 同类型同 ID 已存在 |
| `1_005_000_103` | `ASSET_STATE_INVALID` | 状态迁移非法（附 from → to） |
| `1_005_000_104` | `ASSET_REVISION_CONFLICT` | 乐观锁冲突（附 expected / actual） |
| `1_005_000_105` | `ASSET_TYPE_INVALID` | assetType 非法 |
| `1_005_000_106` | `ASSET_VALIDATION_FAILED` | 校验未通过（附 violations） |
| `1_005_000_107` | `ASSET_DEFINITION_INVALID` | definition 形状非法 / ID 与路径不一致 |

### 3.3 关键流程

#### 3.3.1 草稿生命周期（P0 子集）

```
createDraft ──► DRAFT ──submitReview──► REVIEWING
                  ▲                        │
                  └──── withdrawReview ─────┘
```

- `createDraft` 只接受 `status=draft`。
- `saveDraft` 只允许 `DRAFT`；`REVIEWING` 下必须显式 `withdrawReview` 才能改（防止审核中内容漂移）。
- `review` / `publish` 不在 P0；状态机实现上直接拒绝（`ASSET_STATE_INVALID`），不预留空分支。
- `RETIRED` 为终态，P0 不可达。

#### 3.3.2 校验合并视图（关键设计）

草稿不能单独校验：`metric.propertyId` 需要属性存在，`property.conceptId` 需要对象存在，`scenario` 引用需要指标存在。因此校验必须在**「生效清单 + 草稿覆盖」的合并视图**上执行：

1. 取 active `PublishedManifest.payloadJson`，反序列化为 `ManifestPayload`（catalog 已依赖 ontology，可直接 `JsonUtils`）。
2. 深拷贝，按 `assetType` 定位数组，用草稿 definition **整体替换**同 ID 元素，或追加（新增资产）。
3. 调 `ManifestStructureValidator.validate(merged)` 拿全量 violations。
4. 只返回与本资产相关的 violations：`Violation.location()` 已核实为「类型名 + 资产 ID」格式（校验器用 `"metric." + metric.getId()` 拼接），直接按前缀匹配即可，无需数组索引：

| assetType | location 前缀 | 示例 |
|---|---|---|
| concept | `concept.` + id | `concept.concept.order` |
| property | `property.` + id | `property.property.order.amount` |
| relation | `relation.` + id | `relation.ontology.Order.attributedToChannel` |
| metric | `metric.` + id | `metric.metric.order_amount` |
| dimension | `dimension.` + id | `dimension.dim.region` |

5. **不缓存合并基线**（实施期对原设计的修正）：单次校验解析一次 active payload，管理面低频；要缓存必须深拷贝 payload 才能防止合并污染，成本与重新解析相同，收益为零。若实测成为瓶颈，再加 copy-on-write 缓存并补基准。

**注意**：location 是「类型名 + 资产 ID」的双前缀（如 `metric.metric.order_amount`），看起来冗余但为现状事实。T3 必须按此字面量匹配，**不得**按数组索引或 `semantic.metrics[...]` 猜测；若校验器未来改成单前缀，属于契约变更，需同步过滤逻辑并补测试。

#### 3.3.3 并发控制

```sql
UPDATE semantic_asset_definition
   SET definition = :definition, name = :name, summary = :summary,
       revision = revision + 1, updated_at = now()
 WHERE asset_type = :type AND id = :id AND revision = :expected AND status = 'draft'
```

影响行数为 0 时区分两种原因：记录不存在 → `ASSET_NOT_FOUND`；记录存在但 revision/status 不匹配 → `ASSET_REVISION_CONFLICT`（附当前 revision）。不使用 `SELECT ... FOR UPDATE`，避免管理面长事务占用连接。

#### 3.3.4 与发布的关系

- P0 的草稿**不进清单**：`PublishServiceImpl` 只接收请求体 payload，不读本表。
- P1 才把 `published` 状态的资产纳入发布合成；届时的约束是「只有 published 可进清单」，与 V15 的 scenario/skill/vqr 同规。
- 因此 P0 上线后，`active` 清单与 `published_snapshot` 均不变化，运行时零影响。

| 落点 | 说明 |

## 5. 测试用例与 Golden 样本

### 5.1 状态机与创建（7 例）

1. create 默认值（draft / owner / 0.1.0 / revision 0）
2. create 重复 → `ASSET_ALREADY_EXISTS`
3. `draft → reviewing` 合法
4. `reviewing → draft`（撤回）合法
5. `draft` 状态直接 `withdrawReview` → `ASSET_STATE_INVALID`（P0 没有 publish 入口，`reviewing → published` 是「未实现」而不是「被拒」，不写空分支）
6. `reviewing` 状态直接 `saveDraft` → `ASSET_STATE_INVALID`
7. `submitReview` 校验失败 → `ASSET_VALIDATION_FAILED`（附 violations 摘要）

### 5.2 并发与不可变（2 例）

1. `expectedRevision` 落后 → `ASSET_REVISION_CONFLICT`，附当前 revision
2. 保存时改 `definition.id` → `ASSET_ID_IMMUTABLE`

> `expectedRevision` 匹配成功、revision +1 由 §5.5 接口 happy path 覆盖，不重复计数。

### 5.3 类型与前缀（2 例）

1. `createDraft`：`assetType=metric` 但 `id=dim.region` → `ASSET_DEFINITION_INVALID`
2. `validate`：同上 → `ASSET_DEFINITION_INVALID`（validator 前置校验；DB CHECK 为第二层兜底）

### 5.4 草稿校验（5 例）

1. 合法指标草稿（引用 active 中已有对象/属性）→ `valid=true`
2. 引用不存在的属性 → `valid=false`，violation `location=metric.metric.gmv`
3. 覆盖 active 同 ID 指标（改 aggregation）→ 只校验覆盖后的视图，`valid=true`，不误报其他资产
4. 合法维度草稿 → `valid=true`
5. 空 definition → `ASSET_DEFINITION_INVALID`

### 5.5 接口与请求体（5 例）

1. 5 端点 happy path（create → save → validate → submit → withdraw，revision 0→3）
2. 管理面闸门拒绝 → `403`
3. 请求体带 `owner` → `ASSET_DEFINITION_INVALID`
4. 未知字段经真实 JSON 反序列化被 `@JsonAnySetter` 收集
5. `validate` 路径 ID 与 `definition.id` 不一致 → `ASSET_ID_IMMUTABLE`

合计 **21 例**（实施期相对设计稿 16 例新增：create 默认值 / create 重复 / 请求体拒绝服务端字段 / 未知字段反序列化 / validate ID 一致性，共 5 例）。
