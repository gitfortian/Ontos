## W3 复测（12:25）：候选集 + 会话隔离后，协议层 100%、语义层 62.5%

### 三个必须记住的坑

1. **候选集必须注入**。system prompt 说「只能引用候选集里的 ID」但模型看不到清单，
   结果它去 glob_files 找文件、起子 agent 检索，45s 一次还答错。
   加 `AgentContextProvider`（common 定义）+ ontology 实现后，8s、直接输出 `metric.gmv`。
2. **`AguiAgentRegistry` 只接受 `Supplier<Agent>`，拿不到 threadId** → 所有请求共用一个 session，
   `messages` 从 2 涨到 11，越跑越慢直到返回空。必须每请求独立 `defaultSessionId`。
3. **独立 session 会触发 `SessionLogException: Explicit reconciliation required for unknown tool calls`**
   （默认 EVENT_LOG 会话历史在做未完成工具调用对账）。改用 `SessionHistoryMode.LEGACY` 归零。
   这两个坑是连着的：改了 sessionId 才暴露第二个，不查日志根本看不出来（表现为「1 秒返回空」）。

### 指标口径要分开

判据「终态重建成功率 100%」其实含两层：
- **协议层**：JSON 可解析 + 落到五类之一 → 实测 **100%**
- **语义层**：与期望终态类别一致 → 实测 **62.5%**，五轮区间 50%–81%，不稳定

混在一起会把 prompt 问题误判成框架不达标。探针已拆成两个指标。

### 剩余失败都不是框架问题

「分析客户」返回 `OUT_OF_MANIFEST` 是对的（清单没客户维度）；「有哪些维度」用了 prompt 未定义的
`capability_answer`（模型自创字段，说明契约缺能力发现的表达）；复合问题因缺「客户数」指标只拆出 1 个。
→ 待办在契约层：补能力发现字段、明确澄清与超能力边界、加 JSON Schema 校验 + 重试。

### 代价

M0 不支持多轮上下文。M1 必须按 threadId 维护 agent 实例或在适配层做映射。

### 契约层（12:40）：68.8%，卡点转到模型遵循度
